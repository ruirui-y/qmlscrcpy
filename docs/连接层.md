# 连接层

目标：把设备上的 `scrcpy-server` 拉起来，拿到"视频 socket + 控制 socket"这一对连接，并读出设备名和分辨率。

## 两种隧道

```
reverse（默认，优先）
  设备侧先监听 localabstract:scrcpy_xxxxxxxx
  主机 adb reverse 把这个名字转到本机 tcp:27183
  server 起来后【反向】连过来 → 主机 accept

forward（reverse 失败时的降级）
  主机先监听 tcp:<随机端口>
  adb forward 把本机端口转到设备侧的 localabstract 名
  server 起来后不主动连，【主机主动连】两个端口
```

两条路径的**连接顺序不一样**，这是踩出来的：

```
reverse：先 accept 视频 → 立刻读设备信息 → 再 accept 控制
         （adb 转发会把两条连接串行化，先接控制会让视频卡住）

forward：先连视频 + 控制两个 socket → 再读设备信息
         （server 在两条连接都建好之前不发数据，只发 1 个 dummy 字节）
```

代码：`libs/session/server_session.cpp` 的 `AcceptForReverse` / `ConnectForForward`。

## 建链流程

```
① push      第三方的 scrcpy-server 推到 /data/local/tmp/scrcpy-server.jar
              （只在文件大小/时间戳不一致时才推，省 300ms）

② 建隧道    adb reverse localabstract:scrcpy_%08x tcp:27183
              失败（国产机常见 more than one device）→ 降级 forward

③ 起进程    adb shell CLASSPATH=/data/local/tmp/scrcpy-server.jar app_process \
              / com.genomic.scrcpy.Server <参数...>
              参数拼错会立刻退出，所以起完等 800ms 看一眼有没有报错，
              有就把 server 的 stderr 原样带给界面

④ 拿 socket  见上面的顺序说明

⑤ 读设备信息  固定 76 字节：
              [0..63]  设备名 UTF-8，后面补 0
              [64..67] 编码器 id（当前固定 H.264，不解析）
              [68..71] 视频宽
              [72..75] 视频高
```

## server 参数

`libs/session/server_args.cpp` 拼的，我们实际用的几个：

| 参数 | 值 | 为什么 |
|---|---|---|
| `max_size` | 0（不缩放） | 720 拉到全屏窗口会糊，见 [渲染方案](渲染方案.md) |
| `bit_rate` | 12 Mbps | 原生分辨率下 8 Mbps 也不够 |
| `max_fps` | 不打（设备默认） | 设备给 60fps 已经够 |
| `control` | 默认开 | P4 要用 |
| `log_level` | error | 只留错误，日志太多会拖慢 adb shell |

## 一个容易忽略的点

连接是**同步阻塞**的，全程约 1.4 秒（逆推到 `[session] 连接完成 ... 耗时 1417 ms`）。这期间 GUI 线程卡住，界面不响应。

之所以敢这么写：`ServerSession` 持有 `QTcpServer` / `QProcess`，这些对象必须活在创建它们的线程里。把它挪到子线程就要处理"跨线程 Stop"的问题——之前试过，直接触发了 Qt 的 `Cannot send events to objects owned by a different thread` 断言。1.4 秒的卡顿是当时权衡后的选择，后面如果要优化，方向是把整个 session 连同它的 socket 都搬到一个专门的连接线程里，而不是只搬一部分。

## 超时与失败

| 环节 | 超时 | 失败表现 |
|---|---|---|
| adb 命令 | 5 s | `AdbResult::ErrorText()` 给原因 |
| reverse 后等 accept | 5 s | 降级 forward |
| forward 后等连接 | 5 s × 若干次 | 报"连不上 server" |
| 读设备信息 | 5 s | 报"server 没发设备信息" |

`DrainServerOutput()` 会把 server 进程这段时间打印的东西读干净、只留尾部，失败时能原样报给界面——比"连接失败"这种话有用的多。
