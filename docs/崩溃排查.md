# 崩溃排查

程序崩了、卡死、或者画面突然没了，按这篇走：先把证据拿到手（dump + 日志），再谈修改。

## 1. 先分清楚是哪种"崩"

| 现象 | 通常是什么 | 有没有 dump |
|---|---|---|
| 弹「遇到问题需要关闭」后消失 | 未处理异常（空指针、越界、断言） | 可以抓 |
| 窗口变白 + "(未响应)" | 主线程阻塞（同步等待、死循环） | 抓不到，得看调用栈 |
| 界面全没了、进程还在 | QML 加载失败（整个 Window 创建失败） | 没有，看 stderr / 日志 |
| 画面卡住但窗口能动 | 渲染线程/视频线程问题 | 没有，看 `[perf]` 日志 |

**先看日志**（省事）：`<程序目录>\Log\LOG_yyyy_MM_dd.log`。我们的日志里 `[app]`、`[session]`、`[perf]` 三个前缀能覆盖大半问题。

## 2. 拿到 dump 的三种方式

### 方式 A：任务管理器（最简单，事后抓不到）

现象出现时进程还没退出 → 任务管理器 → 详细信息 → 右键 `QmlScrcpy.exe` → **创建转储文件**。

缺点：要人工来得及点；崩溃瞬间进程已经没了就没法抓。

### 方式 B：Procdump（推荐，自动等异常）

```powershell
# 先下 Sysinternals Procdump，解压后用管理员权限跑
procdump -accepteula -e -ma -w QmlScrcpy.exe D:\dumps
```

| 参数 | 作用 |
|---|---|
| `-e` | 等**未处理异常**才抓（不写 1 就是抓第一次异常，可能抓到"被捕获的异常"） |
| `-ma` | 全内存 dump（能看局部变量和堆） |
| `-w` | 等 `QmlScrcpy.exe` 启动后再挂上，不用掐时间 |

抓出来是 `D:\dumps\QmlScrcpy.exe_日期_时间.dmp`。

### 方式 C：注册表开全局 LocalDumps（一劳永逸）

```powershell
$key = 'HKLM:\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\QmlScrcpy.exe'
New-Item -Path $key -Force | Out-Null
New-ItemProperty -Path $key -Name DumpFolder -PropertyType ExpandString -Value 'D:\dumps' -Force | Out-Null
New-ItemProperty -Path $key -Name DumpType   -PropertyType DWord       -Value 2         -Force | Out-Null
```

| 值 | 含义 |
|---|---|
| `DumpType=1` | 迷你 dump（小，只能看调用栈） |
| `DumpType=2` | 全内存（大，能看变量和堆） |

设完以后**每次崩溃自动落盘**，不用守着。排查完记得删掉这个键，不然磁盘会被 dump 塞满。

## 3. dump 和 pdb 必须对上

调试器匹配符号靠 exe 的「时间戳 + 镜像大小」，所以 dump 必须配**同一版本的 exe + pdb**。

`setup\collect.ps1` 每次打包都会留一份：

```
setup\Output\pdb\20261112_162033\
├─ QmlScrcpy.pdb
└─ QmlScrcpy.exe
```

拿到用户发来的 dump 后，先确认它来自哪个版本的包（让用户报安装包版本 + 崩溃时间，或看 dump 里的模块信息），再用对应时间戳目录里的 pdb。

**对不上会怎样**：`kb` 里只有地址没有函数名，白白浪费一个 dump。

## 4. 用 WinDbg 分析

```powershell
windbg -z D:\dumps\QmlScrcpy.exe_261112_162500.dmp -y "srv*;H:\YJJ\Project\QmlScrcpy\setup\Output\pdb\20261112_162033"
```

`-y` 后面 `srv*` 表示"没有本地符号就去微软符号服务器找"（Qt 的 DLL 符号没有，但系统 DLL 有，能看清调用链在哪断的）。

进去先敲四条：

```
!analyze -v     ; 自动分析：异常码、出错模块、可能的调用栈
.ecxr           ; 切到异常发生的上下文（不切的话看到的是调试器自己的栈）
kb              ; 带参数的调用栈，能看出每层传了什么
lm              ; 加载了哪些模块（确认 Qt 版本、有没有第三方 DLL）
```

**怎么读**：

- 栈里**最上面几帧是 `QmlScrcpy.exe!...`** → 我们的代码，看函数名 + 行号（有 pdb 就有行号）
- 栈里全是 `Qt5Qml.dll!...` 反复出现几十次 → **栈溢出**（递归或 QML 绑定死循环）。我们踩过一次：ToolTip 加 `popupType: Popup.Window` 启动就崩，就是这个形状
- `ASSERT` 类：`QVector::first()` / `QString::at()` 这种"容器空了还取元素"，看调用栈往上找谁传了空
- `!analyze -v` 给出 `FAIL_FAST_...` 一般是 Qt 的 `qFatal`（比如 `assert: "!isEmpty()"`）

## 5. 用 Visual Studio 分析（没有 WinDbg 时）

1. VS → 文件 → 打开 → 文件 → 选 `.dmp`
2. 右侧「符号设置」→ 添加 pdb 目录 `setup\Output\pdb\<时间戳>`
3. 点「**使用仅限本机进行调试**」
4. 看「调用堆栈」窗口；没有行号就在「模块」窗口确认 exe/pdb 是否匹配

## 6. 没有 dump 时怎么定位

### 崩溃前的日志

```powershell
Select-String -Path Log\*.log -Pattern 'ERROR|WARN|ASSERT' | Select-Object -Last 20
```

### 卡死（未响应）

日志会**突然停住**在某一行，那一行就是它最后在做的事。我们同步阻塞的地方只有几处：

- `Connect()` 建链（1~2 秒，正常）
- `EnableWifi()` 切无线（已经丢到工作线程）
- 弹「重置」时写配置

如果卡在别的地方，基本可以断定是新加的同步调用。

### 画面卡但窗口能操作

看 `[perf]` 那一秒的数字：

```
[perf] 0 轮：GUI 排队 ... | 取帧 ... | 画一帧 ... | 两轮间隔 ...
```

- 一行 `[perf]` 都没有 → 一帧都没画过（socket 断了 / 服务端挂了 / `update()` 没发出去）
- `两轮间隔` 远大于 `取帧 + 画一帧` → 时间花在 Qt 的交换缓冲和等唤醒上，不是我们代码
- `GUI 排队` 变大 → GUI 线程被别人堵住了

## 7. 已经踩过的坑（对照着看）

| 现象 | 根因 | 教训 |
|---|---|---|
| 启动就消失，栈里全是 Qt5Qml 帧 | ToolTip 用 `popupType: Popup.Window` + 自定义 contentItem，导致递归 | 同一组件连续三次以不同方式崩，就换方案 |
| 启动弹 `ASSERT: "!isEmpty()" in qvector.h` | 同一 ToolTip 的另一种崩法 | `first()` / `last()` 用之前必须判空 |
| 启动后"程序没窗口" | QML 加载失败（函数名大写、`Layout` 没 import） | 看 stderr 里 `qrc:/qml/xxx.qml:行号` |
| 无线切界面卡顿 | 不是崩溃，是码率超发导致带宽排队 | 先看 `[perf]` 的 `KB/s` 再猜 |

## 8. 给用户的收集清单

让出问题的人提供这几样，比来回问十轮快：

1. 安装包版本（`QmlScrcpy_Setup_x.y.z.exe`）
2. 崩溃时间（精确到分钟）
3. `Log\LOG_yyyy_MM_dd.log` 那天的文件
4. `config\window.ini`（能看出当时的窗口状态、连的是哪台设备）
5. 崩溃 dump（如果他愿意抓）
6. 手机型号、Android 版本、有线还是无线
