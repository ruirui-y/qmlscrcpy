# P0 · CMake 骨架 + QML 空窗口

## 1. 这一阶段要做什么

建一个能干活的骨架：CMake 能配置、能编译、能跑出一个空 QML 窗口，把编译选项、部署、测试三件事先搭好。不写任何业务逻辑。

## 2. 怎么做的

- CMakePresets 而不是命令行参数（任何 shell 都能配，不用开发者命令行）
- 编译选项做成 `INTERFACE` 目标 `qs_options`，所有目标继承（`/W4 /permissive- /utf-8`）
- 部署走一个 `cmake -P` 脚本，而不是 `add_custom_command` 里直接调 windeployqt

## 3. 为什么第一版不理想

**① 部署命令把 shell 搞崩了**

```
pwsh.exe 不是内部或外部命令，也不是可运行的程序
```

原因：`add_custom_command` 里把 `$ENV{PATH}` 拼进命令行，Windows 的 PATH 里全是分号，被 CMake 当成命令分隔符拆开了。

**② 部署完 QML 加载失败**

现象：程序起来了，但是白窗口，日志里 `qrc:/qml/MainWindow.qml: module "QtQuick" is not installed`。

**③ 本机 PATH 里第一个 Qt 是 5.14.2**

`windeployqt` 用的是 5.14 的那个，部署出来的东西和 5.15.2 编出来的二进制对不上，QML 模块直接找不到。

## 4. 怎么定位的

- ①②都是"命令行被拆开"，先怀疑引号/转义，改成 `cmake -P` 脚本后消失——脚本里 `set(ENV{PATH} ...)` 不经过 shell
- ③是 `where windeployqt` 打出来的路径不是 5.15.2，确认是 PATH 顺序问题

## 5. 怎么解决的

```cmake
# cmake/DeployQt.cmake：先把 Qt 的 bin 塞到 PATH 最前面，再跑 windeployqt
set(ENV{PATH} "${QS_QT_ROOT}/bin;$ENV{PATH}")
execute_process(COMMAND windeployqt --qmldir ... )
# 部署完强制自检，没 QML 模块就直接 FATAL_ERROR，不要静默产出坏包
file(GLOB qml_modules "${deploy_dir}/QtQuick*/qmldir" ...)
```

## 6. 最终效果与收获

- `cmake --preset windows-debug` + 构建 + `ctest` 三条命令可用
- 收获：**CMake 的自定义命令不要碰 PATH 这种带分号的变量**；部署脚本必须自检，宁可在构建期报错

# P1 · 协议层

## 1. 这一阶段要做什么

把 scrcpy 的线路格式实现成纯逻辑库：12 字节视频包头、12 种控制消息、3 种设备消息。要求脱离设备和网络就能单测。

## 2. 怎么做的

- 三个头文件一个 cpp：`wire.h`（大端读写）、`video_packet.*`、`control_message.*`、`device_message.*`
- 设备消息解析用三态返回：正数=消费字节数，0=数据不够，-1=流坏了。这样调用方可以直接塞进循环里处理半包
- 只依赖 QtCore，不依赖网络/界面

## 3. 为什么第一版不理想

**① 测试编译不过，报"宏参数个数不对"**

```cpp
QCOMPARE(AdbArgs::Devices(), QStringList{QStringLiteral("devices")});
```

`QCOMPARE` 是宏，`QStringList{a, b}` 里的逗号被当成宏参数分隔符了。

**② 换文件后突然一堆"缺少函数标题 / 未声明的标识符"**

现象：同一个头文件，加了几行中文注释之后编译报错，报的位置还莫名其妙。

## 4. 怎么定位的

- ①一看就明白是宏展开，不用猜
- ②先怀疑是声明写错，逐行注释掉对照；最后发现**报错的行号对应的是注释里的中文**——是编码问题

## 5. 怎么解决的

- ①写了个 `Argv({...})` 辅助函数，把初始化列表先收进一个变量再比较
- ②给 `qs_options` 加 `/utf-8`，并且让它对 `qs_ffmpeg` 也生效（不然那个目标读中文注释还是按 GBK）

## 6. 最终效果与收获

- 23 条单测全绿
- 收获：**MSVC 默认按本地代码页读源文件，中文注释不带 `/utf-8` 会把后面一行吃掉**

# P2a · adb 命令层

## 1. 这一阶段要做什么

把 adb 命令拼装和进程执行封成库：设备列表、push、reverse/forward、shell。仍然不碰业务。

## 2. 怎么做的

- `AdbArgs` 静态方法，每个方法返回 `QStringList`（不拼字符串，路径带空格也不会被拆开）
- `AdbResult` 带 stdout/stderr/退出码，`ErrorText()` 优先给 stderr
- `adb.exe` 不入库，运行时按 `SetAdbPath()` → `QS_ADB_PATH` → 程序目录 → PATH 找

## 3. 为什么第一版不理想

真机连上之后，server 起来了但立刻退出，日志只有一句：

```
[server] ERROR: Could not connect to local socket
```

## 4. 怎么定位的

先怀疑 server 参数错（对照 scrcpy 文档逐项核），没问题；再怀疑端口没监听，`adb reverse --list` 一看——隧道建了，但方向反了。

## 5. 怎么解决的

`adb reverse` 的两个参数顺序写反了。正确是**设备侧在前**：

```
adb reverse localabstract:scrcpy_xxxxxxxx  tcp:27183
              ↑ 设备侧监听的名字            ↑ 本机端口
```

`forward` 反过来：本机端口在前，设备侧名字在后。改成两个显式的方法各自拼，不做"通用隧道"抽象。

## 6. 最终效果与收获

- 14 条单测（含真机 `adb version`）
- 收获：**reverse 和 forward 的参数顺序是相反语义，抽象成一个函数必然出错**

# P2b · 连接状态机

## 1. 这一阶段要做什么

一条完整的建链流程：推 server → 建隧道 → 起进程 → 拿视频/控制两个 socket → 读设备信息。

## 2. 怎么做的

`ServerSession::Start()` 同步阻塞执行（约 1.4 秒），内部拆成 `PushServer` / `SetUpTunnel` / `StartServerProcess` / `ConnectSockets` / `ReadInfo` 五个小函数，每个出错都带原因。

## 3. 为什么第一版不理想

**① reverse 模式只收到一个连接**

视频 socket 连上了，控制 socket 一直等到超时。

**② 改成"先接控制"之后，视频又卡住**

**③ forward 模式 server 起不来**

日志停在 server 输出的第一行，之后没有任何数据。

**④ 把 session 挪到子线程后直接崩**

```
ASSERT failure in QCoreApplication::sendEvent: "Cannot send events to objects owned by a different thread.
Current thread 0x..., receiver 'QTcpServer' (of type 'QTcpServer') was created in thread 0x..."
```

## 4. 怎么定位的

- ①埋点发现 accept 只成功一次 → 查 adb 文档：**adb 的转发会把同一条隧道的连接串行化**，第二条要等第一条的数据流先动起来
- ②于是试"先读设备信息，再 accept 控制" → 成功。设备信息是从**视频 socket** 上发过来的，先把它读掉，第一条连接才算"处理完"
- ③forward 模式对比 reverse：server 在两条连接都建好之前只发 1 个 dummy 字节。所以必须**先把两条连接都建起来，再去读**
- ④栈很明确：`QTcpServer` 在子线程创建、主线程调 `Stop()` 触发事件投递

## 5. 怎么解决的

```
reverse：accept 视频 → 立刻读设备信息 → 再 accept 控制
forward：连视频 + 连控制 → 再读设备信息
```

④没有硬修，改成**连接全程在主线程同步执行**（1.4 秒卡顿），换来对象生命周期简单。真要修就整体搬到一个专门的连接线程，而不是只搬一部分。

## 6. 最终效果与收获

- 真机建链成功：`[session] 连接完成："RMX5010" QSize(1264, 2776) reverse 耗时 1500 ms`
- 收获：**阻塞式握手 + 框架对象 = 线程归属问题**；顺带记住"adb 转发会串行化连接"这个反直觉行为

# P3 · 视频链路（最折腾的一段）

## 1. 这一阶段要做什么

从视频 socket 读字节 → 解 H.264 → 变成屏幕上的画面。目标 60fps、低延迟。

## 2. 怎么做的（最终形态）

```
视频线程：waitForReadyRead → 切帧 → 解码 → emit FrameReady（直连）
渲染线程：synchronize 取帧 + 拷三平面 → render 上传 3 张纹理 + 着色器 → FBO
Qt：把 FBO 当纹理合成到窗口 → DWM → 屏幕
```

期间试过四种渲染方案、崩了五次，下面按顺序讲。

## 3. 为什么第一版不理想（按发生顺序）

**① sws_scale 直接写进 QImage 缓冲 → 堆损坏**

```
0xC0000374: 堆已损坏
```

现象：偶尔崩，崩在完全无关的地方（有时是块析构）。

**② 自定义材质 + 每帧换纹理 → 崩在 bind()**

```
Invalid texture accessed: 0x0
Aborting: scene graph is invalid
```

**③ 材质持有 AVFrame 跨帧 → 断开连接时 use-after-free**

```
YuvMaterial::Sync() 行 206
std::shared_ptr<void const>::~shared_ptr
std::_Ref_count_base::_Decref
```

**④ 在 updatePaintNode 里调 GL → 绿屏 + 退出崩**

**⑤ 继承 QSGTexture 自己上传 → 崩在虚调用**

```
YuvShader::updateState 行 213
texture->bind()
```

**⑥ FBO 方案跑通后：画面上下颠倒、标题栏糊成一团**

**⑦ 拖窗口卡 5 秒**

**⑧ 缩放窗口卡几秒**

**⑨ 画质很糊**

## 4. 怎么定位的（逐个说）

**①** 先怀疑解码器线程不安全，单线程跑还是一样；后来注意到只有窗口尺寸不是 32 的倍数时才崩——`QImage` 每行是紧凑的，没有 FFmpeg 需要的对齐填充，`sws_scale` 按 stride 写就越界。改成 `av_image_alloc` 分配目标帧、再逐行 memcpy 回 QImage。

**②** 栈指向 `bind()`，说明对象被删了。谁删的？我每帧 `delete` 旧纹理，但**渲染器缓存着材质指针**，它下一次用时就是野指针。

**③** 栈很直白：`pending_ = Frame()` 触发的析构里崩。对着代码推演发现：材质把帧持有到"下一帧渲染时"才放，而这期间用户点了断开 → 解码器销毁 → 帧的缓冲区跟着没 → 再释放就是访问已释放内存。

**④** `updatePaintNode` 是同步阶段，不是渲染阶段，GL 上下文状态不保证。绿屏说明上传根本没生效。

**⑤** `QSGTexture` 的生死不归我们管，Qt 的渲染器缓存着它。这条路（自己实现 `bind()`）理论上是对的，但配合 Qt5 的材质缓存就是不稳定。

**⑥** 两个独立的错：FBO 的 y 轴朝上，我按"v=0 在顶部"映射 → 整幅翻过来；另外我用完 1、2 号纹理单元没切回 0 号，Qt 接着画自己的文字时还停在 2 号单元，采样到我的平面纹理 → 文字糊成一条。

**⑦** 一开始以为是解码慢，上了埋点：

```
[perf] fps 61 等数据 15.5ms 解码 0.44ms 转换 0.33ms 上屏 0.02ms
```

每帧处理只有 0.8ms，60fps 稳态——**根本不是算不动**。真正的现象是：拖窗口时 fps 从 61 掉到 15。

继续查：从视频线程 `update()` 会往 GUI 线程投事件，而拖窗口时 GUI 线程卡在 Windows 的系统模态循环里，这一投就把视频线程堵住了。改成"视频线程只存帧，GUI 线程用 8ms 定时器来取"之后，fps 回到 61。

**⑧** 缩放时窗口卡住不动，测出来是 `QSettings::sync()` 在每个 `onWidthChanged` 里都落盘，一秒上百次写文件。

**⑨** 不是抗锯齿问题：720p 的 328×720 被拉到 545 宽显示，是**物理放大**。

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 堆损坏 | `av_image_alloc` 分配目标帧 + 逐行 memcpy |
| ②③④⑤ 四次崩溃 | 全部放弃，改用 `QQuickFramebufferObject`：`render()` 是 Qt 保证"渲染线程 + 上下文当前"的唯一入口 |
| ③ 帧寿命 | 渲染器只拷像素（5.2 MB / 1ms），不持有 AVFrame；断开时先 `Clear()` 再关解码器 |
| ⑥ 上下颠倒 | 顶点 v 轴反向（顶部用 v=1） |
| ⑥ 标题栏糊 | `render()` 结束前还原 GL 状态（纹理单元回 0、像素对齐回 4） |
| ⑦ 拖拽卡 | 视频线程不投递任何跨线程事件；重绘由 GUI 线程定时器发起 |
| ⑧ 缩放卡 | 位置尺寸改成停手 400ms 后防抖写盘 |
| ⑨ 画质糊 | 采集改原生分辨率（`max_size=0`），窗口按帧的物理像素定大小 |

## 6. 最终效果与收获

```
fps 61   等数据 6.5ms   解码 5.6ms   转换 0ms   上屏 0.4ms
```

- CPU 只剩 H.264 解码；RGB 转换在 GPU 上
- 拖动窗口画面不冻、不积帧；缩放不再卡
- 收获：
  - **Qt5 场景图里 GL 的合法时机只有 `render()`**，`updatePaintNode` 不是
  - **跨线程投递事件要小心**：GUI 线程可能被系统模态循环扣住
  - **先埋点再优化**：我一开始认定是解码慢，数据和结论完全相反

# P3.5 · 窗口与交互

## 1. 这一阶段要做什么

把"控制 + 画面挤在一个窗口"拆成两扇窗，加上缩放、记忆、无边框拖动。

## 2. 怎么做的

- 控制窗（序列号 + 连接/断开 + 状态/帧率）和投屏窗分离
- 投屏窗无边框、自绘 28px 标题栏（拖动 + 最小化 + 关闭），左上右下各一个缩放把手
- 窗口位置写 `userdata.ini`，位置随时记、尺寸只在用户手动改过时记

## 3. 为什么第一版不理想

**① 系统标题栏拖动 → 画面冻住**

**② 缩放时窗口不跟手，卡 5 秒**

**③ 窗口被系统压成 650×2403**

**④ 勾选框文字看不见**

**⑤ `Cannot assign to non-existent property "palette"`**

## 4. 怎么定位的

- ①前面 P3 已经查明：系统拖拽进模态循环，GUI 线程被扣。**换无边框 + 自己处理鼠标移动**就绕开了（事件循环一直在转）
- ②P3 里是 `QSettings::sync()` 每次事件写盘；这次又叠了一个：`updatePaintNode` 在没有新帧时直接返回，画面矩形不更新，所以窗口变大画面不变。两个都修
- ③按帧的物理像素定窗口，但原生 1264×2776 比屏幕还高，只夹了宽度 → 高度被系统硬压
- ④`Window` 上设 `palette` 报错——palette 是 Control 的属性，Window 没有。改成给每个控件单独配色 + 勾选框不带文字
- ⑤同上，一眼看日志就知道

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 拖动冻画面 | 无边框 + 自绘标题栏 + 自己算鼠标位移（按屏幕绝对坐标取差值） |
| ② 缩放卡 | 写盘防抖 400ms；没有新帧时也重算画面矩形 |
| ③ 被压 | 宽高都按屏幕可用区域（85%）收缩 |
| ④⑤ 看不见/报错 | 控件单独配色，勾选框用无字 CheckBox + 独立 Label |

## 6. 最终效果与收获

- 投屏窗 328×748（720 画面 + 28 标题栏），拖动顺畅、两个角都能缩放、位置尺寸会记住
- 收获：**Qt Quick 里"能拖动的窗口"必须绕开系统拖拽**；**写盘这类副作用永远要防抖**

# P4a · 输入层：坐标与触摸

## 1. 这一阶段要做什么

把画布坐标换算成视频帧坐标，并拼出触摸/滚轮控制消息。纯逻辑，脱离设备可单测。

## 2. 怎么做的

- `CoordinateMapper`：两种模式（拉满 / 等比居中）
- `TouchController`：按下/移动/抬起/滚轮 → `protocol::ControlMessage`
- 5 条单测逐字段断言 32 字节触摸消息

## 3. 为什么第一版不理想

单测直接失败：

```
Actual   (near_right)     : QPoint(60,100)
Expected (QPoint(90, 100)): QPoint(90,100)
```

## 4. 怎么定位的

对着数字推：画布 200×200，帧 100×200，等比缩放应该缩到 1 倍（一个帧像素 = 一个画布像素），画面居中后左右各 50px 黑边。点 (120,100) 应该在帧坐标 (70,100)。

实际算出 60，说明**偏移没生效**。再看代码：`scale_x = frame_w / item_w` 是"画布→帧"的比例，我却把它当"帧→画布"去算可见宽度（`frame_w / scale_x`）——方向用反了。

## 5. 怎么解决的

```cpp
// 改前：把两个方向混着用
const qreal scale_x = frame_size_.width() / item_size_.width();
offset_x = (item_size_.width() - frame_size_.width() / scale) / 2.0;

// 改后：统一用"一个帧像素占几个画布像素"
const qreal fit_x = item_size_.width() / frame_size_.width();
offset_x = (item_size_.width() - frame_size_.width() * fit_x) / 2.0;
帧坐标 = local_x / fit_x;
```

## 6. 最终效果与收获

- 5 条单测全绿，`ctest 7/7`
- 收获：**这类几何换算一定要用单测钉死**，纯靠眼看代码发现不了方向错

# P4b · 输入层：键盘

## 1. 这一阶段要做什么

Qt 按键 → 安卓键码，处理自动重复次数和修饰键 metaState。

## 2. 怎么做的

- `keycode_table.*`：字母/数字/F1~F12 用连续区间，其余逐个映射；未映射返回 0
- `key_controller.*`：自己数重复次数（`QHash<int,int>`），抬起清零
- 7 条单测

## 3. 为什么第一版不理想

**① 测试进程直接崩**

```
QFATAL : KeyTest::AutoRepeatCounts() ASSERT: "uint(i) < uint(size())"
in file .../qbytearray.h, line 500
```

**② 修完崩溃后发现长度断言失败**

```
Actual   (first.size()): 14
Expected (21)          : 21
```

## 4. 怎么定位的

- ①先是以为 `Press()` 返回了空数组，加了 `QCOMPARE(first.size(), 21)` 才看清：其实是 14 字节，我按 21 去读偏移 13，越界。**崩溃不是"二次求值"，是长度算错**——我最初的猜测（QCOMPARE 展开两次）是错的，用 size 断言排除了它
- ②读数：`control_message.cpp` 里 `InjectKeycode` 是 `type(1) + action(1) + keycode(4) + repeat(4) + meta(4)`，一共 **14** 字节。我按"5 字节头 + 4 字节 action"算成了 21

顺带发现 `MakeHeader` 上面的注释写着"拼 12 字节控制消息头"，实际只有 1 字节类型头——**注释是错的**，一起改了。

## 5. 怎么解决的

- 测试里的长度和偏移全部按 14 字节改（action 在 1、keycode 在 2、repeat 在 6、meta 在 10）
- 修掉那句错误注释，避免下一个人（包括我）再被误导

## 6. 最终效果与收获

- 7 条键盘单测全绿，`ctest 8/8`
- 收获：
  - **不要凭印象写协议的字节偏移**，去读实现，或者直接断言 size
  - 崩溃时先确认"对象多长"，再怀疑宏/求值顺序

# P4c · 接线：把输入接到控制 socket

## 1. 这一阶段要做什么

**③ 启动后日志里出现两次"开始连接"，一次 wifi 序列号一次 usb 序列号**

## 4. 怎么定位的

- ①看名字就明白了：`SendMessage` 是 `<windows.h>` 里的宏（`SendMessageA/W`），我的私有方法名被宏替换掉了。改成 `EmitControlMessage`

- ③先怀疑代码里有两处自动连接，grep 只找到 `main.cpp` 一处；再加两行临时探针打印"谁在调 Connect"，结果只有 main 一次。**最后发现是用户中途手动点了"连接"按钮**——输入框里是 `proposedSerial`（usb 序列号），于是第二次连接用另一个序列号。不是 bug，探针撤掉

## 6. 最终效果与收获

# P4d · 日志与配置

## 1. 这一阶段要做什么

输入接了线但点了没反应，没有任何线索可查。先建日志模块和配置文件，不然只能靠猜。

## 2. 怎么做的

- `libs/base/log.*`：`QLoggingCategory` 分类 + `qInstallMessageHandler` 落文件
- 按天一个文件 `Log/LOG_yyyy_MM_dd.log`，启动时删掉超过 15 天的
- `config.ini` 存用户设置（日志级别、采集参数），`window.ini` 存窗口位置尺寸
- 输入链路埋四个观测点（事件进来 / 消息拼出 / 写 socket / socket 不可用）

## 3. 为什么第一版不理想

**① `config.ini` 里的中文注释被写成乱码**

```
# 视频采集：长边上限...
```
变成了

```
%23%20%E8%A7%86%E9%A2%91%E9%87%87%E9%9B%86...
```

**② 链接 qsc_session 的测试全都报未解析符号**

```
LNK2019: 无法解析的外部符号 qsc::base::lcInput(void)
```

**③ `QDir::remove` 编译不过**

```
error C2662: "bool QDir::remove(const QString &)": 不能将 "this" 指针从 "const QDir" 转换
```

## 4. 怎么定位的

- ①现象很明确：所有 `#` 开头的行都被百分号转义了。查 QSettings 行为：**它写回文件时会重新生成整个 INI，注释按 key 转义**，所以只要程序写过一次配置，注释必然被破坏
- ②测试目标只链了 `qsc_session`，而 `qsc_session` 现在用了日志分类；分类符号在 `qsc_base` 里
- ③编译器说得很清楚，`remove()` 不是 const 成员

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 注释被破坏 | **拆成两个文件**：`config.ini` 我们只读、绝不写；程序状态放 `window.ini`。这样用户可以放心写注释 |
| ② 未解析符号 | `qsc_session` / `qsc_stream` 都 PUBLIC 链接 `qsc_base`，依赖方自动继承 |
| ③ const 对象 | `const QDir dir(...)` 改成 `QDir dir(...)` |

## 6. 最终效果与收获

```
config.ini    注释完好，用户改完重启生效
window.ini    只有 x/y/w/h，没有注释
Log/LOG_2026_11_12.log    当天日志，超 15 天自动清
```

- 收获：
  - **`QSettings` 不是配置文件的编辑器**，它只适合"程序自己的状态"；给用户看的配置要自己控制写入
  - 库之间加依赖时，`PUBLIC` 会把传递依赖带出去，别忘了目标本身也要能解析

## P4c 追记：真凶是那行没加上的 connect

上面第三节说"点下去没反应"，那时还没有日志。日志建好之后第一次抓就抓到了：

# P5 · 控制窗重做 + 标题显示设备 + 启动自动连接

## 1. 这一阶段要做什么

四件事：控制窗太难看、换屏幕之后按钮变成白条、标题栏应该显示连的是哪台设备、启动时希望能自动连上次的设备（只连一次）。

## 2. 怎么做的

- 控制窗全部改成自绘控件（`ActionButton` = `Rectangle` + `Text` + `MouseArea`），输入框只覆盖 `background`
- 布局改成"标题行 + 两张圆角卡片"：串号卡片、状态卡片，状态前面一个绿/灰小圆点
- 投屏窗标题绑 `deviceController.deviceName`

**① 换到另一块屏幕后，按钮变成一排白条**

第一版直接用了 `Button` / `TextField` 的默认样式。深色窗口上默认样式是浅色底，而且换到不同缩放比例的屏幕时，背景按新 DPI 重算、尺寸约束没跟上，就截成了半截白条。

**② 标题是写死的 "QmlScrcpy — 投屏"**

**③ 工具栏没有回到控制窗的入口**

投屏窗和工具栏都是独立窗口，控制窗被别的窗口盖住之后只能去任务栏找。

**④ 每次启动都要手点「连接」**

调试时还好，日常用太烦。

## 4. 怎么定位的

- ②③④ 都是功能缺失，不需要定位

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 白条 | 控件全自绘：按钮用 `Rectangle`，输入框只覆盖 `background`，颜色写死 |
| ② 标题 | `VideoWindow.title` 绑 `deviceController.deviceName`，连上设成串号、断开清空 |
| ③ 回主窗 | 工具栏加「主窗」按钮，`control.requestActivate()` + `control.raise()` |
| ④ 自动连 | `PickStartupSerial()`：候选串号必须在 `adb devices` 的在线列表里，否则不连 |

# P6 · 设备列表 + 一键切无线 + 控制窗位置

## 1. 这一阶段要做什么

三件事：主窗里要能看见在线设备并选一台；不插线也能切到 wifi 调试；控制窗每次启动都跑到另一块屏幕上，位置要记住。

## 2. 怎么做的

- `RefreshDevices()` 除了填 `proposedSerial`，还把在线列表存进 `devices_`，通过 `Q_PROPERTY(QStringList devices)` 给 QML 的 `ComboBox` 当 model
- 新增「切无线」：`adb tcpip 5555` → 轮询 `ip route` 问 IP → `adb connect ip:5555`（失败重试 3 次）
- 控制窗自己也记几何：`window.ini` 的 `[control_window]`，防抖 400ms 写盘
- 最小尺寸定成 560×300，`onScreenChanged` 里再兜一次，防止换屏后内容被裁

## 3. 为什么第一版不理想

**① 点「切无线」之后界面直接报错**

```
视频出错：视频连接断开：The remote host closed the connection
```

而且 IP 也没问出来，等于无线没切成。

**② 只问一次 IP**

第一版 `adb tcpip` 之后直接 `adb shell ip route`，大概率拿到空字符串 —— adbd 正在重启。

**③ 控制窗位置每次都在另一块屏幕**

只给投屏窗记了几何，控制窗完全靠 Qt 默认摆放（默认会挑一块屏居中，所以每次都"飘"过去）。

## 4. 怎么定位的

- ①日志里能看到 `adb tcpip` 成功，但紧接着视频线程报 `remote host closed`。这是必然的：**`adb tcpip` 会重启设备上的 adbd**，USB 那条连接立刻被对端关闭。第一版没有先断开，所以看起来像"切无线把投屏搞崩了"
- ②看时间线：`tcpip` 返回后立刻 `shell ip route`，输出是空的；过两秒再看就有内容了 —— 典型的"服务还没起来"
- ③对比 `window.ini`：只有 `[video_window]`，没有控制窗的组

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 报错 + 切不成 | 切之前先 `Disconnect()`，把会话/解码器/读线程收干净，再切；这样界面只会显示"正在切无线调试 …" |
| ② 问不到 IP | 每 500ms 问一次 `ip route`，最多 8 次；解析 `src <ip>` 那个 token |
| ③ 位置不记 | 控制窗加 `Component.onCompleted` 恢复 + 防抖保存；第一次没有记录时立刻存一次当前位置 |
| 额外 | `adb connect` 失败时退出码也可能是 0，必须看输出里有没有 `failed` |

## 6. 最终效果与收获

`window.ini` 现在记全了：

```ini
[video_window]
x=393
y=69
w=405
h=911

[control_window]
x=929
y=333
w=560
h=340

[input]
wheel_mode=drag
drag_pixels=29

[device]
last_serial=e77121ed
```

- 收获：**涉及 adb 设备状态的操作要先把自家会话收干净**，否则"对端断开"会和"我们主动做的操作"混在一起，看日志会误判
- 收获：**异步生效的系统操作（adbd 重启）必须轮询等状态**，不能假设"命令返回 0 就绪了"
- 收获：**`adb connect` 这类命令的退出码不可信**，要看输出文本

## P6 追记：切无线卡死 + 抓错 IP

用户点了「切无线」，窗口直接"未响应"，状态栏停在
`adb connect 10.33.61.144:5555 失败，检查电脑和设备是否同一个 wifi`。

两个独立问题：

**① 卡死**：`EnableWifi()` 里全是阻塞 adb 调用加 `QThread::msleep`，而且都跑在 GUI 线程上。最坏路径：

```
adb tcpip ≤10s + 轮询 8×(500ms + ≤5s) + connect 重试 3×≤8s  ≈ 40 秒以上
```

窗口当然"未响应"。改成：主线程只做「断开当前会话 + 置忙标志」，其余丢给 `QThread::create`，算完 `invokeMethod(Queued)` 回主线程刷状态。

**② IP 抓错**：`ip route` 的输出是这样的

```
10.33.61.128/27 dev rmnet_data3 proto kernel scope link src 10.33.61.144   ← 移动网络
192.168.31.0/24  dev wlan0      proto kernel scope link src 192.168.31.114 ← wifi
```

第一版取"第一个 src"，正好抓到移动网络的 `10.33.61.144`；电脑和手机不在一个网段，`adb connect` 必然失败。改成只认含 `wlan` 的行，路由表没有时再查 `ip -f inet addr show wlan0`。

手工验证过整条链路：

```
$ adb -s e77121ed tcpip 5555
restarting in TCP mode port: 5555
$ adb shell ip route | grep wlan
192.168.31.0/24 dev wlan0 proto kernel scope link src 192.168.31.114
$ adb connect 192.168.31.114:5555
connected to 192.168.31.114:5555
$ adb devices
e77121ed              device
192.168.31.114:5555   device
```

- 收获：**"第一个匹配"永远是个坑**，设备上可能有多个网络接口，必须按名字过滤
- 收获：**界面上任何超过 200ms 的同步操作都会变成"未响应"**，adb 这类外部进程调用一律丢工作线程

## P6 再追记：从"认接口名"改成"认同网段"

用户提了一句很关键的话：**"应该抓和当前主机 IP 同前三位的那个地址，这样更靠谱"**。

他是对的。第二版"只认 wlan0"能跑，但那是**猜接口名**；手机换网络（热点 / VPN / 双 wifi）时名字就不作数了。而"和本机同 /24"直接对应"能不能连通"这个本质。

于是抽出 `libs/adb/net_address.*`（纯字符串处理，可单测）：

| 函数 | 作用 |
|---|---|
| `SameLan24(a, b)` | 前三位一样就算同一个 /24 |
| `RouteAddresses(output)` | 从 `ip route` 里抠出所有 src，可能同时有移动网络和 wifi |
| `AddrInet(output)` | 从 `ip -f inet addr show wlan0` 里抠 inet |
| `OrderByLocalLan(candidates, local)` | 同网段的排前面，其余保持原顺序 |

控制器侧：

```cpp
const QStringList ordered = qsc::adb::OrderByLocalLan(candidates, HostLanAddresses());
for (const QString &address : ordered) { ... adb connect ... 成功就返回 ... }
```

`HostLanAddresses()` 用 `QNetworkInterface::allAddresses()` 拿本机非回环 IPv4。

新增 4 条单测（`tst_net_address`），ctest 从 8 项变 9 项。失败时状态栏会列出试过哪些地址，不再只有一句"连不上"。

- 收获：**判断"能不能连"要用网络拓扑，不要用设备内部命名**；接口名是设备视角，网段才是连通性视角
- 收获：**候选不唯一时不要赌一个**，按可信度排序逐个试，成本只是一次 adb 往返

# P7 · 横竖屏卡死、符号键、主窗按钮、扫描式设备列表

## 1. 这一阶段要做什么

用户实测反馈四条：全屏视频（横屏）卡住、`Shift + ?` 这类组合符号打不出来、工具栏「主窗」按钮拉不回主界面、主界面操作不顺手。外加字号太小、设备列表要"扫到就能选"。

## 2. 怎么做的

- 纹理按平面尺寸重建（横竖屏切换时尺寸变了）
- 投屏窗检测宽高比翻转，按新比例调窗口
- 键盘补齐带 Shift 的符号键，映射回基础键
- 「主窗」按钮补 `show()` / `showNormal()`
- 设备列表合并 `adb devices` 和 `adb mdns services`，带 `USB` / `无线` 前缀，**选中即连**
- 标题栏和工具栏字号提到 13~14px 并加粗

## 3. 为什么第一版不理想

**① 播放横屏视频直接卡住，返回竖屏又好了**

**② `Shift + /`（问号）打不出来**

**③ 点「主窗」没反应**

**④ 选设备要两次操作**

## 4. 怎么定位的

- ①"横屏卡、竖屏好"这个现象指向尺寸：帧从 1264×2776 变成 2776×1264，而 `render()` 里建纹理只判断 `textures_[i] == 0`，旧尺寸纹理被新尺寸数据覆盖 → `glTexSubImage2D` 越界。返回竖屏时尺寸又和旧纹理匹配，所以看起来"返回就好了"
- ②查 Qt 的 key 取值：`Shift + /` 给的是 `Qt::Key_Question`，`Shift + 1` 给 `Key_Exclam`，而键码表里只有 `Key_Slash` / `Key_1`，符号键全落进 `default: return 0` 被跳过。顺便发现 Qt 里没有 `Key_Quotedbl`（是 `Key_QuoteDbl`），编译直接报错
- ③主窗可能被最小化，`raise()` 单独用不会把最小化窗口恢复
- ④设备列表已经有了，只是选中只填输入框，还要再点一次连接

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 横屏卡住 | 每张纹理记住自己的尺寸，变了删掉重建；窗口在宽高比翻转时按新比例调整 |
| ② 符号键 | 补 20 个符号键映射（`! @ # … ? ~`），Shift 交给 metaState |
| ③ 主窗按钮 | `show() → showNormal() → raise() → requestActivate()` |
| ④ 两步变一步 | 下拉框 `onActivated` 直接 `Connect(devices[index])` |

## 6. 最终效果与收获

- 启动自动连上了无线那台：`[app] 自动连接上次的设备 "192.168.31.114:5555"`
- 设备下拉框里有 `USB   e77121ed` 和 `无线  192.168.31.114:5555`，选一个直接连
- `ctest 9/9`
- 收获：**"有时坏有时好"的 bug 先量尺寸**——横竖屏都能复现、换回竖屏就正常，几乎一定是尺寸/长度假设错了
- 收获：**输入映射不能只映射"主键"**，Shift 后的符号是另一套 key 值

# P8 · 横竖屏分开记尺寸 + 主窗按钮 + 一行操作

## 1. 这一阶段要做什么

三件事：横屏和竖屏要各自记住窗口大小（看电影和刷手机要的形状不一样）；工具栏「主窗」按钮还是拉不回窗口；主窗操作区压成一行，别占两行卡片。

## 2. 怎么做的

- `window.ini` 里按姿势存两套：`[video_window]`（竖屏）和 `[video_window_landscape]`（横屏）
- 帧尺寸变化时判断 `width > height`：姿势变了就先存旧的、再取新的（没有记录就按帧比例算一套）
- 「主窗」按钮改成走 `DeviceController::ShowControlWindow()`（C++ 里 `show → showNormal → raise → requestActivate`）
- 主窗只留一行：输入框 + `▾` 菜单 + 刷新 / 连接 / 断开；切无线移进 `▾` 菜单

## 3. 为什么第一版不理想

**① 横屏拉伸、切回竖屏变成一根细条**

之前只有一套几何：竖屏 414×938，横屏时还用它 → 画面缩在中间一条；用户拉宽之后切回竖屏，又变成细条。

**② 「主窗」按钮仍然没反应**

QML 里直接 `control.raise() + requestActivate()`。Windows 有前台锁，而且窗口最小化时 `raise()` 不会恢复显示。

**③ 两行卡片太占地方**

输入区和设备下拉各占一大块，窗口被撑到 340 高，实际只用得上一行。

## 4. 怎么定位的

- ①现象很明确：同一套尺寸在两种姿势下都不合适。检查 `window.ini` 只有 `[video_window]` 一个键，确认是设计缺失
- ②先在有焦点的窗口上试 `raise()`——能到前面；最小化之后再试——没反应。说明缺 `showNormal()`。同时 QML 里的窗口对象操作不如 C++ 稳，索性整体挪到控制器
- ③量了一下内容：一行 58px + 标题 24 + 状态 20 + 边距，190 就够，之前是 340

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 两套几何 | 按 `frameSize.width > frameSize.height` 分 `video_window` / `video_window_landscape`；切换时先存旧的再取新的 |
| ② 主窗按钮 | 控制器存 `QWindow*`，`ShowControlWindow()` 里 `show + showNormal + raise + requestActivate`，并打日志确认是否激活 |
| ③ 一行操作 | 设备下拉改成 `▾` 弹出菜单，选中即连；「用 USB 设备开无线调试」作为菜单最后一项 |
| 顺手 | 自动算出来的尺寸也主动落盘一次（`saveTimer.restart()`），否则下次启动又得重算 |

## 6. 最终效果与收获

干净启动后 `window.ini`：

```ini
[control_window]
x=797
y=369
w=600
h=250

[video_pos]
x=247
y=121

[video_window]
x=247
y=121
w=414
h=938
```

- 收获：**`raise()` 不等于"把窗口叫回来"**，最小化的窗口必须先 `showNormal()`
- 收获：**用户"改了没生效"先确认进程是新起的**——这一轮又被 exe 占用（`LNK1168`）坑了一次，构建失败但旧进程还在跑，看起来像修复无效
- 收获：**窗口行为放 C++ 更可控**，QML 的 `Window` 只能做有限的窗口管理

# P10 · 三扇窗的关系 + 状态归位

## 1. 这一阶段要做什么

三条反馈：提示词不该出现在主窗；点投屏窗的最小化，工具栏不跟着走；**主窗最小化却把投屏窗一起带走了**（用户明确不想要）；另外"投屏窗的一切状态都该在它自己标题栏，主窗只留连接状态"。

## 2. 怎么做的

- 两个附属窗口都写 `transientParent: null`，断开和主窗的从属关系
- 工具栏监听投屏窗的 `visibility`：投屏窗最小化 → `toolWindow.showMinimized()`；还原 → `showNormal()`
- 投屏窗标题栏文字改成复合内容：有 `hint` 显示 hint，否则 `设备名 + fps + 分辨率`
- 主窗删掉帧率、分辨率、提示行，只留"连接状态"一行

## 3. 为什么第一版不理想

**① 主窗最小化，投屏窗跟着消失**

**② 投屏窗最小化，工具栏还杵在那儿**

**③ 状态信息散在主窗**

## 4. 怎么定位的

- ①这不是"绑定写错了"，而是 QML 的默认行为：**窗口声明在另一个窗口内部时，会自动成为它的 transient 子窗**，Win32 层面就像对话框之于父窗口，父窗口最小化自然带走子窗口。查 `Window` 的 `transientParent` 属性确认了这一点
- ②工具栏的 `visible` 只绑了 `target.visible`，而**最小化不改 `visible`**，改的是 `visibility`（`Minimized`）。绑定时机选错了属性
- ③纯粹是信息摆放问题

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 主窗带走投屏窗 | `VideoWindow` 和 `ToolBarWindow` 都设 `transientParent: null` |
| ② 工具栏不跟随 | `Connections` 监听 `target.visibility`，最小化/还原时同步自己 |
| ③ 状态散落 | 帧率、分辨率、提示词全部搬到投屏窗标题栏，主窗只留连接状态 |

标题栏文字：

```qml
text: {
    if (deviceController.hint.length > 0) {
        return deviceController.hint          // 悬停提示优先
    }
    let text = 设备名
    if (fps > 0)  text += "   fps"
    if (frameSize 有效) text += "   宽x高"
    return text                                // 默认：设备名 + 状态
}
```

## 6. 最终效果与收获

```
控制窗                     投屏窗标题栏                工具栏
┌──────────────┐          ┌──────────────────────┐   ┌────┐
│ QmlScrcpy    │          │ e77121ed  60 fps     │   │返回 │
│ [串号][▾][…] │          │ 1264x2776            │   │任务 │
│ ● 已连接 …   │          └──────────────────────┘   │ …  │
└──────────────┘
   最小化不影响投屏窗        最小化 → 工具栏跟着走
```

- 收获：**QML 里"声明在 Window 内"不等于"属于它"，但会继承 `transientParent`**，窗口间从属关系要显式断开
- 收获：**`visible` 和 `visibility` 是两回事**——最小化改的是后者，做窗口联动必须监听 `visibility`

# P11 · 合并成两扇窗

## 1. 这一阶段要做什么

用户问：为什么要三个窗口，不能一个窗口里拼两块钱（画面 + 工具栏）？——能，而且更好。这阶段把工具栏从独立窗口搬进投屏窗，最终只剩两扇窗：**控制窗** + **投屏窗（内含工具栏）**。

## 2. 怎么做的

- `VideoWindow.qml` 里搞成 `ColumnLayout { 标题栏; RowLayout { VideoSurface; 工具栏列 } }`
- 删掉 `ToolBarWindow.qml` 整个文件，`qml.qrc` 同步去掉
- 删掉 `MainWindow.qml` 里的工具栏实例化，以及 `SetControlWindow`
- 删掉控制器里的 `SetControlWindow` / `ShowControlWindow` / `SetHint` / `Hint` / `hint_` / `control_window_`
- 悬停提示从"跨窗口传给控制器"变成 `VideoWindow` 自己的 `hint` 属性
- 尺寸算法补上工具栏宽度：`wantWidth = 帧宽/DPR + 64`

## 3. 为什么第一版三个窗口

第一版工具栏想嵌在画面里，做完发现窗口宽是按帧比例算的，插进 64px 之后画面区域比例变了（要么变形要么黑边）。当时图省事，把工具栏拆成独立窗口、用绑定贴上去。

## 4. 三个窗口带来的问题（这几天逐个踩的）

```
位置跟随    x = target.x + target.width，投屏窗一动就要跟着算
贴紧缝隙    曾经多写 6px 间距，看起来有条缝
最小化同步  两个 HWND，visible 管不了最小化，要监听 visibility 手动同步
owner 关系  transientParent 继承 → 主窗最小化把投屏窗和工具栏一起藏掉
```

最后一个最坑：`transientParent: null` 写在属性里没用，因为 `componentComplete()` 会把它设回父窗口，必须在 `Component.onCompleted` 里再清一次。

## 5. 怎么解决的

```
┌──────────────────────────┐   ┌────────────────────────┬──────┐
│ 控制窗（主）              │   │ 标题栏（设备名/fps/提示） │ 工具栏│
│ [串号] [▾] [刷新][连接][断开]│   ├────────────────────────┼──────┤
│ ● 已连接 …                │   │       VideoSurface      │ 按钮列│
└──────────────────────────┘   └────────────────────────┴──────┘
     关闭 = 退出进程                 关闭 = 只关画面
```

合并之后，位置、最小化、owner 这三个问题**从"要手写代码补偿"变成"不存在"**——布局由 `RowLayout` 保证。

代价：全屏时工具栏列要收起（`visible: visibility !== Window.FullScreen`）。

## 6. 效果与收获

- 可见窗口从 3 个降到 2 个
- 删掉三处补丁：`transientParent = null`（工具栏那份）、`followX/followY/height` 绑定、最小化 `Connections`
- 控制器少了 4 个方法、2 个成员
- 收获：**能用布局表达的关系，不要用多窗口 + 绑定去模拟**。跨窗口每加一条同步逻辑，就多一处只在特定操作顺序下才暴露的 bug
- 收获：**"拆开图省事"往往是最贵的省事**——第一版避开的是 30 行的尺寸计算，付出的是后面几天反复修窗口联动

# P11 追记：合并之后的三个布局缺陷

合并成两扇窗之后，用户实测又报三条，都是布局结构用错导致的，跟逻辑无关。

**① 缩放把手跑到左下角**

把手原本是窗口的兄弟节点，靠 `anchors.right: toolBar.visible ? toolBar.left : parent.right` 定位。问题：`toolBar.left` 依赖 RowLayout 算完之后才有值，**布局未完成时它是 0**，于是把手被摆到窗口最左边。

根子在于"跨容器反推坐标"。改成把画面和把手装进同一个 `Item`，把手贴这个 Item 的右下角：

```qml
Item {                                   // 视频区
    Layout.fillWidth: true
    Layout.fillHeight: true
    VideoSurface { anchors.fill: parent }
    Rectangle { anchors.right: parent.right; anchors.bottom: parent.bottom }
}
```

**② 拖侧边栏不能移动窗口**

这轮合并时，拖动区只加在标题栏上；老版本工具栏是独立窗口，自带一整块背景拖动区，合并时漏掉了。补一个铺满工具栏列的 `toolBarDragArea`，放在按钮 `Column` 之前——按钮的 MouseArea 声明在后面，会先吃掉点击，只有按钮之间的空地能拖。

**③ 提示词被标题栏省略号截断**

提示文字挪进标题栏后，标题栏只有视频区那么宽，长句直接被 `elide` 切掉。改成独立的提示条：整窗宽、盖在标题栏上层（`z: 10`），底色深蓝，悬停才出现。标题栏回归单纯显示 `设备名 + fps + 分辨率`。

- 收获：**子元素坐标只在同一个坐标系里算**。跨容器用 `A.left` 反推位置，在布局还没跑完时拿到的是 0，会闪一下甚至一直错
- 收获：合并窗口时**要盘点旧窗口自带的行为**（这里就是工具栏空白可拖），否则功能会静默消失
