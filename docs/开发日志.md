# P0 · CMake 骨架 + QML 空窗口

## 1. 这一阶段要做什么

建一个能干活的骨架：CMake 能配置、能编译、能跑出一个空 QML 窗口，把编译选项、部署、测试三件事先搭好。不写任何业务逻辑。

## 2. 怎么做的

- CMakePresets 而不是命令行参数（任何 shell 都能配，不用开发者命令行）
- 编译选项做成 `INTERFACE` 目标 `qs_options`，所有目标继承（`/W4 /permissive- /utf-8`）
- 部署走一个 `cmake -P` 脚本，而不是 `add_custom_command` 里直接调 windeployqt

## 3. 为什么第一版不理想

**① 部署命令把 shell 搞崩了**

```
pwsh.exe 不是内部或外部命令，也不是可运行的程序
```

原因：`add_custom_command` 里把 `$ENV{PATH}` 拼进命令行，Windows 的 PATH 里全是分号，被 CMake 当成命令分隔符拆开了。

**② 部署完 QML 加载失败**

现象：程序起来了，但是白窗口，日志里 `qrc:/qml/MainWindow.qml: module "QtQuick" is not installed`。

**③ 本机 PATH 里第一个 Qt 是 5.14.2**

`windeployqt` 用的是 5.14 的那个，部署出来的东西和 5.15.2 编出来的二进制对不上，QML 模块直接找不到。

## 4. 怎么定位的

- ①②都是"命令行被拆开"，先怀疑引号/转义，改成 `cmake -P` 脚本后消失——脚本里 `set(ENV{PATH} ...)` 不经过 shell
- ③是 `where windeployqt` 打出来的路径不是 5.15.2，确认是 PATH 顺序问题

## 5. 怎么解决的

```cmake
# cmake/DeployQt.cmake：先把 Qt 的 bin 塞到 PATH 最前面，再跑 windeployqt
set(ENV{PATH} "${QS_QT_ROOT}/bin;$ENV{PATH}")
execute_process(COMMAND windeployqt --qmldir ... )
# 部署完强制自检，没 QML 模块就直接 FATAL_ERROR，不要静默产出坏包
file(GLOB qml_modules "${deploy_dir}/QtQuick*/qmldir" ...)
```

## 6. 最终效果与收获

- `cmake --preset windows-debug` + 构建 + `ctest` 三条命令可用
- 收获：**CMake 的自定义命令不要碰 PATH 这种带分号的变量**；部署脚本必须自检，宁可在构建期报错

# P1 · 协议层

## 1. 这一阶段要做什么

把 scrcpy 的线路格式实现成纯逻辑库：12 字节视频包头、12 种控制消息、3 种设备消息。要求脱离设备和网络就能单测。

## 2. 怎么做的

- 三个头文件一个 cpp：`wire.h`（大端读写）、`video_packet.*`、`control_message.*`、`device_message.*`
- 设备消息解析用三态返回：正数=消费字节数，0=数据不够，-1=流坏了。这样调用方可以直接塞进循环里处理半包
- 只依赖 QtCore，不依赖网络/界面

## 3. 为什么第一版不理想

**① 测试编译不过，报"宏参数个数不对"**

```cpp
QCOMPARE(AdbArgs::Devices(), QStringList{QStringLiteral("devices")});
```

`QCOMPARE` 是宏，`QStringList{a, b}` 里的逗号被当成宏参数分隔符了。

**② 换文件后突然一堆"缺少函数标题 / 未声明的标识符"**

现象：同一个头文件，加了几行中文注释之后编译报错，报的位置还莫名其妙。

## 4. 怎么定位的

- ①一看就明白是宏展开，不用猜
- ②先怀疑是声明写错，逐行注释掉对照；最后发现**报错的行号对应的是注释里的中文**——是编码问题

## 5. 怎么解决的

- ①写了个 `Argv({...})` 辅助函数，把初始化列表先收进一个变量再比较
- ②给 `qs_options` 加 `/utf-8`，并且让它对 `qs_ffmpeg` 也生效（不然那个目标读中文注释还是按 GBK）

## 6. 最终效果与收获

- 23 条单测全绿
- 收获：**MSVC 默认按本地代码页读源文件，中文注释不带 `/utf-8` 会把后面一行吃掉**

# P2a · adb 命令层

## 1. 这一阶段要做什么

把 adb 命令拼装和进程执行封成库：设备列表、push、reverse/forward、shell。仍然不碰业务。

## 2. 怎么做的

- `AdbArgs` 静态方法，每个方法返回 `QStringList`（不拼字符串，路径带空格也不会被拆开）
- `AdbResult` 带 stdout/stderr/退出码，`ErrorText()` 优先给 stderr
- `adb.exe` 不入库，运行时按 ``{程序目录}\Tools\adb.exe` → PATH 找

## 3. 为什么第一版不理想

真机连上之后，server 起来了但立刻退出，日志只有一句：

```
[server] ERROR: Could not connect to local socket
```

## 4. 怎么定位的

先怀疑 server 参数错（对照 scrcpy 文档逐项核），没问题；再怀疑端口没监听，`adb reverse --list` 一看——隧道建了，但方向反了。

## 5. 怎么解决的

`adb reverse` 的两个参数顺序写反了。正确是**设备侧在前**：

```
adb reverse localabstract:scrcpy_xxxxxxxx  tcp:27183
              ↑ 设备侧监听的名字            ↑ 本机端口
```

`forward` 反过来：本机端口在前，设备侧名字在后。改成两个显式的方法各自拼，不做"通用隧道"抽象。

## 6. 最终效果与收获

- 14 条单测（含真机 `adb version`）
- 收获：**reverse 和 forward 的参数顺序是相反语义，抽象成一个函数必然出错**

# P2b · 连接状态机

## 1. 这一阶段要做什么

一条完整的建链流程：推 server → 建隧道 → 起进程 → 拿视频/控制两个 socket → 读设备信息。

## 2. 怎么做的

`ServerSession::Start()` 同步阻塞执行（约 1.4 秒），内部拆成 `PushServer` / `SetUpTunnel` / `StartServerProcess` / `ConnectSockets` / `ReadInfo` 五个小函数，每个出错都带原因。

## 3. 为什么第一版不理想

**① reverse 模式只收到一个连接**

视频 socket 连上了，控制 socket 一直等到超时。

**② 改成"先接控制"之后，视频又卡住**

**③ forward 模式 server 起不来**

日志停在 server 输出的第一行，之后没有任何数据。

**④ 把 session 挪到子线程后直接崩**

```
ASSERT failure in QCoreApplication::sendEvent: "Cannot send events to objects owned by a different thread.
Current thread 0x..., receiver 'QTcpServer' (of type 'QTcpServer') was created in thread 0x..."
```

## 4. 怎么定位的

- ①埋点发现 accept 只成功一次 → 查 adb 文档：**adb 的转发会把同一条隧道的连接串行化**，第二条要等第一条的数据流先动起来
- ②于是试"先读设备信息，再 accept 控制" → 成功。设备信息是从**视频 socket** 上发过来的，先把它读掉，第一条连接才算"处理完"
- ③forward 模式对比 reverse：server 在两条连接都建好之前只发 1 个 dummy 字节。所以必须**先把两条连接都建起来，再去读**
- ④栈很明确：`QTcpServer` 在子线程创建、主线程调 `Stop()` 触发事件投递

## 5. 怎么解决的

```
reverse：accept 视频 → 立刻读设备信息 → 再 accept 控制
forward：连视频 + 连控制 → 再读设备信息
```

④没有硬修，改成**连接全程在主线程同步执行**（1.4 秒卡顿），换来对象生命周期简单。真要修就整体搬到一个专门的连接线程，而不是只搬一部分。

## 6. 最终效果与收获

- 真机建链成功：`[session] 连接完成："RMX5010" QSize(1264, 2776) reverse 耗时 1500 ms`
- 收获：**阻塞式握手 + 框架对象 = 线程归属问题**；顺带记住"adb 转发会串行化连接"这个反直觉行为

# P3 · 视频链路（最折腾的一段）

## 1. 这一阶段要做什么

从视频 socket 读字节 → 解 H.264 → 变成屏幕上的画面。目标 60fps、低延迟。

## 2. 怎么做的（最终形态）

```
视频线程：waitForReadyRead → 切帧 → 解码 → emit FrameReady（直连）
渲染线程：synchronize 取帧 + 拷三平面 → render 上传 3 张纹理 + 着色器 → FBO
Qt：把 FBO 当纹理合成到窗口 → DWM → 屏幕
```

期间试过四种渲染方案、崩了五次，下面按顺序讲。

## 3. 为什么第一版不理想（按发生顺序）

**① sws_scale 直接写进 QImage 缓冲 → 堆损坏**

```
0xC0000374: 堆已损坏
```

现象：偶尔崩，崩在完全无关的地方（有时是块析构）。

**② 自定义材质 + 每帧换纹理 → 崩在 bind()**

```
Invalid texture accessed: 0x0
Aborting: scene graph is invalid
```

**③ 材质持有 AVFrame 跨帧 → 断开连接时 use-after-free**

```
YuvMaterial::Sync() 行 206
std::shared_ptr<void const>::~shared_ptr
std::_Ref_count_base::_Decref
```

**④ 在 updatePaintNode 里调 GL → 绿屏 + 退出崩**

**⑤ 继承 QSGTexture 自己上传 → 崩在虚调用**

```
YuvShader::updateState 行 213
texture->bind()
```

**⑥ FBO 方案跑通后：画面上下颠倒、标题栏糊成一团**

**⑦ 拖窗口卡 5 秒**

**⑧ 缩放窗口卡几秒**

**⑨ 画质很糊**

## 4. 怎么定位的（逐个说）

**①** 先怀疑解码器线程不安全，单线程跑还是一样；后来注意到只有窗口尺寸不是 32 的倍数时才崩——`QImage` 每行是紧凑的，没有 FFmpeg 需要的对齐填充，`sws_scale` 按 stride 写就越界。改成 `av_image_alloc` 分配目标帧、再逐行 memcpy 回 QImage。

**②** 栈指向 `bind()`，说明对象被删了。谁删的？我每帧 `delete` 旧纹理，但**渲染器缓存着材质指针**，它下一次用时就是野指针。

**③** 栈很直白：`pending_ = Frame()` 触发的析构里崩。对着代码推演发现：材质把帧持有到"下一帧渲染时"才放，而这期间用户点了断开 → 解码器销毁 → 帧的缓冲区跟着没 → 再释放就是访问已释放内存。

**④** `updatePaintNode` 是同步阶段，不是渲染阶段，GL 上下文状态不保证。绿屏说明上传根本没生效。

**⑤** `QSGTexture` 的生死不归我们管，Qt 的渲染器缓存着它。这条路（自己实现 `bind()`）理论上是对的，但配合 Qt5 的材质缓存就是不稳定。

**⑥** 两个独立的错：FBO 的 y 轴朝上，我按"v=0 在顶部"映射 → 整幅翻过来；另外我用完 1、2 号纹理单元没切回 0 号，Qt 接着画自己的文字时还停在 2 号单元，采样到我的平面纹理 → 文字糊成一条。

**⑦** 一开始以为是解码慢，上了埋点：

```
[perf] fps 61 等数据 15.5ms 解码 0.44ms 转换 0.33ms 上屏 0.02ms
```

每帧处理只有 0.8ms，60fps 稳态——**根本不是算不动**。真正的现象是：拖窗口时 fps 从 61 掉到 15。

继续查：从视频线程 `update()` 会往 GUI 线程投事件，而拖窗口时 GUI 线程卡在 Windows 的系统模态循环里，这一投就把视频线程堵住了。改成"视频线程只存帧，GUI 线程用 8ms 定时器来取"之后，fps 回到 61。

**⑧** 缩放时窗口卡住不动，测出来是 `QSettings::sync()` 在每个 `onWidthChanged` 里都落盘，一秒上百次写文件。

**⑨** 不是抗锯齿问题：720p 的 328×720 被拉到 545 宽显示，是**物理放大**。

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 堆损坏 | `av_image_alloc` 分配目标帧 + 逐行 memcpy |
| ②③④⑤ 四次崩溃 | 全部放弃，改用 `QQuickFramebufferObject`：`render()` 是 Qt 保证"渲染线程 + 上下文当前"的唯一入口 |
| ③ 帧寿命 | 渲染器只拷像素（5.2 MB / 1ms），不持有 AVFrame；断开时先 `Clear()` 再关解码器 |
| ⑥ 上下颠倒 | 顶点 v 轴反向（顶部用 v=1） |
| ⑥ 标题栏糊 | `render()` 结束前还原 GL 状态（纹理单元回 0、像素对齐回 4） |
| ⑦ 拖拽卡 | 视频线程不投递任何跨线程事件；重绘由 GUI 线程定时器发起 |
| ⑧ 缩放卡 | 位置尺寸改成停手 400ms 后防抖写盘 |
| ⑨ 画质糊 | 采集改原生分辨率（`max_size=0`），窗口按帧的物理像素定大小 |

## 6. 最终效果与收获

```
fps 61   等数据 6.5ms   解码 5.6ms   转换 0ms   上屏 0.4ms
```

- CPU 只剩 H.264 解码；RGB 转换在 GPU 上
- 拖动窗口画面不冻、不积帧；缩放不再卡
- 收获：
  - **Qt5 场景图里 GL 的合法时机只有 `render()`**，`updatePaintNode` 不是
  - **跨线程投递事件要小心**：GUI 线程可能被系统模态循环扣住
  - **先埋点再优化**：我一开始认定是解码慢，数据和结论完全相反

# P3.5 · 窗口与交互

## 1. 这一阶段要做什么

把"控制 + 画面挤在一个窗口"拆成两扇窗，加上缩放、记忆、无边框拖动。

## 2. 怎么做的

- 控制窗（序列号 + 连接/断开 + 状态/帧率）和投屏窗分离
- 投屏窗无边框、自绘 28px 标题栏（拖动 + 最小化 + 关闭），左上右下各一个缩放把手
- 窗口位置写 `userdata.ini`，位置随时记、尺寸只在用户手动改过时记

## 3. 为什么第一版不理想

**① 系统标题栏拖动 → 画面冻住**

**② 缩放时窗口不跟手，卡 5 秒**

**③ 窗口被系统压成 650×2403**

**④ 勾选框文字看不见**

**⑤ `Cannot assign to non-existent property "palette"`**

## 4. 怎么定位的

- ①前面 P3 已经查明：系统拖拽进模态循环，GUI 线程被扣。**换无边框 + 自己处理鼠标移动**就绕开了（事件循环一直在转）
- ②P3 里是 `QSettings::sync()` 每次事件写盘；这次又叠了一个：`updatePaintNode` 在没有新帧时直接返回，画面矩形不更新，所以窗口变大画面不变。两个都修
- ③按帧的物理像素定窗口，但原生 1264×2776 比屏幕还高，只夹了宽度 → 高度被系统硬压
- ④`Window` 上设 `palette` 报错——palette 是 Control 的属性，Window 没有。改成给每个控件单独配色 + 勾选框不带文字
- ⑤同上，一眼看日志就知道

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 拖动冻画面 | 无边框 + 自绘标题栏 + 自己算鼠标位移（按屏幕绝对坐标取差值） |
| ② 缩放卡 | 写盘防抖 400ms；没有新帧时也重算画面矩形 |
| ③ 被压 | 宽高都按屏幕可用区域（85%）收缩 |
| ④⑤ 看不见/报错 | 控件单独配色，勾选框用无字 CheckBox + 独立 Label |

## 6. 最终效果与收获

- 投屏窗 328×748（720 画面 + 28 标题栏），拖动顺畅、两个角都能缩放、位置尺寸会记住
- 收获：**Qt Quick 里"能拖动的窗口"必须绕开系统拖拽**；**写盘这类副作用永远要防抖**

# P4a · 输入层：坐标与触摸

## 1. 这一阶段要做什么

把画布坐标换算成视频帧坐标，并拼出触摸/滚轮控制消息。纯逻辑，脱离设备可单测。

## 2. 怎么做的

- `CoordinateMapper`：两种模式（拉满 / 等比居中）
- `TouchController`：按下/移动/抬起/滚轮 → `protocol::ControlMessage`
- 5 条单测逐字段断言 32 字节触摸消息

## 3. 为什么第一版不理想

单测直接失败：

```
Actual   (near_right)     : QPoint(60,100)
Expected (QPoint(90, 100)): QPoint(90,100)
```

## 4. 怎么定位的

对着数字推：画布 200×200，帧 100×200，等比缩放应该缩到 1 倍（一个帧像素 = 一个画布像素），画面居中后左右各 50px 黑边。点 (120,100) 应该在帧坐标 (70,100)。

实际算出 60，说明**偏移没生效**。再看代码：`scale_x = frame_w / item_w` 是"画布→帧"的比例，我却把它当"帧→画布"去算可见宽度（`frame_w / scale_x`）——方向用反了。

## 5. 怎么解决的

```cpp
// 改前：把两个方向混着用
const qreal scale_x = frame_size_.width() / item_size_.width();
offset_x = (item_size_.width() - frame_size_.width() / scale) / 2.0;

// 改后：统一用"一个帧像素占几个画布像素"
const qreal fit_x = item_size_.width() / frame_size_.width();
offset_x = (item_size_.width() - frame_size_.width() * fit_x) / 2.0;
帧坐标 = local_x / fit_x;
```

## 6. 最终效果与收获

- 5 条单测全绿，`ctest 7/7`
- 收获：**这类几何换算一定要用单测钉死**，纯靠眼看代码发现不了方向错

# P4b · 输入层：键盘

## 1. 这一阶段要做什么

Qt 按键 → 安卓键码，处理自动重复次数和修饰键 metaState。

## 2. 怎么做的

- `keycode_table.*`：字母/数字/F1~F12 用连续区间，其余逐个映射；未映射返回 0
- `key_controller.*`：自己数重复次数（`QHash<int,int>`），抬起清零
- 7 条单测

## 3. 为什么第一版不理想

**① 测试进程直接崩**

```
QFATAL : KeyTest::AutoRepeatCounts() ASSERT: "uint(i) < uint(size())"
in file .../qbytearray.h, line 500
```

**② 修完崩溃后发现长度断言失败**

```
Actual   (first.size()): 14
Expected (21)          : 21
```

## 4. 怎么定位的

- ①先是以为 `Press()` 返回了空数组，加了 `QCOMPARE(first.size(), 21)` 才看清：其实是 14 字节，我按 21 去读偏移 13，越界。**崩溃不是"二次求值"，是长度算错**——我最初的猜测（QCOMPARE 展开两次）是错的，用 size 断言排除了它
- ②读数：`control_message.cpp` 里 `InjectKeycode` 是 `type(1) + action(1) + keycode(4) + repeat(4) + meta(4)`，一共 **14** 字节。我按"5 字节头 + 4 字节 action"算成了 21

顺带发现 `MakeHeader` 上面的注释写着"拼 12 字节控制消息头"，实际只有 1 字节类型头——**注释是错的**，一起改了。

## 5. 怎么解决的

- 测试里的长度和偏移全部按 14 字节改（action 在 1、keycode 在 2、repeat 在 6、meta 在 10）
- 修掉那句错误注释，避免下一个人（包括我）再被误导

## 6. 最终效果与收获

- 7 条键盘单测全绿，`ctest 8/8`
- 收获：
  - **不要凭印象写协议的字节偏移**，去读实现，或者直接断言 size
  - 崩溃时先确认"对象多长"，再怀疑宏/求值顺序

# P4c · 接线：把输入接到控制 socket

## 1. 这一阶段要做什么

**③ 启动后日志里出现两次"开始连接"，一次 wifi 序列号一次 usb 序列号**

## 4. 怎么定位的

- ①看名字就明白了：`SendMessage` 是 `<windows.h>` 里的宏（`SendMessageA/W`），我的私有方法名被宏替换掉了。改成 `EmitControlMessage`

- ③先怀疑代码里有两处自动连接，grep 只找到 `main.cpp` 一处；再加两行临时探针打印"谁在调 Connect"，结果只有 main 一次。**最后发现是用户中途手动点了"连接"按钮**——输入框里是 `proposedSerial`（usb 序列号），于是第二次连接用另一个序列号。不是 bug，探针撤掉

## 6. 最终效果与收获

# P4d · 日志与配置

## 1. 这一阶段要做什么

输入接了线但点了没反应，没有任何线索可查。先建日志模块和配置文件，不然只能靠猜。

## 2. 怎么做的

- `libs/base/log.*`：`QLoggingCategory` 分类 + `qInstallMessageHandler` 落文件
- 按天一个文件 `Log/LOG_yyyy_MM_dd.log`，启动时删掉超过 15 天的
- `config.ini` 存用户设置（日志级别、采集参数），`window.ini` 存窗口位置尺寸
- 输入链路埋四个观测点（事件进来 / 消息拼出 / 写 socket / socket 不可用）

## 3. 为什么第一版不理想

**① `config.ini` 里的中文注释被写成乱码**

```
# 视频采集：长边上限...
```
变成了

```
%23%20%E8%A7%86%E9%A2%91%E9%87%87%E9%9B%86...
```

**② 链接 qsc_session 的测试全都报未解析符号**

```
LNK2019: 无法解析的外部符号 qsc::base::lcInput(void)
```

**③ `QDir::remove` 编译不过**

```
error C2662: "bool QDir::remove(const QString &)": 不能将 "this" 指针从 "const QDir" 转换
```

## 4. 怎么定位的

- ①现象很明确：所有 `#` 开头的行都被百分号转义了。查 QSettings 行为：**它写回文件时会重新生成整个 INI，注释按 key 转义**，所以只要程序写过一次配置，注释必然被破坏
- ②测试目标只链了 `qsc_session`，而 `qsc_session` 现在用了日志分类；分类符号在 `qsc_base` 里
- ③编译器说得很清楚，`remove()` 不是 const 成员

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 注释被破坏 | **拆成两个文件**：`config.ini` 我们只读、绝不写；程序状态放 `window.ini`。这样用户可以放心写注释 |
| ② 未解析符号 | `qsc_session` / `qsc_stream` 都 PUBLIC 链接 `qsc_base`，依赖方自动继承 |
| ③ const 对象 | `const QDir dir(...)` 改成 `QDir dir(...)` |

## 6. 最终效果与收获

```
config.ini    注释完好，用户改完重启生效
window.ini    只有 x/y/w/h，没有注释
Log/LOG_2026_11_12.log    当天日志，超 15 天自动清
```

- 收获：
  - **`QSettings` 不是配置文件的编辑器**，它只适合"程序自己的状态"；给用户看的配置要自己控制写入
  - 库之间加依赖时，`PUBLIC` 会把传递依赖带出去，别忘了目标本身也要能解析

## P4c 追记：真凶是那行没加上的 connect

上面第三节说"点下去没反应"，那时还没有日志。日志建好之后第一次抓就抓到了：

# P5 · 控制窗重做 + 标题显示设备 + 启动自动连接

## 1. 这一阶段要做什么

四件事：控制窗太难看、换屏幕之后按钮变成白条、标题栏应该显示连的是哪台设备、启动时希望能自动连上次的设备（只连一次）。

## 2. 怎么做的

- 控制窗全部改成自绘控件（`ActionButton` = `Rectangle` + `Text` + `MouseArea`），输入框只覆盖 `background`
- 布局改成"标题行 + 两张圆角卡片"：串号卡片、状态卡片，状态前面一个绿/灰小圆点
- 投屏窗标题绑 `deviceController.deviceName`

**① 换到另一块屏幕后，按钮变成一排白条**

第一版直接用了 `Button` / `TextField` 的默认样式。深色窗口上默认样式是浅色底，而且换到不同缩放比例的屏幕时，背景按新 DPI 重算、尺寸约束没跟上，就截成了半截白条。

**② 标题是写死的 "QmlScrcpy — 投屏"**

**③ 工具栏没有回到控制窗的入口**

投屏窗和工具栏都是独立窗口，控制窗被别的窗口盖住之后只能去任务栏找。

**④ 每次启动都要手点「连接」**

调试时还好，日常用太烦。

## 4. 怎么定位的

- ②③④ 都是功能缺失，不需要定位

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 白条 | 控件全自绘：按钮用 `Rectangle`，输入框只覆盖 `background`，颜色写死 |
| ② 标题 | `VideoWindow.title` 绑 `deviceController.deviceName`，连上设成串号、断开清空 |
| ③ 回主窗 | 工具栏加「主窗」按钮，`control.requestActivate()` + `control.raise()` |
| ④ 自动连 | `PickStartupSerial()`：候选串号必须在 `adb devices` 的在线列表里，否则不连 |

# P6 · 设备列表 + 一键切无线 + 控制窗位置

## 1. 这一阶段要做什么

三件事：主窗里要能看见在线设备并选一台；不插线也能切到 wifi 调试；控制窗每次启动都跑到另一块屏幕上，位置要记住。

## 2. 怎么做的

- `RefreshDevices()` 除了填 `proposedSerial`，还把在线列表存进 `devices_`，通过 `Q_PROPERTY(QStringList devices)` 给 QML 的 `ComboBox` 当 model
- 新增「切无线」：`adb tcpip 5555` → 轮询 `ip route` 问 IP → `adb connect ip:5555`（失败重试 3 次）
- 控制窗自己也记几何：`window.ini` 的 `[control_window]`，防抖 400ms 写盘
- 最小尺寸定成 560×300，`onScreenChanged` 里再兜一次，防止换屏后内容被裁

## 3. 为什么第一版不理想

**① 点「切无线」之后界面直接报错**

```
视频出错：视频连接断开：The remote host closed the connection
```

而且 IP 也没问出来，等于无线没切成。

**② 只问一次 IP**

第一版 `adb tcpip` 之后直接 `adb shell ip route`，大概率拿到空字符串 —— adbd 正在重启。

**③ 控制窗位置每次都在另一块屏幕**

只给投屏窗记了几何，控制窗完全靠 Qt 默认摆放（默认会挑一块屏居中，所以每次都"飘"过去）。

## 4. 怎么定位的

- ①日志里能看到 `adb tcpip` 成功，但紧接着视频线程报 `remote host closed`。这是必然的：**`adb tcpip` 会重启设备上的 adbd**，USB 那条连接立刻被对端关闭。第一版没有先断开，所以看起来像"切无线把投屏搞崩了"
- ②看时间线：`tcpip` 返回后立刻 `shell ip route`，输出是空的；过两秒再看就有内容了 —— 典型的"服务还没起来"
- ③对比 `window.ini`：只有 `[video_window]`，没有控制窗的组

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 报错 + 切不成 | 切之前先 `Disconnect()`，把会话/解码器/读线程收干净，再切；这样界面只会显示"正在切无线调试 …" |
| ② 问不到 IP | 每 500ms 问一次 `ip route`，最多 8 次；解析 `src <ip>` 那个 token |
| ③ 位置不记 | 控制窗加 `Component.onCompleted` 恢复 + 防抖保存；第一次没有记录时立刻存一次当前位置 |
| 额外 | `adb connect` 失败时退出码也可能是 0，必须看输出里有没有 `failed` |

## 6. 最终效果与收获

`window.ini` 现在记全了：

```ini
[video_window]
x=393
y=69
w=405
h=911

[control_window]
x=929
y=333
w=560
h=340

[input]
wheel_mode=drag
drag_pixels=29

[device]
last_serial=e77121ed
```

- 收获：**涉及 adb 设备状态的操作要先把自家会话收干净**，否则"对端断开"会和"我们主动做的操作"混在一起，看日志会误判
- 收获：**异步生效的系统操作（adbd 重启）必须轮询等状态**，不能假设"命令返回 0 就绪了"
- 收获：**`adb connect` 这类命令的退出码不可信**，要看输出文本

## P6 追记：切无线卡死 + 抓错 IP

用户点了「切无线」，窗口直接"未响应"，状态栏停在
`adb connect 10.33.61.144:5555 失败，检查电脑和设备是否同一个 wifi`。

两个独立问题：

**① 卡死**：`EnableWifi()` 里全是阻塞 adb 调用加 `QThread::msleep`，而且都跑在 GUI 线程上。最坏路径：

```
adb tcpip ≤10s + 轮询 8×(500ms + ≤5s) + connect 重试 3×≤8s  ≈ 40 秒以上
```

窗口当然"未响应"。改成：主线程只做「断开当前会话 + 置忙标志」，其余丢给 `QThread::create`，算完 `invokeMethod(Queued)` 回主线程刷状态。

**② IP 抓错**：`ip route` 的输出是这样的

```
10.33.61.128/27 dev rmnet_data3 proto kernel scope link src 10.33.61.144   ← 移动网络
192.168.31.0/24  dev wlan0      proto kernel scope link src 192.168.31.114 ← wifi
```

第一版取"第一个 src"，正好抓到移动网络的 `10.33.61.144`；电脑和手机不在一个网段，`adb connect` 必然失败。改成只认含 `wlan` 的行，路由表没有时再查 `ip -f inet addr show wlan0`。

手工验证过整条链路：

```
$ adb -s e77121ed tcpip 5555
restarting in TCP mode port: 5555
$ adb shell ip route | grep wlan
192.168.31.0/24 dev wlan0 proto kernel scope link src 192.168.31.114
$ adb connect 192.168.31.114:5555
connected to 192.168.31.114:5555
$ adb devices
e77121ed              device
192.168.31.114:5555   device
```

- 收获：**"第一个匹配"永远是个坑**，设备上可能有多个网络接口，必须按名字过滤
- 收获：**界面上任何超过 200ms 的同步操作都会变成"未响应"**，adb 这类外部进程调用一律丢工作线程

## P6 再追记：从"认接口名"改成"认同网段"

用户提了一句很关键的话：**"应该抓和当前主机 IP 同前三位的那个地址，这样更靠谱"**。

他是对的。第二版"只认 wlan0"能跑，但那是**猜接口名**；手机换网络（热点 / VPN / 双 wifi）时名字就不作数了。而"和本机同 /24"直接对应"能不能连通"这个本质。

于是抽出 `libs/adb/net_address.*`（纯字符串处理，可单测）：

| 函数 | 作用 |
|---|---|
| `SameLan24(a, b)` | 前三位一样就算同一个 /24 |
| `RouteAddresses(output)` | 从 `ip route` 里抠出所有 src，可能同时有移动网络和 wifi |
| `AddrInet(output)` | 从 `ip -f inet addr show wlan0` 里抠 inet |
| `OrderByLocalLan(candidates, local)` | 同网段的排前面，其余保持原顺序 |

控制器侧：

```cpp
const QStringList ordered = qsc::adb::OrderByLocalLan(candidates, HostLanAddresses());
for (const QString &address : ordered) { ... adb connect ... 成功就返回 ... }
```

`HostLanAddresses()` 用 `QNetworkInterface::allAddresses()` 拿本机非回环 IPv4。

新增 4 条单测（`tst_net_address`），ctest 从 8 项变 9 项。失败时状态栏会列出试过哪些地址，不再只有一句"连不上"。

- 收获：**判断"能不能连"要用网络拓扑，不要用设备内部命名**；接口名是设备视角，网段才是连通性视角
- 收获：**候选不唯一时不要赌一个**，按可信度排序逐个试，成本只是一次 adb 往返

# P7 · 横竖屏卡死、符号键、主窗按钮、扫描式设备列表

## 1. 这一阶段要做什么

用户实测反馈四条：全屏视频（横屏）卡住、`Shift + ?` 这类组合符号打不出来、工具栏「主窗」按钮拉不回主界面、主界面操作不顺手。外加字号太小、设备列表要"扫到就能选"。

## 2. 怎么做的

- 纹理按平面尺寸重建（横竖屏切换时尺寸变了）
- 投屏窗检测宽高比翻转，按新比例调窗口
- 键盘补齐带 Shift 的符号键，映射回基础键
- 「主窗」按钮补 `show()` / `showNormal()`
- 设备列表合并 `adb devices` 和 `adb mdns services`，带 `USB` / `无线` 前缀，**选中即连**
- 标题栏和工具栏字号提到 13~14px 并加粗

## 3. 为什么第一版不理想

**① 播放横屏视频直接卡住，返回竖屏又好了**

**② `Shift + /`（问号）打不出来**

**③ 点「主窗」没反应**

**④ 选设备要两次操作**

## 4. 怎么定位的

- ①"横屏卡、竖屏好"这个现象指向尺寸：帧从 1264×2776 变成 2776×1264，而 `render()` 里建纹理只判断 `textures_[i] == 0`，旧尺寸纹理被新尺寸数据覆盖 → `glTexSubImage2D` 越界。返回竖屏时尺寸又和旧纹理匹配，所以看起来"返回就好了"
- ②查 Qt 的 key 取值：`Shift + /` 给的是 `Qt::Key_Question`，`Shift + 1` 给 `Key_Exclam`，而键码表里只有 `Key_Slash` / `Key_1`，符号键全落进 `default: return 0` 被跳过。顺便发现 Qt 里没有 `Key_Quotedbl`（是 `Key_QuoteDbl`），编译直接报错
- ③主窗可能被最小化，`raise()` 单独用不会把最小化窗口恢复
- ④设备列表已经有了，只是选中只填输入框，还要再点一次连接

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 横屏卡住 | 每张纹理记住自己的尺寸，变了删掉重建；窗口在宽高比翻转时按新比例调整 |
| ② 符号键 | 补 20 个符号键映射（`! @ # … ? ~`），Shift 交给 metaState |
| ③ 主窗按钮 | `show() → showNormal() → raise() → requestActivate()` |
| ④ 两步变一步 | 下拉框 `onActivated` 直接 `Connect(devices[index])` |

## 6. 最终效果与收获

- 启动自动连上了无线那台：`[app] 自动连接上次的设备 "192.168.31.114:5555"`
- 设备下拉框里有 `USB   e77121ed` 和 `无线  192.168.31.114:5555`，选一个直接连
- `ctest 9/9`
- 收获：**"有时坏有时好"的 bug 先量尺寸**——横竖屏都能复现、换回竖屏就正常，几乎一定是尺寸/长度假设错了
- 收获：**输入映射不能只映射"主键"**，Shift 后的符号是另一套 key 值

# P8 · 横竖屏分开记尺寸 + 主窗按钮 + 一行操作

## 1. 这一阶段要做什么

三件事：横屏和竖屏要各自记住窗口大小（看电影和刷手机要的形状不一样）；工具栏「主窗」按钮还是拉不回窗口；主窗操作区压成一行，别占两行卡片。

## 2. 怎么做的

- `window.ini` 里按姿势存两套：`[video_window]`（竖屏）和 `[video_window_landscape]`（横屏）
- 帧尺寸变化时判断 `width > height`：姿势变了就先存旧的、再取新的（没有记录就按帧比例算一套）
- 「主窗」按钮改成走 `DeviceController::ShowControlWindow()`（C++ 里 `show → showNormal → raise → requestActivate`）
- 主窗只留一行：输入框 + `▾` 菜单 + 刷新 / 连接 / 断开；切无线移进 `▾` 菜单

## 3. 为什么第一版不理想

**① 横屏拉伸、切回竖屏变成一根细条**

之前只有一套几何：竖屏 414×938，横屏时还用它 → 画面缩在中间一条；用户拉宽之后切回竖屏，又变成细条。

**② 「主窗」按钮仍然没反应**

QML 里直接 `control.raise() + requestActivate()`。Windows 有前台锁，而且窗口最小化时 `raise()` 不会恢复显示。

**③ 两行卡片太占地方**

输入区和设备下拉各占一大块，窗口被撑到 340 高，实际只用得上一行。

## 4. 怎么定位的

- ①现象很明确：同一套尺寸在两种姿势下都不合适。检查 `window.ini` 只有 `[video_window]` 一个键，确认是设计缺失
- ②先在有焦点的窗口上试 `raise()`——能到前面；最小化之后再试——没反应。说明缺 `showNormal()`。同时 QML 里的窗口对象操作不如 C++ 稳，索性整体挪到控制器
- ③量了一下内容：一行 58px + 标题 24 + 状态 20 + 边距，190 就够，之前是 340

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 两套几何 | 按 `frameSize.width > frameSize.height` 分 `video_window` / `video_window_landscape`；切换时先存旧的再取新的 |
| ② 主窗按钮 | 控制器存 `QWindow*`，`ShowControlWindow()` 里 `show + showNormal + raise + requestActivate`，并打日志确认是否激活 |
| ③ 一行操作 | 设备下拉改成 `▾` 弹出菜单，选中即连；「用 USB 设备开无线调试」作为菜单最后一项 |
| 顺手 | 自动算出来的尺寸也主动落盘一次（`saveTimer.restart()`），否则下次启动又得重算 |

## 6. 最终效果与收获

干净启动后 `window.ini`：

```ini
[control_window]
x=797
y=369
w=600
h=250

[video_pos]
x=247
y=121

[video_window]
x=247
y=121
w=414
h=938
```

- 收获：**`raise()` 不等于"把窗口叫回来"**，最小化的窗口必须先 `showNormal()`
- 收获：**用户"改了没生效"先确认进程是新起的**——这一轮又被 exe 占用（`LNK1168`）坑了一次，构建失败但旧进程还在跑，看起来像修复无效
- 收获：**窗口行为放 C++ 更可控**，QML 的 `Window` 只能做有限的窗口管理

# P10 · 三扇窗的关系 + 状态归位

## 1. 这一阶段要做什么

三条反馈：提示词不该出现在主窗；点投屏窗的最小化，工具栏不跟着走；**主窗最小化却把投屏窗一起带走了**（用户明确不想要）；另外"投屏窗的一切状态都该在它自己标题栏，主窗只留连接状态"。

## 2. 怎么做的

- 两个附属窗口都写 `transientParent: null`，断开和主窗的从属关系
- 工具栏监听投屏窗的 `visibility`：投屏窗最小化 → `toolWindow.showMinimized()`；还原 → `showNormal()`
- 投屏窗标题栏文字改成复合内容：有 `hint` 显示 hint，否则 `设备名 + fps + 分辨率`
- 主窗删掉帧率、分辨率、提示行，只留"连接状态"一行

## 3. 为什么第一版不理想

**① 主窗最小化，投屏窗跟着消失**

**② 投屏窗最小化，工具栏还杵在那儿**

**③ 状态信息散在主窗**

## 4. 怎么定位的

- ①这不是"绑定写错了"，而是 QML 的默认行为：**窗口声明在另一个窗口内部时，会自动成为它的 transient 子窗**，Win32 层面就像对话框之于父窗口，父窗口最小化自然带走子窗口。查 `Window` 的 `transientParent` 属性确认了这一点
- ②工具栏的 `visible` 只绑了 `target.visible`，而**最小化不改 `visible`**，改的是 `visibility`（`Minimized`）。绑定时机选错了属性
- ③纯粹是信息摆放问题

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 主窗带走投屏窗 | `VideoWindow` 和 `ToolBarWindow` 都设 `transientParent: null` |
| ② 工具栏不跟随 | `Connections` 监听 `target.visibility`，最小化/还原时同步自己 |
| ③ 状态散落 | 帧率、分辨率、提示词全部搬到投屏窗标题栏，主窗只留连接状态 |

标题栏文字：

```qml
text: {
    if (deviceController.hint.length > 0) {
        return deviceController.hint          // 悬停提示优先
    }
    let text = 设备名
    if (fps > 0)  text += "   fps"
    if (frameSize 有效) text += "   宽x高"
    return text                                // 默认：设备名 + 状态
}
```

## 6. 最终效果与收获

```
控制窗                     投屏窗标题栏                工具栏
┌──────────────┐          ┌──────────────────────┐   ┌────┐
│ QmlScrcpy    │          │ e77121ed  60 fps     │   │返回 │
│ [串号][▾][…] │          │ 1264x2776            │   │任务 │
│ ● 已连接 …   │          └──────────────────────┘   │ …  │
└──────────────┘
   最小化不影响投屏窗        最小化 → 工具栏跟着走
```

- 收获：**QML 里"声明在 Window 内"不等于"属于它"，但会继承 `transientParent`**，窗口间从属关系要显式断开
- 收获：**`visible` 和 `visibility` 是两回事**——最小化改的是后者，做窗口联动必须监听 `visibility`

# P11 · 合并成两扇窗

## 1. 这一阶段要做什么

用户问：为什么要三个窗口，不能一个窗口里拼两块钱（画面 + 工具栏）？——能，而且更好。这阶段把工具栏从独立窗口搬进投屏窗，最终只剩两扇窗：**控制窗** + **投屏窗（内含工具栏）**。

## 2. 怎么做的

- `VideoWindow.qml` 里搞成 `ColumnLayout { 标题栏; RowLayout { VideoSurface; 工具栏列 } }`
- 删掉 `ToolBarWindow.qml` 整个文件，`qml.qrc` 同步去掉
- 删掉 `MainWindow.qml` 里的工具栏实例化，以及 `SetControlWindow`
- 删掉控制器里的 `SetControlWindow` / `ShowControlWindow` / `SetHint` / `Hint` / `hint_` / `control_window_`
- 悬停提示从"跨窗口传给控制器"变成 `VideoWindow` 自己的 `hint` 属性
- 尺寸算法补上工具栏宽度：`wantWidth = 帧宽/DPR + 64`

## 3. 为什么第一版三个窗口

第一版工具栏想嵌在画面里，做完发现窗口宽是按帧比例算的，插进 64px 之后画面区域比例变了（要么变形要么黑边）。当时图省事，把工具栏拆成独立窗口、用绑定贴上去。

## 4. 三个窗口带来的问题（这几天逐个踩的）

```
位置跟随    x = target.x + target.width，投屏窗一动就要跟着算
贴紧缝隙    曾经多写 6px 间距，看起来有条缝
最小化同步  两个 HWND，visible 管不了最小化，要监听 visibility 手动同步
owner 关系  transientParent 继承 → 主窗最小化把投屏窗和工具栏一起藏掉
```

最后一个最坑：`transientParent: null` 写在属性里没用，因为 `componentComplete()` 会把它设回父窗口，必须在 `Component.onCompleted` 里再清一次。

## 5. 怎么解决的

```
┌──────────────────────────┐   ┌────────────────────────┬──────┐
│ 控制窗（主）              │   │ 标题栏（设备名/fps/提示） │ 工具栏│
│ [串号] [▾] [刷新][连接][断开]│   ├────────────────────────┼──────┤
│ ● 已连接 …                │   │       VideoSurface      │ 按钮列│
└──────────────────────────┘   └────────────────────────┴──────┘
     关闭 = 退出进程                 关闭 = 只关画面
```

合并之后，位置、最小化、owner 这三个问题**从"要手写代码补偿"变成"不存在"**——布局由 `RowLayout` 保证。

代价：全屏时工具栏列要收起（`visible: visibility !== Window.FullScreen`）。

## 6. 效果与收获

- 可见窗口从 3 个降到 2 个
- 删掉三处补丁：`transientParent = null`（工具栏那份）、`followX/followY/height` 绑定、最小化 `Connections`
- 控制器少了 4 个方法、2 个成员
- 收获：**能用布局表达的关系，不要用多窗口 + 绑定去模拟**。跨窗口每加一条同步逻辑，就多一处只在特定操作顺序下才暴露的 bug
- 收获：**"拆开图省事"往往是最贵的省事**——第一版避开的是 30 行的尺寸计算，付出的是后面几天反复修窗口联动

# P11 追记：合并之后的三个布局缺陷

合并成两扇窗之后，用户实测又报三条，都是布局结构用错导致的，跟逻辑无关。

**① 缩放把手跑到左下角**

把手原本是窗口的兄弟节点，靠 `anchors.right: toolBar.visible ? toolBar.left : parent.right` 定位。问题：`toolBar.left` 依赖 RowLayout 算完之后才有值，**布局未完成时它是 0**，于是把手被摆到窗口最左边。

根子在于"跨容器反推坐标"。改成把画面和把手装进同一个 `Item`，把手贴这个 Item 的右下角：

```qml
Item {                                   // 视频区
    Layout.fillWidth: true
    Layout.fillHeight: true
    VideoSurface { anchors.fill: parent }
    Rectangle { anchors.right: parent.right; anchors.bottom: parent.bottom }
}
```

**② 拖侧边栏不能移动窗口**

这轮合并时，拖动区只加在标题栏上；老版本工具栏是独立窗口，自带一整块背景拖动区，合并时漏掉了。补一个铺满工具栏列的 `toolBarDragArea`，放在按钮 `Column` 之前——按钮的 MouseArea 声明在后面，会先吃掉点击，只有按钮之间的空地能拖。

**③ 提示词被标题栏省略号截断**

提示文字挪进标题栏后，标题栏只有视频区那么宽，长句直接被 `elide` 切掉。改成独立的提示条：整窗宽、盖在标题栏上层（`z: 10`），底色深蓝，悬停才出现。标题栏回归单纯显示 `设备名 + fps + 分辨率`。

- 收获：**子元素坐标只在同一个坐标系里算**。跨容器用 `A.left` 反推位置，在布局还没跑完时拿到的是 0，会闪一下甚至一直错
- 收获：合并窗口时**要盘点旧窗口自带的行为**（这里就是工具栏空白可拖），否则功能会静默消失

# P12 · 命令行窗口开关

## 1. 这一阶段要做什么

调试时想看日志，发布时又不想让用户看见黑窗口。做成运行时可切换，并把选择记进配置，下次启动照上次来。

## 2. 怎么做的

- 先确认 exe 子系统：`QS_HIDE_CONSOLE=OFF` → PE 头 `Subsystem=3`（Console），一启动就有控制台
- `libs/base/console_window.*`：`ConsoleWindowAvailable()` + `SetConsoleWindowVisible(bool)`
- `AppSettings` 加 `[ui] show_console`，默认 `true`
- `DeviceController::SetShowConsole(bool)`：切窗口 + 写盘 + 发信号 + 更新状态文字
- `main.cpp` 启动时读一次配置并应用
- 主窗右上角加「命令行」按钮（选中时蓝底）

## 3. 为什么不是"按需创建控制台"

两个方向：

| 做法 | 适用 | 问题 |
|---|---|---|
| 隐藏已有控制台 | `QS_HIDE_CONSOLE=OFF`（当前） | 只需 `ShowWindow`，一行搞定 |
| 按需 `AllocConsole()` | `QS_HIDE_CONSOLE=ON`（GUI 子系统） | 还要 `freopen("CONOUT$")` 把 stdout/stderr 重绑，否则 `qInfo` 不进新窗口 |

当前构建就是控制台子系统，所以走第一条。发布版换成 GUI 子系统后，按钮会变成空操作——这点写进了文档，免得以后误以为是 bug。

## 4. 为什么不用 FreeConsole

`FreeConsole()` 会把这个进程和控制台彻底断开，之后 `std::cout` / `printf` 全部失败；想再显示得 `AllocConsole()` 重建，还得把标准流重定向到 `CONOUT$`。我们只是"不想看见它"，`ShowWindow(SW_HIDE)` 就够，日志照写。

## 5. 怎么解决的

```
主窗「命令行」按钮
   │
   ▼
DeviceController::SetShowConsole(bool)
   ├── qsc::base::SetConsoleWindowVisible()   立刻生效
   ├── AppSettings::SetShowConsole()          写 window.ini 的 [ui] show_console
   ├── emit ShowConsoleChanged()              按钮高亮跟着变
   └── SetStatus("命令行窗口已显示 / 已隐藏")
```

启动时：

```cpp
qsc::base::SetConsoleWindowVisible(app_settings.ShowConsole());
```

## 6. 效果与收获

- 点一下就显示/隐藏控制台，状态记在 `window.ini`，下次启动保持
- 收获：**先查 PE 子系统和实际行为，再决定实现路径**——`AllocConsole` 和 `ShowWindow` 是两套完全不同的代码量
- 收获：**`FreeConsole` 是有副作用的**（标准流断掉），"隐藏"和"断开"要分清

## P12 追记：光标反馈

用户提了一句"所有按钮都要手型，只有悬停有点 low"。补全之后按语义分了三类：

| 区域 | 光标 |
|---|---|
| 按钮（主窗四个 + 设备菜单项 + 工具栏十个 + 标题栏最小化/关闭） | `PointingHandCursor` |
| 标题栏空白、工具栏按钮间空地 | `SizeAllCursor`（四向，暗示能拖窗口） |
| 右下/左上缩放把手 | `SizeFDiagCursor`（斜向，暗示能改尺寸） |

- 收获：**光标是零成本的可用性信号**，一行 `cursorShape` 就能区分"能点"和"能拖"

# P13 · 给帧链路埋点 + 配置目录

## 1. 这一阶段要做什么

用户报了两件事：无线模式下切换界面有明显延迟（有线很丝滑），fps 会从 30 多突然跳到 120。要回答"到底是传输慢还是渲染只肯一帧一帧走"，先把链路量化——不许猜。顺带把散在 exe 根目录的 ini 收进 `config/`。

## 2. 怎么做的

- `PerfStats` 扩成完整计数器：收帧、字节、关键帧、推、丢、渲、带新帧的渲、积压（现在/平均/最大）
- 读线程记字节数和关键帧；用包头的 µs PTS 算"相对第一帧的积压"
- 渲染线程 `synchronize` 里数渲染次数和"拿到新帧的次数"
- `Present` 里发现有待渲染帧就记一次丢弃（以前这个信息完全丢了）
- 默认每秒打一行 `[perf]`，`QS_PERF=0` 才关
- `config.ini` / `window.ini` 移到 `config/`，启动时自动迁移旧文件

## 3. 为什么原来看不出来

**① fps 显示的是"到达速率"，不是渲染速率**

```cpp
const int arrived = frames_arrived_.loadAcquire();
if (arrived != frames_painted_) { frames_painted_ = arrived; update(); }
```

`frames_painted_ = arrived` 只是记下"看到过多少次到达"，**根本没有数画了几帧**。所以界面上那个 120 可能是解码输出速率，也可能是一次重连把计数弄乱了。

**② `UpdateFps` 用了函数内 static**

```cpp
static int last_arrived = 0;      // 所有实例共享，重连后计数器归零会算出负数
```

**③ 丢帧没有统计**

`Present` 直接覆盖旧帧，丢了多少没人知道。

## 4. 现在一眼能看出什么

```
[perf] 收 58 帧 704KB/s 关键帧 2 | 推 57 丢 36 | 渲 96（带新帧 57）| 积压 现在 18.4ms 平均 16.2ms 最大 84.1ms | 等数据 4.0ms 解码 5.6ms 转换 0.0ms 上屏 0.4ms
```

判断规则：

```
收 ≈ 30、KB/s 顶到码率上限、积压持续上涨   → 传输带宽不够
收 60、丢很多、渲 125（带新帧 60）           → 渲染被 8ms 定时器限流，多余帧被丢
收 60、丢 0、积压平稳但界面仍慢              → 延迟出在设备编码 / adb 传输，不在我们这侧
```

**积压为什么用相对值**：设备的 PTS 是它自己的单调钟，和本机不同源；第一帧记下 `offset = now - pts`，之后算 `now - pts - offset`，只看增长趋势。

## 5. 顺手修的

| 问题 | 修法 |
|---|---|
| `static last_arrived` 跨实例共享 | 改成成员 `fps_last_arrived_`，`Clear()` 里归零 |
| 丢帧无统计 | `Present` 里检查 `has_pending_`，被覆盖就 `dropped++` |
| ini 散在根目录 | 新增 `ConfigDirPath()` / `FilepathInConfigDir()` / `MigrateLegacyIni()` |
| perf 只在 `QS_PERF=1` 时打 | 默认开，`QS_PERF=0` 关 |

## 6. 收获

- **"帧率"必须有明确口径**：到达、解码、渲染是三个不同的数，混成一个数字就永远查不出问题
- **丢帧是性能问题最重要的证据**，把"覆盖旧帧"当成天经地义，等于主动扔掉唯一的线索
- 迁移旧配置要"根目录有、新位置没有才搬"，否则会把用户新改的配置覆盖掉

## P13 追记：两组实测数据推翻了原来的猜测

用户跑了有线 / 无线各一组日志，结论和"无线传输慢"这个直觉相反：

| 指标 | 有线 | 无线 |
|---|---|---|
| 入队到上屏 平均 | 3.3~4.6ms | 3.6~4.5ms |
| 入队到上屏 最大 | 6~7ms | 6~8ms |
| 解码 | 3.7~6.6ms | 3.7~7.0ms |
| 等数据（活跃） | 4.7~20ms | 7.1~21ms |
| 收帧 | 39~120 | 39~120 |

两条链路几乎没有差别，所以"渲染只肯一帧一帧走"和"无线传输慢"都不是主因。真正对不上的是这个：

```
配置 bit_rate=8000000（8Mbps）
实测 1983KB/s ≈ 16Mbps；峰值 3288KB/s ≈ 26Mbps
```

参数名没错（`video_bit_rate=8000000` 确实传下去了），是 Android 屏幕编码器不吃这个上限——高动态画面它会自己超发。26Mbps 在 WiFi 上必然排队，而有线 USB 2.0 有 480Mbps，完全无感。这才是"切窗口有延迟感"最合理的解释。

顺带三个发现：

- `收 120 帧` 不是 bug：设备是 120Hz 屏，scrcpy 默认不限帧
- `积压` 那个指标是假的：`offset` 每秒都在变（-79841481894 → -79841469020 → -79841419842），说明基准没固定住，恒为 0 毫无意义 → 删掉，换成不跨时钟域的 `入队到上屏`
- `丢 20%` 也是正常的：Qt 一个 vsync 只画一次，同一刷新周期里后到的帧本来就该覆盖先到的

## 下一步（等用户测）

把 `max_fps` 暴露到 `config.ini`（默认 0 = 不限），让用户用配置做对照实验：

```ini
[video]
bit_rate=4000000
max_fps=60
```

预期 `KB/s` 从 2000~3300 降到 500~900，无线手感接近有线。

## P13 三追：画质做成可调的

用户反馈"手感好很多，但画质略微降了"，问能不能自己调。于是把 `max_fps` 和 `bit_rate` 做成能自己填的面板：

```
┌──────────────────────────┐
│ 帧率上限（0 = 不限）       │
│ [60                  ]   │
│ 码率（Mbps，可填小数）     │
│ [8.0                 ]   │
│ 改完会自动断开重连（1~2 秒）│
│ [   应用并重连         ]  │
└──────────────────────────┘
```

三个设计决定：

| 决定 | 原因 |
|---|---|
| 界面里改的值写 `window.ini`，不写 `config.ini` | `config.ini` 是手改的、带注释的，程序写会被 `QSettings` 把注释转义 |
| `max_fps` 的覆盖值用 `-1` 当哨兵 | `0` 是合法值（不限帧），不能拿 0 表示"没调过" |
| 应用后自动断开重连 | 码率和帧率是 server 启动参数，scrcpy 的控制消息里没有"改码率"，只能重启 server |

顺带把启动时那条 `QObject::disconnect: Unexpected nullptr parameter` 过滤掉了——它是 Qt 创建 QML 窗口时对空指针的一次内部调用，没有实际影响，留在日志里只会误导排查。

- 收获：**参数类配置要分清"启动时固定"和"运行时可改"**，前者做 UI 就必须带上重连，否则用户改了没反应会以为坏了
- 收获：**`0` 当哨兵是个经典陷阱**，凡是 `0` 有语义（不限、禁用、默认）的地方，覆盖值要用 `-1`

## P13 四追：有线和无线各一套画质参数

用户实测：无线 6 Mbps 就很顺，有线 8 Mbps 拉满；帧率填 30 和填 0 看不出差别。所以把配置按连接方式拆成两档：

```ini
[video]                # 有线／兜底
bit_rate=8000000
max_fps=0

[video_wireless]       # 串号里带冒号（IP:端口）就用这组
bit_rate=6000000
max_fps=0
```

读取顺序：`window.ini` 的 `[video_wired]` / `[video_wireless]` → `config.ini` 的同名段 → `config.ini` 的 `[video]` → 内置 8 Mbps。

判档只要一行：

```cpp
QString AppSettings::VideoProfile(const QString &serial)
{
    return serial.contains(QLatin1Char(':')) ? QStringLiteral("wireless") : QStringLiteral("wired");
}
```

界面里改的只写当前那一档，所以"无线调 5M、有线保持 8M"能同时存在。

顺带清掉了老版本写在 `window.ini` `[video]` 里的单档覆盖值，否则会和新的 `[video_wired]` 混着看。

- 收获：**INI 天然支持分段**，"按连接方式 / 按设备分开配置"不用上数据库，加一个 `[video_wireless]` 就够了
- 收获：**用户实测反馈要落到默认值上**：帧率这项既然没差别，就别在文档里推荐"无线填 60"，直接写"一般不用改"

# P14 · 横竖屏位置分开 + 打包

## 1. 这一阶段要做什么

三个体验问题 + 一件工程事：横屏默认尺寸太大、横竖屏共用一套位置（退出横屏会跳到左上角）、全屏时工具栏被一起吃掉；以及用 Inno Setup 做安装包。

## 2. 怎么做的

- 横屏第一次出现时默认 `1300×600`（受屏幕 90% 限制），不再按帧比例算到接近全屏
- 位置键拆成 `video_pos`（竖屏）和 `video_pos_landscape`（横屏），切姿势时先存旧的再取新的
- 全屏不再隐藏工具栏（去掉 `visible: visibility !== Window.FullScreen`）
- 新增 `setup/`：`collect.ps1` 收发布文件、`QmlScrcpy.iss` 是 Inno Setup 脚本、`build_installer.bat` 调 ISCC

## 3. 为什么第一版不理想

**① 横屏默认尺寸太大**

原来横屏也走 `fitToFrame()`：按帧的物理像素 + 屏幕 85% 去算，1264×2776 的竖屏转成横屏后窗口接近铺满整块屏幕。

**② 横竖屏共用位置**

`video_pos` 只有一个。设备转横屏时窗口尺寸变了，Windows 按左上角为锚点重排，于是"退出横屏 → 窗口跑回左上角"。

**③ 全屏吃掉工具栏**

之前为了"全屏时别挡画面"把工具栏列设成 `visible: visibility !== Window.FullScreen`，结果用户全屏后所有按钮消失，只能先把全屏还原才能操作。

## 4. 怎么定位的

- ①对比第一次横屏的窗口和屏幕分辨率，宽高都接近 90%，明显偏大
- ②看 `window.ini`：只有一个 `[video_pos]`，横竖屏互相覆盖 → 确认是配置维度不够
- ③现象很直接：全屏后右侧一列不见了

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| ① 横屏太大 | 首次出现给固定 `1300×600`，仍受屏幕 90% 约束 |
| ② 位置串台 | `positionKey()` 按姿势返回不同键；切姿势时"存旧取新" |
| ③ 全屏吃工具栏 | 去掉隐藏绑定，全屏时工具栏保持可见 |
| ④ 打包 | `collect.ps1` 构建 Release → 清 `Log/screenshots/config/*.pdb` → 带上 `Tools\adb.exe`；`.iss` 装到 `D:\QmlScrcpy`（程序要往自己目录写配置） |

## 6. 收获

- **窗口位置这种"人的习惯"必须按场景分开存**，尺寸和位置往往都不是一套能覆盖的
- **"全屏"不是"隐藏周边"**，用户要的是画面大，不是按钮消失
- 打包细节见 [打包发布](打包发布.md)

## P14 追记：复位与出厂重置

打包前又补了两个"用户自己能把界面调回来"的入口：

| 入口 | 位置 | 做什么 |
|---|---|---|
| 复位 | 投屏窗工具栏最下面 | 删掉当前姿势的尺寸记录，立刻套默认值（横屏 900×400，竖屏按画面比例） |
| 重置 | 主窗右上角 | 清空 `window.ini`、重新生成 `config.ini`，重启后回到出厂状态 |

为什么要做成按钮：默认值改了但 `window.ini` 里已有记录时，新默认值永远看不到，用户只能手动删 ini——这条"记录优先于默认值"的规则虽然正确，但对用户不友好，得给个出口。

重置的注意点：

```cpp
window_store.clear();      // 先清再 sync，否则 QSettings 对象析构时会把旧值写回去
window_store.sync();
QFile::remove(ConfigPath());
EnsureDefaultConfig();     // 立刻补一份带注释的模板，别让用户面对一个空目录
```

顺带把安装包那条已知限制解决了：`AdbPath()` 的查找顺序里加了 `Tools\` 子目录，`setup/collect.ps1` 放进去的 adb 装完就能直接用。

- 收获：**"默认值"和"已保存的值"打架时，必须提供清空入口**，否则改默认值等于没改
- 收获：`QSettings` 的 `clear()` 之后要 `sync()`，否则析构时会把旧内容写回文件

## P14 再追：启动只亮主窗

以前启动直接两扇窗一起出来，投屏窗是一片黑，像"程序卡住了"。现在：

```qml
// VideoWindow.qml
visible: false                                    // 启动时不露脸
Connections {
    target: deviceController
    function onConnectedChanged() {
        videoWindow.visible = deviceController.connected    // 连上才出现，断开自动收起
    }
}
```

用 `Connections` 而不是把 `visible` 绑到 `connected`：用户手动关掉投屏窗时，赋值会打断绑定，正好实现"关了就别自己弹回来，下次连接再说"。

另外 QML 加载时可能已经连上了（自启动连上次设备），所以 `Component.onCompleted` 里补一句 `visible = deviceController.connected`，不依赖信号一定在之后到达。

- 收获：**"什么时候显示"也是状态机的一部分**，空窗口比不显示更让人怀疑程序坏了

## P14 终追：应用图标

打包出来"连个图标都没有"，任务管理器里也是一片空白。图标要接三个地方，漏一个就露馅：

| 位置 | 不进位的表现 |
|---|---|
| exe 资源（`app.rc`） | 文件管理器、任务管理器没图标 |
| `setWindowIcon`（运行时） | 任务栏和 Alt+Tab 是默认白纸图标 |
| `SetupIconFile`（安装包） | 安装向导还是 Inno Setup 的默认图标 |

图标本身用脚本画（`resources/make_icon.ps1`），不手搓二进制，配色和形状能在版本库里 diff。

第一次生成的两版都失败了，都跟 PowerShell/格式有关：

1. 用 PNG 压缩的 ICO —— GDI+ 的 `Icon` 类读不出来，`rc.exe` 老版本也不认
2. `return $bytes` —— PowerShell 把 `byte[]` 展开成多个输出，我拿 `$layer[1]` 只取到了**一个字节**，成品只有 125 字节

修法：图标用 32bpp DIB + AND 掩码；函数返回改成 `return ,$bytes`，层数据用 `[PSCustomObject]` 装。

- 收获：**PowerShell 函数返回数组要加逗号**（`,$arr`），否则调用方拿到的是展开后的多个对象
- 收获：**exe 图标、窗口图标、安装包图标是三处独立配置**，只改一处会"有的地方有、有的地方没有"

# P15 · 剪贴板双向同步 + 老板键

## 1. 这一阶段要做什么

两件用户明确要的事：电脑和手机之间互传文字（顺带解决中文输入——键盘只能发按键码，剪贴板能直接送 UTF-8 文本）；以及一键藏起所有窗口的"老板键"。

## 2. 怎么做的

**剪贴板**：协议层其实早就写好了（`SET_CLIPBOARD` / `GET_CLIPBOARD` / `DeviceMessage`），缺的是**读**：

```cpp
control_reader_ = session_->ControlSocket();          // 新加：不转移所有权的访问器
QObject::connect(control_reader_, &QTcpSocket::readyRead, this, &DeviceController::OnControlData);
```

`OnControlData()` 用 `DeviceMessage::TryParse` 按消费字节数切消息，0 表示半条、等下一次数据。

**老板键**：`libs/base/hotkey.*` 只负责解析 `"Ctrl+Alt+B"`（纯字符串，能单测），`src/boss_key.*` 负责 `RegisterHotKey` + `QAbstractNativeEventFilter` 截 `WM_HOTKEY`，控制器里做"藏/恢复"。

## 3. 为什么之前收不到手机剪贴板

`SendControl()` 只写不读，`server_session` 的 `control_socket_` 从来没挂过 `readyRead`。控制 socket 是**双向**的（设备会主动推剪贴板、回 Ack），我们只用了一半。

## 4. 踩的坑

**① 自动同步的回环**

写电脑剪贴板（接收手机内容）会触发 `QClipboard::dataChanged`，如果开着自动同步，就变成"手机→电脑→手机"来回推。用 `suppress_clipboard_` 标志挡住自己写的那一次。

**② 隐藏窗口用裸指针会崩**

`hidden_windows_` 存窗口指针，但 QML 会话断开时投屏窗可能被销毁。改成 `QList<QPointer<QWindow>>`，恢复前 `isNull()` 检查。

**③ 老板键必须至少带一个修饰键**

允许 `"B"` 这种单键热键等于把整个系统的 B 键抢走。`ParseHotkey` 里直接拒绝，配了单测。

**④ 程序被关之前要 UnregisterHotKey**

不注销的话这个组合会被系统认为仍被占用，下次启动注册失败。`BossKey` 析构里调，`Bind()` 开头也先 `Unbind()`。

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| 只写不读 | 给 `ServerSession` 加 `ControlSocket()`（只借不拿），挂 `readyRead` |
| 半条消息 | 缓冲区累积，`TryParse` 返回 0 就等下一次数据 |
| 回环 | `suppress_clipboard_` 标志 |
| 野指针 | `QPointer<QWindow>` |
| 断线后窗口找不回 | `TearDown()` 里先恢复被藏起来的窗口 |
| 热键配置写错 | `ParseHotkey` 严格校验 + 启动时打一行警告 |

## 6. 效果

```
[app] 老板键已注册 "Ctrl+Alt+B"
```

- 工具栏多两个按钮：`发给手机`（SET_CLIPBOARD + paste）、`取回电脑`（GET_CLIPBOARD）
- 按 `Ctrl+Alt+B` 藏窗口，再按恢复；断开连接时自动恢复
- 单测从 9 个加到 10 个（新增 `tst_hotkey`，5 个用例）

- 收获：**"只写不读"的 socket 就是半个 socket**，协议文档里写了双向，实现时容易只做一半
- 收获：**全局热键的注册/注销要成对**，否则会污染整个系统

## P15 追记：两个"看起来能用、其实没通"的 bug

### ① 「取回电脑」永远没反应

用户测出来只有「发给手机」生效。查 scrcpy 源码发现设备消息类型号是 `TYPE_CLIPBOARD = 0`、`TYPE_ACK_CLIPBOARD = 1`，我们写成了 `1 / 2 / 3`：

```cpp
// 改前
Clipboard = 1, AckClipboard = 2, UhidOutput = 3
// 改后
Clipboard = 0, AckClipboard = 1, UhidOutput = 2
```

「发给手机」是纯写入（`SET_CLIPBOARD` + `paste=1`），不走读取路径，所以看起来"一半好"。

**单测为什么没抓到**：测试里写的是 `static_cast<quint8>(DeviceMessage::Type::Clipboard)`，自己和自己比，枚举值错了照样通过。补了一条锁死线上值的用例：

```cpp
QCOMPARE(static_cast<quint8>(DeviceMessage::Type::Clipboard), quint8(0));
```

### ② 老板键只藏主窗，投屏窗闪一下又回来

两个独立问题叠在一起：

- `QGuiApplication::topLevelWindows()` 里**没有投屏窗**：它在 QML 里声明在主窗内部，`QWindow::parent()` 非空。改成登记制（`RegisterWindow` + `app_windows_`）
- 登记之后仍然"闪一下"：加 `visibilityChanged` 日志才看到 `-> 0` 紧接着 `-> 2`，即 **Qt 自己在隐藏后又 show 了一次**。解法是 `hide()` 之后 `QTimer::singleShot(0)` 再补一刀

验证手段是 Win32 枚举，不是看界面：

```
按键之前：      投屏窗 visible=True   主窗 visible=True
第一次按键后：  投屏窗 visible=False  主窗 visible=False
第二次按键后：  投屏窗 visible=True   主窗 visible=True
```

- 收获：**"自己编码、对面解码"的常量，单测必须对着协议断言**，不能对着自己的枚举断言
- 收获：**窗口隐藏后又被显示，先怀疑框架事件（激活/曝光），再怀疑自己的代码**；一行 `visibilityChanged` 日志就能定位

# P16 · 桌面/电源按键与窗口快捷键

## 1. 这一阶段要做什么

补三个高频操作：回桌面、按电源键、常用快捷键。

## 2. 怎么做的

- 两个新按钮都走现成的 `SendKeycode()`：`KEYCODE_HOME(3)`、`KEYCODE_POWER(26)`
- 快捷键用 QML 的 `Shortcut`，挂在投屏窗上：

```qml
Shortcut { sequence: "Esc";           onActivated: deviceController.SendBack() }
Shortcut { sequence: "Home";          onActivated: deviceController.SendHome() }
Shortcut { sequence: "Ctrl+Shift+S";  onActivated: deviceController.SaveScreenshot() }
Shortcut { sequence: "F11";           onActivated: 切换全屏 }
```

## 3. 为什么不用 keyPressEvent 里判断

`VideoItem::keyPressEvent` 里也能拦，但那样要自己判断修饰键、还要和输入法的事件抢。`Shortcut` 由 Qt 的快捷键表在**按键分发之前**处理：

```
按键 → QShortcutMap 先匹配 → 命中就吃掉，不进画面
                            → 不命中才交给 VideoItem 发给设备
```

所以 `Esc`/`F11` 这类不会再被当成设备按键发出去，普通字母照旧进设备。

## 4. 三个键的语义区分

这三个容易混，按钮的提示里都写清了：

| 按钮 | 键码 | 效果 |
|---|---|---|
| 息屏 / 亮屏 | `SET_DISPLAY_POWER` 消息 | 只关屏幕显示，**不锁屏**，设备仍在跑 |
| 电源 | `KEYCODE_POWER(26)` | 等于按手机电源键：锁屏或点亮 |
| 返回 | `BACK_OR_SCREEN_ON` | 返回上一级；息屏时顺便点亮 |

## 5. 剪贴板为什么保持显式按钮

有人会问"能不能 Ctrl+C 就自动发到手机"。试想了一下没有做：

- 焦点在手机画面上时，`Ctrl+C` 的语义是冲突的：复制电脑的还是手机的？
- 自动推送会把密码、聊天记录这类内容静默送到另一台设备

所以默认两个按钮，按一次做一次；想要自动的人在 `config.ini` 里开 `input/clipboard_autosync`（只做电脑→手机方向，并且接收时会抑制回环）。

## 6. 收获

- **快捷键要用框架的机制**（`Shortcut`），别自己在按键回调里手写匹配
- **名字相近的功能要在提示里写清区别**（息屏 vs 电源），否则用户一定会问

# P17 · 主窗收成一个「设置」入口 + 快捷键可改

## 1. 这一阶段要做什么

主窗头部已经塞了四个按钮（画质 / 重置 / 老板键 / 命令行），再加上快捷键映射就没地方了。要做的是：**主窗只管连接，其他都挪进设置窗**，并且让快捷键能在界面上改。

## 2. 怎么做的

- 主窗头部四个按钮合成一个「设置」
- 新增 `qml/SettingsWindow.qml`：520×560 独立小窗，三组内容（画质 / 快捷键 / 其他），`modality: Qt.ApplicationModal`
- 快捷键存 `window.ini` 的 `[keys]`（界面改的优先），回落到 `config.ini`，再回落到内置默认
- 投屏窗的 `Shortcut.sequence` 绑到控制器属性，`enabled` 判断非空——留空即禁用
- 校验用 `QKeySequence(text).isEmpty()`，写错的组合直接拒绝

## 3. 为什么是独立窗口，不是 Popup

三个方案都试过：

| 方案 | 结果 |
|---|---|
| 塞进主窗（600×250） | 五组控件挤成一行小方块，看不下去 |
| `Popup`（默认 `popupType: Item`） | 画在父母口内部，内容一多就被裁 |
| `Popup` + `Popup.Window` | 之前在 ToolTip 上用过，启动栈溢出（`Qt5Qml` 递归帧），不敢再赌 |
| **独立 `Window` + 自带标题栏** | 可控、能随便定尺寸、模态交给 `modality` |

## 4. 踩的坑

**① 内联组件里不能用类型名取实例属性**

```qml
component ShortcutRow: RowLayout {
    property string value: ""
    Text { text: ShortcutRow.value }     // ← undefined，运行时报 "Unable to assign [undefined] to QString"
}
```

改成给组件一个 `id: shortcutRow`，用 `shortcutRow.value`。

**② 删除大段 QML 后括号对不上**

用脚本按标记删掉三个旧 Popup，残留了 `}        }` 这种合并行，直接 `Syntax error`。教训：**删 QML 块之后要先看行号附近的括号**，别只看是否删干净。

**③ 快捷键不能写死在 QML 里**

第一版是 `Shortcut { sequence: "Esc" }`。要做到可配置，`sequence` 必须绑属性；但 `Shortcut` 对空串会告警，所以加 `enabled: xxx.length > 0`。

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| 主窗放不下 | 头部只留「设置」，其余进设置窗 |
| Popup 被裁 / 不稳 | 改用独立 `Window` |
| 内联组件取值 undefined | 组件内加 `id`，不用类型名 |
| 快捷键要能改 | `sequence` 绑控制器属性 + `enabled` 判空 |
| 空串语义 | 空 = 禁用，状态栏提示"已禁用该快捷键" |

## 6. 收获

- **表单类界面优先用独立窗口**，Popup 只适合短菜单
- **"可配置"要一路打通**：设置项→存储→绑定→失效处理，缺一环就会出现"改了没反应"
- 删代码块之后**先验证语法再继续**，否则后面的改动都建在坏文件上

# P18 · 文件拖拽传输

## 1. 这一阶段要做什么

把电脑上的文件传到手机：拖进投屏窗就行，不用切文件管理器、不用手动敲 adb。

## 2. 怎么做的

- `libs/adb` 加 `PushFile(serial, local, remote_dir, progress_callback, *error)`：用 `QProcess` 边跑边读 stdout，正则抓百分比
- 控制器加 `PushFiles(QVariantList urls)`：过滤出真实文件 → 丢工作线程逐个 push → 进度 `Queued` 回主线程刷状态栏
- QML 用 `DropArea` 铺满投屏窗，拖动时显示蓝色蒙层 + "松手传到手机 Download/"

## 3. 为什么不能用现成的 Run()

`qsc::adb::Run()` 是"跑完拿输出"：`waitForFinished()` 之后一次性读 `stdOut`。push 的进度是**过程中一行行输出的**，跑完再读就只剩最后一行 `1 file pushed`，进度全丢。

所以新写一个流式版本：

```cpp
while (process.state() != QProcess::NotRunning)
{
    if (process.waitForReadyRead(200))
    {
        consume(process.readAllStandardOutput());   // 按行切，抓 [ 45%]
    }
}
```

## 4. 踩的坑

**① 进度行被拆开**

`waitForReadyRead` 返回的块不保证按行边界切，`[ 4` 和 `5%]` 可能分两次到。所以要有 `pending` 缓冲，只处理到最后一个 `\n`，剩下的留到下一次。

**② 小文件没有进度行**

2 MB 以下的文件 adb 一瞬就传完，只打 `1 file pushed, 0 skipped`。所以失败/成功都要在结束时兜底补一个 100，否则进度条会停在 0。

**③ 拖进来的可能是文件夹**

`drop.urls` 里 `isFile()` 为 false 的（目录、快捷方式）直接过滤。目录要 `push -r`，这一版没做。

## 5. 怎么解决的

| 问题 | 解法 |
|---|---|
| 要进度 | 流式读 + 正则 `\[\s*(\d+)%\]` |
| 块不按行切 | `pending` 缓冲，只消费完整行 |
| 小文件无进度 | 结束时补 100 |
| 目录混进来 | `QFileInfo::isFile()` 过滤 |
| 阻塞卡界面 | 整个 push 循环丢 `QThread::create` |
| 工作线程改 UI | `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` |

## 6. 验证

adb 层单独验过（2 MB 文件，40 MB/s）：

```
$ adb -s e77121ed push test.bin /sdcard/Download/
test.bin: 1 file pushed, 0 skipped. 40.1 MB/s (2097152 bytes in 0.050s)
$ adb -s e77121ed shell ls -l /sdcard/Download/
-rw-rw---- 1 u0_a298 media_rw 2097152 ... test.bin
```

拖放本身要人工验（自动化模拟拖拽不可靠）。

- 收获：**"有进度"和"只要结果"是两种 adb 调用模式**，前者必须流式读，不能复用同步封装
- 收获：**读子进程输出的块边界不可信**，任何按行解析都要自带缓冲

# P19 · 三个体验问题的修复

## 1. 这一阶段要做什么

用户实测反馈三条：

1. 第一次切横屏时窗口很大，得手动点一次「复位」
2. 工具栏第一个按钮（返回）被顶部那条悬停提示挡住
3. 设置窗打开时，往投屏窗拖文件没反应

## 2. 怎么做的

| 问题 | 改法 |
|---|---|
| ① 横屏尺寸 | 「换姿势」分支里也判：没有横屏记录就用 900×400，不再走 `fitToFrame()` |
| ② 挡住按钮 | 工具栏内容整体下移 34px（提示条 30 + 间距 4） |
| ③ 拖放失效 | 设置窗从 `ApplicationModal` 改成 `NonModal` |
| 附加 | 工具栏包进 `Flickable`：横屏只有 400 高，16 个按钮约 580px，不滚会裁掉 |

## 3. 为什么会出现这三个问题

**① 两条分支只改了一条**

"第一帧就是横屏"和"先竖屏后来转横屏"是两个代码分支：

```qml
if (!ready) {
    // 第一帧：这里本来就有 900x400 的默认值
} else if (nowLandscape !== landscape) {
    // 换姿势：这里只有"读记录 / fitToFrame()"，漏了默认值
}
```

`fitToFrame()` 是按帧的物理像素 + 屏幕 85% 算的，1264×2776 转横屏后接近全屏。

**② 提示条横跨整窗**

标题栏的悬停提示条用 `anchors.left/right: parent.left/right` 铺满整窗（想让长文案能显示），高度 30，`z: 10`，于是压住了工具栏最上面那个按钮。

**③ 模态挡住了拖放**

`Qt.ApplicationModal` 会让**其它所有窗口**在模态期间不接收输入事件——包括拖放。设置窗只是表单，不该阻塞。

## 4. 怎么解决的

**①** 换姿势分支补一条 `else if (nowLandscape)`，用和第一帧一样的 900×400。

**②** 工具栏 `Flickable` 的 `anchors.topMargin: 34`，按钮从提示条下方开始。

**③** `modality: Qt.NonModal`，关闭靠 ✕ 或 `Esc`。

**附加** 的 `Flickable` 是顺带发现的：横屏 400 高装不下 16 个 36px 按钮，最后两个（全屏/复位）以前就点不到，只是没人注意。

## 5. 收获

- **同一件事有两条代码路径时，改一条等于没改**：横屏尺寸的默认值就是一个典型
- **`z` 高的覆盖层会连着"布局位置"一起改**，要么让位（topMargin），要么把覆盖层限宽
- **模态不是"更礼貌"，是更强的限制**：它连拖放都挡，表单类窗口能非模态就别模态

# P20 · 横屏默认值迁移 + 打开传输目录

## 1. 这一阶段要做什么

用户实测还剩两条：

1. 第一次进横屏窗口还是很大，点一次「复位」才正常
2. 传完文件要去手机上找目录，最好能一键打开

## 2. 怎么做的

- **一次性迁移**：`window.ini` 里打一个版本标记 `ui/landscape_default_v2`，没有这个标记就清掉旧的横屏尺寸/位置，清完打标记
- **打开目录**：`DeviceController::OpenUploadDir()` 先 `mkdir -p`，再用 `am start` 拉起系统文件管理器

## 3. 为什么光改代码没用

上一版已经改了两条分支（第一帧横屏 / 初竖后横），代码逻辑是对的。用户还是看到大窗口，因为：

```
window.ini
  [video_window_landscape] w=900 h=430   ← 看起来是对的
```

但用户实际跑的那份配置里存的是**旧算法**算出来的尺寸（1280×720 之类）。程序启动时优先读记录，记录存在就不会走默认值分支。

结论：**改了默认值，必须让老记录失效**，否则改了等于没改。

## 4. 怎么定位的

1. 先看代码：两条分支都有默认值 → 逻辑没问题
2. 再看配置：`build\windows-debug\bin\Debug\config\window.ini` 里 `[video_window_landscape]` 是 900×430 → 这份是对的
3. 但用户截图里的窗口明显大于 900 → **他跑的不是这份配置**（安装版有自己的 config）
4. 结论转向"记录里存着旧值"，改成一次性迁移

## 5. 怎么解决的

```cpp
// 一次性迁移：横屏默认尺寸从"按帧比例"改成了 900x400。
// 老用户的 window.ini 里存着按旧算法算出来的大尺寸，光改代码看不到效果，所以这里清一次。
if (!window_store.contains(QStringLiteral("ui/landscape_default_v2")))
{
    window_store.remove(QStringLiteral("video_window_landscape"));
    window_store.remove(QStringLiteral("video_pos_landscape"));
    window_store.setValue(QStringLiteral("ui/landscape_default_v2"), true);
    window_store.sync();
}
```

用标记保证**只清一次**：之后用户自己拖出来的尺寸不会再被抹掉。

## 6. 打开目录的两条命令

```
① adb shell mkdir -p /sdcard/Download/QmlScrcpy
② adb shell am start -n com.android.documentsui/.files.FilesActivity \
     -d "content://com.android.externalstorage.documents/document/primary%3ADownload%2FQmlScrcpy"
③ 失败退回：am start -a android.intent.action.VIEW_DOWNLOADS
```

试过三种打开方式：

| 方式 | 结果 |
|---|---|
| `VIEW` + `content://…document/primary%3ADownload%2FQmlScrcpy` | 弹"用哪个应用打开"选择框，烦 |
| 加 `-t vnd.android.document/directory` | 还是选择框 |
| **`-n com.android.documentsui/.files.FilesActivity`** | 直接进文件管理器 ✓（实测 realme 停在「下载」根目录） |
| `VIEW_DOWNLOADS` | 稳定进「下载」，作为退路 |

已知不完美：不是所有机型都能直接定位到子目录，但 `QmlScrcpy` 文件夹就在第一项。

## 7. 收获

- **改了默认值要配套迁移**：读优先级是"记录 > 默认"，不迁移就等于没改
- **迁移要用版本标记**，不能"每次启动都清"，否则用户的自定义永远存不住
- **调 Intent 时优先点名组件**（`-n`），走 `VIEW` 会被系统弹选择框

# P21 · 零服务器版本检查

## 1. 这一阶段要做什么

用户想解决"每次发版都要手动通知"的问题，方案是启动时查版本、有新版就提示自己去下载。原本设想自建 TCP 服务器，讨论后改成**静态 JSON + CDN**：0 服务器、0 费用。

## 2. 怎么做的

- 仓库根目录放 `latest.json`（`latest` / `minimum` / `url` / `notes`）
- `libs/update/version_compare.*`：只做版本解析与比较，纯逻辑、可单测
- `src/update_checker.*`：依次尝试三个源，成功后比对，给出 `updateAvailable` / `updateRequired`
- 主窗右上角红标：橙色=有新版，红色=必须更新；悬停显示 notes，点击开浏览器

## 3. 为什么不用自建 TCP

原本想法是"启动时连一次 TCP 拿版本号，旧版直接踢下线"。问题：

1. 只在启动时连，**没有连接可踢**；要踢就得长连接或定时轮询
2. 版本信息就是一个几百字节的 JSON，**用完即断**，TCP 自定义协议只增加工作量
3. 自建就要处理 TLS、并发、超时、进程守护

静态文件把这四件事全省了。真需要"统计有多少人在用"时才值得上服务器。

## 4. 怎么定位的几个坑

**① GitHub 直连不通**

第一版只有 jsDelivr，实测本机：

```
curl https://cdn.jsdelivr.net/... → 000（0.23s 就失败）
curl https://raw.githubusercontent.com/... → 000
curl https://www.baidu.com → 200
```

结论：**国内环境必须有国内源**。改成 Gitee → jsDelivr → GitHub 依次尝试。

**② Qt 5.15 没有 OpenSSL**

```
[update] 检查更新失败（不影响使用）: "TLS initialization failed"
```

这套 Qt 安装里没有 `libssl-1_1-x64.dll`（Qt 因许可证不打包）。两条路：把 DLL 塞进安装包，或换传输手段。

选了后者：`QSslSocket::supportsSsl()` 为 false 时用系统自带的 `curl.exe`（Win10 1803+，走 SChannel）。多一个进程，但只在启动时跑一次，且不增加安装包体积。

**③ 版本比较不能按字符串**

`"0.10.0" < "0.9.0"` 按字符串比是对的，按语义是错的。单测专门锁了这条。

## 5. 怎么解决的

```
客户端启动
   │
   ├─ Gitee raw       ← 国内先试这个
   ├─ jsDelivr CDN
   └─ GitHub raw      ← 兜底
        │
        └─ 谁先返回合法 JSON 用谁，全失败就静默跳过
```

四种状态：

| 情况 | 表现 |
|---|---|
| `本地 < minimum` | 红色「必须更新 x.y.z」 |
| `本地 < latest` | 橙色「新版 x.y.z」 |
| 本地 = latest | 不显示 |
| 全部源失败 | 不显示，只写一行日志 |

## 6. 验证

单测（`tests/tst_version.cpp`，6 个用例）锁了：三段解析、后缀忽略、非法输入、`0.10 > 0.9`、`1.2 == 1.2.0`、非法远端不误拦。

链路验证（把 JSON 放本地、用 `config.ini` 的 `update/url` 指过去）：

```
[update] 本地 "0.1.4" 远端 "0.1.5" 提示更新 true 强制 false
```

主窗出现橙色「新版 0.1.5」。

## 7. 收获

- **先问"这东西是不是一个静态文件"**：能静态化的就别写服务
- **国内环境默认要双源**：GitHub 直连不可靠，Gitee/CDN 兜一层
- **Qt 5.15 的 HTTPS 依赖 OpenSSL**，没打包就得准备退路（系统 curl 是个好兜底）
- **版本比较必须按数字**，字符串比会出 `0.9 > 0.10` 这种荒唐结果
- **检查更新要能失败**：任何网络问题都不该阻止软件启动

# P22 · 一键更新（下载 + 校验 + 静默安装）

## 1. 这一阶段要做什么

0.1.5 的版本检查只是"有新版就亮红标，跳浏览器"。用户还得自己下、自己装。这一阶段把后半段也做成程序的事：**点一下，剩下全自动**。

范围：下载、校验、启动安装、自动重启。
不做：改安装位置（那会涉及老用户迁移）。

## 2. 怎么做的

```
点「立即更新」
   → curl -L --fail -o %TEMP%\QmlScrcpy\Setup_x.y.z.exe
   → 核对 size → 算 SHA-256（后台线程）
   → startDetached(Setup, {/SILENT, /CLOSEAPPLICATIONS, /NORESTART})
   → QCoreApplication::quit()
   → Inno [Run] 段装完自动起新版本
```

`latest.json` 增加两个字段：`size` 和 `sha256`，由发版脚本自动算。

## 3. 为什么下载用 curl 不用 Qt 网络

Qt 5.15 的 HTTPS 依赖 OpenSSL，这套 Qt 没带 `libssl-1_1-x64.dll`（前面做版本检查时已经踩过）。要么把 OpenSSL 打进安装包（+5MB + 许可证），要么用系统 curl。

选了 curl：Win10 1803+ 自带，走 SChannel，不依赖 OpenSSL。

两个参数很关键：

- `-L`：Gitee 的下载链接会 302 到 CDN，不跟随就拿到一个空文件
- `--fail`：4xx/5xx 直接非 0 退出，不然会把错误页当 exe 存下来

## 4. 进度为什么不用 curl 的输出

`curl --progress-bar` 写 **stderr** 且用 `\r` 回退刷新，解析起来要处理半行、回车、单位转换。改成**轮询文件大小**：

```cpp
progressTimer->setInterval(300);
progress = QFileInfo(path).size() / latest.size;
```

`size` 来自 `latest.json`，所以进度分母是准的。300ms 对进度条足够。

## 5. 哈希为什么必须算

只比 size 只能防截断，防不了替换：

| 风险 | size 能挡吗 | sha256 能挡吗 |
|---|---|---|
| 下载中断、文件截断 | ✅ | ✅ |
| CDN 缓存串版本 | ❌ | ✅ |
| DNS 污染 / 中间人换包 | ❌ | ✅ |

算哈希读 45MB 约 200ms，放主线程会让进度条卡住，所以丢 `TaskRunner`：

```cpp
TaskRunner::Instance().Post([this, path, expect]() {
    QCryptographicHash hash(QCryptographicHash::Sha256);
    hash.addData(&file);
    // 结果用 invokeMethod 回主线程
});
```

## 6. 安装为什么一定弹 UAC

`setup\QmlScrcpy.iss`：

```ini
PrivilegesRequired=admin
DefaultDirName=D:\QmlScrcpy
```

装到 `D:\` 要管理员权限，`/SILENT` 只是"不问问题"，不等于"不要权限"。所以用户会看到一次 UAC 确认，这一步绕不过去——能绕就是提权漏洞。

要做到完全无感只能改：

```ini
PrivilegesRequired=lowest
DefaultDirName={localappdata}\QmlScrcpy
```

但安装位置变了，老用户 `D:\QmlScrcpy` 里的配置、日志、截图都得迁移。权衡后没做。

## 7. /CLOSEAPPLICATIONS 不加会卡住

安装程序要覆盖 `QmlScrcpy.exe`，Windows 不允许覆盖运行中的 exe。

```cpp
QProcess::startDetached(setup, {"/SILENT", "/CLOSEAPPLICATIONS", "/NORESTART"});
QCoreApplication::quit();
```

`/CLOSEAPPLICATIONS` 让 Inno 主动关掉我们的进程；同时自己 `quit()` 更快。少了这一步，安装会弹"请关闭 QmlScrcpy"然后卡住。

## 8. 怎么验证的

能用命令行验证的部分都验了：

```
$ curl -L --fail -o test_setup.exe <0.1.6 直链>
下载大小：47979834  期望：47979834  一致=True
下载 sha256：9bf79e84…aac3
期望 sha256：9bf79e84…aac3
校验通过：True
```

界面部分（进度条 → 安装 → 重启）需要人工验：涉及 UAC 提权和进程重启，自动化脚本模拟不可靠。

## 9. 收获

- **"静默"要拆成下载和安装两段**：下载可以完全静默，安装受 UAC 约束
- **失败路径要留退路**：永远保留「下载页」和「稍后」，否则网络一抖用户就没法更新
- **哈希校验不能省**：只比大小挡不住替换
- **覆盖运行中的 exe 必须让进程先退**：`/CLOSEAPPLICATIONS` + 主动 quit

## P23 拆控制器：主窗只管连接，投屏行为独立

### 这一阶段要做什么

`DeviceController` 已经长到 167 行头文件 + 1161 行实现、30 个 `Q_INVOKABLE`，里面塞了会话、输入注入、滚轮、剪贴板、文件传输、老板键、窗口登记、设置转发。目标是把"投屏窗那一侧的行为"整体切出去，让主窗控制器只剩连接、设备列表、设置。

不做的事：不改任何行为，不动 QML 的界面布局，不碰协议。

### 怎么做的

候选方案三个：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. QML 直接绑多个对象 | 每个模块一个 `Q_INVOKABLE` 集合，QML 里分别绑 | 职责最清晰，但 QML 要改 40 多处绑定 |
| B. 门面内部拆子对象 | `DeviceController` 保留全部接口，内部转发到子模块 | QML 一行不改，但"投屏行为"仍然挂在主窗对象上 |
| C. 切一半 | 把投屏行为搬到新类，用接口解耦 | 折中：QML 改 24 处，但两边都能独立演进 |

选 C。边界定在"这行为属于哪个窗口"：投屏窗里的按钮和画面交互归 `VideoController`，主窗的设备管理和设置归 `DeviceController`。

新类要发控制消息，但会话在 `DeviceController` 手里。直接互相持有会绕成环，于是加了个 4 方法的纯接口：

```cpp
class ControlWriter
{
    virtual bool WriteControl(const QByteArray &message) = 0;
    virtual void ReportStatus(const QString &text) = 0;
    virtual bool IsConnected() const = 0;
    virtual QString DeviceSerial() const = 0;
};
```

`DeviceController` 实现它，`VideoController` 只依赖这 4 个方法。

### 写完为什么不是理想效果

第一次编译直接报了一串：

```
error C2535: "bool DeviceController::IsConnected(void) const": 已经定义或声明成员函数
error C2027: 使用了未定义类型"VideoController"
error LNK2019: 无法解析的外部符号 VideoController::Surface
```

原因分别是：`IsConnected` 原本就是属性 getter，加 `override` 时写了两份声明；`device_controller.h` 只前向声明了 `VideoController` 却在 `connect` 里取它的返回值；新文件没加进 `src/CMakeLists.txt`。

还有一个非编译错误但更隐蔽：搬过去的 `PushFiles` 在工作线程里直接调 `writer_->ReportStatus()`——`writer_` 是纯接口指针，不是 `QObject`，从工作线程改状态栏会踩 GUI 对象。改成用 `VideoController` 自己（`QObject`）做 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 转发。

### 怎么定位的

编译错误按顺序清：先把重复声明删掉，再补 `#include "video_controller.h"`，最后把两个新文件加进 `CMakeLists.txt` 重新 configure。

跨线程那条是靠读代码发现的：`writer_` 的类型是 `ControlWriter *`，它没有线程亲和性信息，但实现方 `DeviceController` 有。凡是工作线程里要碰它，就必须投递回主线程。

### 怎么解决的

- `src/control_writer.h`：4 方法接口
- `src/video_controller.{h,cpp}`：16 个 `Q_INVOKABLE` + 2 个属性 + `OnSurfaceControlMessage` 转发 + 工作线程回主线程的投递
- `DeviceController`：删掉 19 个函数（约 300 行），补 4 个接口实现 + `AttachVideoController`
- `main.cpp`：新建 `VideoController`、注入、注册进 QML 上下文
- QML：24 处 `deviceController.X` → `videoController.X`

### 最终效果 + 学到什么

| 指标 | 拆前 | 拆后 |
|---|---|---|
| `device_controller.h` | 167 行 | 154 行 |
| `device_controller.cpp` | 1161 行 | 862 行 |
| `Q_INVOKABLE` 数 | 30 | 14 |
| 新类体量 | — | 60 + 407 行 |

启动无 QML 报错，视频窗与工具栏未回归（截图、滚轮、快捷键逐项待人工验收）。

学到的：**先按"哪个窗口的行为"划边界，比按"技术分层"划更好落地**。技术分层（输入层/传输层）会让同一次点击横跨三个对象；按窗口划，QML 的改动是机械替换，回归面小。
## P24 渲染延迟：从平均值骗局到 3.8ms

### 这一阶段要做什么

量清楚一帧从进进程到上屏到底花在哪一段，并尽量把它压下来。要求逐帧、同帧、可证伪。

### 怎么做的

观测手段迭代了三版：全局计数器 + 每秒平均 → 只打印最近一帧 → **每帧一个 `FrameTrace` 跟着帧走**。第三版才做到"一行里的九个数字属于同一帧"。

### 写完为什么不是理想效果

- 第一版：平均值把 0.3ms 和 6ms 的帧糊成"稳定 5ms"，得出"固定延迟"的错误结论
- 第二版：字段不同步更新，同一行里混着两帧的数据
- 第三版：同一帧会因为窗口重绘多跑一轮 `render()`，打印两次（靠 `printed` 原子标记挡掉）

### 怎么定位的

看到"等唤醒恒定 5ms"先怀疑 Qt 唤醒渲染线程慢，于是加了两个探针：`QEvent::UpdateRequest` 的处理时刻、每帧 `update()` 的合并次数。

结果推翻假设：

| 段 | 实测 |
|---|---|
| `update()` → 事件被处理 | 4.3~6.5ms |
| 事件处理 → 渲染线程开跑 | 0.02ms |

接着依次排掉三个嫌疑人：8ms 轮询定时器（删了没用）、日志写盘（0.3ms）、重绘请求合并（恒为 1 次）。最后换渲染循环模式做对照实验，三组各跑 16~20 秒：

| `QSG_RENDER_LOOP` | 总延迟中位 |
|---|---|
| `threaded`（默认） | 7.08ms |
| `basic` | 7ms 量级 |
| `windows` | **3.78ms** |

### 怎么解决的

`main.cpp` 里在 `QGuiApplication` 之前 `qputenv("QSG_RENDER_LOOP", "windows")`。`windows` 循环不走 `QEvent::UpdateRequest`，那 5ms 的调度等待直接消失。

### 最终效果 + 学到什么

客户端总延迟 7.1ms → 3.8ms（90 分位 7.8 → 4.6ms），接近砍半。

教训：**平均值会把双峰抹成"稳定"，逐帧同帧才是唯一可信的观测**。这次连续两次被自己编的指标骗，完整排查过程见 [渲染延迟](渲染延迟.md)。

### 追加：剩下那 2ms

换到 windows 循环后还剩 3.7ms，继续拆出两段：`beforeSynchronizing` 到达时刻和它到 `synchronize` 的差。

| 段 | 中位 |
|---|---|
| GUI → 渲染线程被唤醒 | **1.95ms** |
| Qt 同步前准备 | 0.01ms |

唤醒时间集中在 1.5~2.5ms（660 帧里 347 帧），是定时器节拍而不是排队；`QSG_RENDER_TIMING=1` 也显示 Qt 自己的 sync+render 只有 0~3ms。翻了 Qt 5.15.2 的私有头文件坐实：`qsgwindowsrenderloop_p.h` 里就是 `pendingUpdate` + `maybePostUpdateTimer()` + `m_updateTimer`，`update()` 只置标志，真正开画由定时器触发。**这 2ms 在 Qt 的 windows 渲染循环内部，应用层改不掉**，再压只能自绘原生窗口，收益上限 2ms，不值得。

顺带算了一笔 120fps 的账：每帧预算 8.33ms，渲染线程只占 1.3ms、GUI 几乎不占、视频线程解码 3~5ms——客户端撑得住，限制在设备编码和传输。
### 再追加：真正的解法是 QT_QPA_UPDATE_IDLE_TIME

翻 Qt 文档时发现一句关键说明：两个渲染循环都通过 `QWindow::requestUpdate()` 安排下一帧，**多数平台上这由一个 5ms 的 GUI 线程定时器支撑**，`QT_QPA_UPDATE_IDLE_TIME` 可以把它调掉。

实测五种组合：

| 配置 | 总延迟中位 | 唤醒中位 |
|---|---|---|
| threaded 默认 | 6.26ms | 4.41ms |
| **threaded + `IDLE=0`** | **1.89ms** | **0.11ms** |
| windows 循环 | 3.74ms | 2.06ms |
| basic + `IDLE=0` | 1.69ms | 0.06ms（CPU 18.4%，不选） |

所以最终把 `QSG_RENDER_LOOP=windows` 换成了 **默认 threaded + `QT_QPA_UPDATE_IDLE_TIME=0`**：中位延迟 1.9~2.4ms，唤醒 0.1ms，静止画面 CPU 没有明显增加。之前那 2ms 的"定时器节拍"结论也一并作废——它不是 windows 循环特有的，而是 `requestUpdate` 的余量在两种循环里的不同表现。

另外确认了两件事：Qt 6.8 只剩 `basic` 和 `threaded` 两种循环（`windows` 是 Qt 5 独有），升级 Qt 6 反而没有这条捷径；跨线程直接调 `render()` 不可行，要自己掌控节奏只能用 `QQuickRenderControl` 或原生子窗口。
