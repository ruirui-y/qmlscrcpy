# 架构总览

## 一、背景

这个项目只沿用 scrcpy 的**协议事实**（12 字节包头、控制消息布局、server 参数），
代码和线程模型全部重写，不是 QtScrcpy 的 fork。

设备侧跑第三方 `scrcpy-server`（固定 5.0.1），主机侧用 Qt Quick 拉一条 H.264 流，
在 GPU 上转成 RGB 显示，并把鼠标键盘送回设备。

一开始用的是 Qt5 的 `QQuickFramebufferObject` + OpenGL，后来为了做零拷贝
换成了 `QQuickRhiItem` + D3D12（过程见 [D3D12迁移](../03-视频与解码/D3D12迁移.md)）。
下面写的都是换完之后的样子。

## 二、模块划分

```
QmlScrcpy
├── libs/                    ← 可独立编译、可单测的纯逻辑，不碰界面
│   ├── protocol/            scrcpy 线路格式：包头、控制消息、设备消息
│   ├── adb/                 adb 命令拼装 + 进程执行
│   ├── session/             server 参数、建链、隧道、握手
│   ├── stream/              读包、H.264 解码、帧所有权、耗时埋点
│   └── input/               坐标换算、触摸/滚轮/键盘消息拼装
├── ui/                      视频画布（QQuickRhiItem + RHI 渲染器 + QSB 着色器）
├── src/                     应用层：会话控制器 + 视频控制器、窗口配置、main
├── qml/                     控制窗 + 投屏窗
├── tests/                   单测（ctest），真机用例没设备会自动跳过
└── third_party/             vendored FFmpeg 8.1 + scrcpy-server 5.0.1
```

依赖方向是单向的：`src` → `ui` → `libs/*`，
`libs` 之间只允许 `session → adb/protocol`、`stream → protocol`。

## 三、控制器怎么分工

界面上两个窗口，对应两个控制器，靠一个 4 方法的接口连起来：

```
        QML
   ┌─────┴───────────────┐
   ▼                     ▼
deviceController      videoController
（主窗）               （投屏窗）
   │                     │
   │ 连接 / 断开 / 刷新    │ 鼠标键盘注入 / 滚轮 / 剪贴板 / 传文件 / 截图
   │ 设备列表             │
   │ 设置转发、老板键      │ 需要发消息时 ↓
   │                     │
   │   ┌─────────────────┘
   ▼   ▼
 ControlWriter（接口，4 个方法）
   WriteControl / ReportStatus / IsConnected / DeviceSerial
   ▲
   │ 实现
 DeviceController
   └─ ServerSession::SendControl → control_socket_->write()
```

- **VideoController 不认识 `ServerSession`**，只认 `ControlWriter`，所以它改不了连接状态
- **DeviceController 只多 4 个转发方法**，会话逻辑没被拆散
- 画布（`VideoItem`）拼好的鼠标/键盘消息走 `SigControlMessageReady`
  → `VideoController::OnSurfaceControlMessage` → 接口，转手写进 socket

拆之前 `DeviceController` 是 167 行头文件 + 1161 行实现、30 个 `Q_INVOKABLE`；
拆完是 154 + 862、14 个，剩下 16 个搬进了 `video_controller.{h,cpp}`（60 + 407 行）。

## 四、线程模型

```
┌──────────────────────────────────────────────────────────────────────┐
│ GUI 线程（Qt 事件循环）                                                │
│   QML、按钮、输入事件、控制 socket 读取                                 │
│   连接/断开是同步阻塞的（约 1.4 秒），建链阶段界面会卡一下                │
│   渲染器 synchronize() 也在这里跑（参数是 QQuickRhiItem*）              │
└──────────────────────────────────────────────────────────────────────┘
        │ update()（只是标脏）
        ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 渲染线程（Qt Quick 的 QSGRenderThread）                                │
│   render()：上传纹理 / 录制命令列表 / 画进 item 纹理                    │
│   之后 Qt 把它当普通纹理合成到窗口，再交给 DWM                          │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 视频线程（VideoReader，QThread，每个窗口一条）                          │
│   收包 → 解码 → Present（就地把最新一帧交给画布）                        │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 后台任务线程（TaskRunner，qsc-worker，一条）                            │
│   adb push 文件 / 切无线调试 / 写 window.ini / 检查更新                 │
│   全部从 TaskRunner::Post() 投递，串行执行，不碰 UI                     │
└──────────────────────────────────────────────────────────────────────┘
```

四条线程的来源：

- **GUI 线程**：Qt 规定，所有 QObject / QML / 窗口消息都在这里
- **渲染线程**：Qt Quick 自己开的，RHI 归它，所有 GPU 提交必须在这条线上
- **视频线程**：我们加的，socket 读会阻塞、解码要几毫秒，放 GUI 线程界面会冻
- **后台任务线程**：也我们加的，凡是"跑起来要几百毫秒、又不着急要结果"的 IO 都往这里丢

一个窗口 = 3 条全局线程 + 1 条视频线程。两个窗口就是 5 条（视频线程各自一条，前三条共用）。

### 为什么任务线程只有一条

一开始是"谁要异步谁自己 `QThread::create`"，结果长出三处：

| 位置 | 干什么 |
|---|---|
| `VideoController::PushFiles` | adb push 循环 |
| `DeviceController::SwitchToWifi` | 切无线调试 |
| `AppSettings::SaveVideoStateAsync` | 写 window.ini |

问题不在线程多，而在**没有统一入口**：线程名、优先级、退出时机各管各的，加第四个功能又是一份新代码。

现在统一成 `qsc::base::TaskRunner`：一个常驻线程 + 一条队列，`Post(std::function<void()>)` 投递。
任务都是 IO 型，串行反而好排查。主线程退出时调 `ShutdownTaskRunner()`，先让队列跑完再停线程。

顺带解决一个隐患：主线程和后台线程都开 `QSettings` 写同一个 `window.ini` 时，
主线程缓存里的旧值可能在退出时覆盖后台写的新值。现在窗口配置只在任务线程里写。

## 五、一帧的旅程

```
设备 MediaCodec
    │ 12 字节头 + H.264 负载
    ▼
adb 隧道（reverse 或 forward）
    │ TCP 27183
    ▼
视频线程  ── 切帧 + 解码 ──▶ GPU 里一张 NV12 纹理
    │ 读回内存（staging + Map + memcpy，5.27 MB）
    ▼
VideoItem::Present（仍在视频线程）── 只存"最新一帧"
    │ 投递 update() 到 GUI 线程
    ▼
GUI 线程 synchronize ── 取帧 + 逐行拷进两张平面（5.27 MB）
    ▼
渲染线程 render ── 上传两张纹理 + NV12 着色器转 RGB ──▶ item 纹理
    ▼
Qt 合成 → DWM → 屏幕
```

实测（1264×2780 原生分辨率，默认就打印 `[perf]`）：

| 段 | 耗时 |
|---|---|
| 解码读回 | 1.65 ~ 3.3 ms |
| synchronize（拷平面） | 1.12 ms |
| 上传 + 绘制 | 2.44 ms |
| 提交 | 1.26 ms |
| 到达 / 上屏 | 84~120 帧 / 64~76 帧 |

## 六、为什么这些设计是现在这样

| 决定 | 原因 |
|---|---|
| 帧只保留"最新一帧" | 投屏要低延迟，队列会累积延迟 |
| `Frame` 用 shared_ptr 带所有权 | 裸指针没人负责释放，上一版每帧漏 1.4 MB |
| 平面拷贝而不是长期持有 AVFrame | 帧活过解码器销毁就是 use-after-free，用 1 ms 换掉一类崩溃 |
| 渲染走 `QQuickRhiItem` | Qt 6 起 `QQuickFramebufferObject` 只能挂 OpenGL 后端，D3D12 要走 RHI |
| 视频线程直连投递 | 排队投递会被 GUI 线程的模态循环拖死（拖窗口卡 5 秒的根因） |
