# 架构总览

## 一句话

Qt Quick 客户端，通过 adb 隧道跟设备上的 scrcpy-server 通信，拉一条 H.264 流，在 GPU 上转成 RGB 显示，并把鼠标键盘送回设备。

> 只沿用 scrcpy 的协议事实（12 字节包头、控制消息布局），代码和线程模型全部重写，不是 QtScrcpy 的 fork。

## 模块划分

```
QmlScrcpy
├── libs/                    ← 可独立编译、可单测的纯逻辑，不碰界面
│   ├── protocol/            scrcpy 线路格式：包头、控制消息、设备消息
│   ├── adb/                 adb 命令拼装 + 进程执行
│   ├── session/             server 参数、建链、隧道、握手
│   ├── stream/              读包、H.264 解码、帧所有权、耗时埋点
│   └── input/               坐标换算、触摸/滚轮/键盘消息拼装
├── ui/                      视频画布（QQuickFramebufferObject + 三平面着色器）
├── src/                     应用层：会话控制器 + 视频控制器、窗口配置、main
├── qml/                     控制窗 + 投屏窗
├── tests/                   单测（ctest），真机用例没设备会自动跳过
└── third_party/             vendored FFmpeg 4.4 + scrcpy-server 3.3.3
```

依赖方向是单向的：`src` → `ui` → `libs/*`，`libs` 之间只允许 `session → adb/protocol`、`stream → protocol`。

## 控制器怎么分工

界面上两个窗口，对应的行为也拆成两个对象，靠一个 4 方法的接口连起来：

```
        QML
   ┌─────┴───────────────┐
   ▼                     ▼
deviceController      videoController
（主窗）               （投屏窗）
   │                     │
   │ 连接 / 断开 / 刷新    │ 鼠标键盘注入 / 滚轮 / 剪贴板 / 传文件 / 截图
   │ 设备列表             │
   │ 设置转发、老板键      │ 需要发消息时 ↓
   │                     │
   │   ┌─────────────────┘
   ▼   ▼
 ControlWriter（接口，4 个方法）
   WriteControl / ReportStatus / IsConnected / DeviceSerial
   ▲
   │ 实现
 DeviceController
   └─ ServerSession::SendControl → control_socket_->write()
```

- **VideoController 不认识 `ServerSession`**，只认 `ControlWriter`，所以它不能偷偷改连接状态
- **DeviceController 只多 4 个转发方法**，会话逻辑一点没被拆散
- 画布（`VideoItem`）拼好的鼠标/键盘消息走 `SigControlMessageReady` → `VideoController::OnSurfaceControlMessage` → 接口，转手写进 socket

拆之前 `DeviceController` 是 167 行头文件 + 1161 行实现、30 个 `Q_INVOKABLE`；拆完是 154 + 862、14 个，剩下 16 个搬进了 `video_controller.{h,cpp}`（60 + 407 行）。

## 线程模型

```
┌──────────────────────────────────────────────────────────────────────┐
│ GUI 线程（Qt 事件循环）                                                │
│   按钮、QML 绑定、8ms 重绘定时器、每秒帧率结算                          │
│   连接/断开是同步阻塞的（约 1.5 秒），建链阶段界面会卡一下                │
└──────────────────────────────────────────────────────────────────────┘
        │ update()（只是标脏）
        ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 渲染线程（Qt Quick 的 QSGRenderThread）                                │
│   sync 阶段：Renderer::synchronize() → 取最新一帧、拷三平面             │
│   render 阶段：Renderer::render()    → 上传纹理、着色器、画进 FBO       │
│   之后 Qt 把 FBO 当普通纹理合成到窗口，再交给 DWM                       │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 视频线程（VideoReader，QThread）                                       │
│   waitForReadyRead → 切帧 → 解码 → emit FrameReady（直连，就地执行）     │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 后台任务线程（TaskRunner，qsc-worker，一条）                            │
│   adb push 文件 / 切无线调试 / 写 window.ini                           │
│   全部从 TaskRunner::Post() 投递，串行执行，不碰 UI                     │
└──────────────────────────────────────────────────────────────────────┘
```

四条线程的来源：

- **GUI 线程**：Qt 规定，所有 QObject / QML / 窗口消息都在这里
- **渲染线程**：Qt Quick 自己开的，GL 上下文归它，所有 GL 调用必须在这条线上
- **视频线程**：我们加的，因为 socket 读会阻塞、解码要 5ms，放 GUI 线程界面会冻
- **后台任务线程**：也我们加的，凡是"跑起来要几百毫秒、又不着急要结果"的 IO 都往这里丢

### 为什么任务线程只有一条

一开始是"谁要异步谁自己 `QThread::create`"，结果长出三处：

| 位置 | 干什么 |
|---|---|
| `VideoController::PushFiles` | adb push 循环 |
| `DeviceController::SwitchToWifi` | 切无线调试 |
| `AppSettings::SaveVideoStateAsync` | 写 window.ini |

问题不在线程多，而在**没有统一入口**：线程名、优先级、退出时机各管各的，将来加第四个功能又是一份新代码。

现在统一成 `qsc::base::TaskRunner`：一个常驻线程 + 一条队列，`Post(std::function<void()>)` 投递。任务都是 IO 型，串行反而好排查；真要并发再换成 `QThreadPool` 也只改这一个文件。

主线程退出时调 `ShutdownTaskRunner()`，先让队列跑完再停线程。

> 顺带解决一个隐患：主线程和后台线程都开 `QSettings` 写同一个 `window.ini` 时，主线程缓存里的旧值可能在退出时覆盖后台写的新值。现在窗口配置只在任务线程里写。

## 一帧的旅程

```
设备 MediaCodec
    │ 12 字节头 + H.264 负载
    ▼
adb 隧道（reverse 或 forward）
    │ TCP 27183
    ▼
视频线程  ── 切帧 + 解码 ──▶ Frame（三个平面指针 + shared_ptr 保命）
    │ emit FrameReady（直连）
    ▼
VideoItem::Present（仍在视频线程）── 只存"最新一帧"
    │ update()（GUI 线程定时器发起）
    ▼
渲染线程 synchronize ── 取帧 + 拷三平面（约 5.2 MB / 1 ms）
    ▼
渲染线程 render ── 3 张纹理 + GLSL 转 RGB ──▶ FBO
    ▼
Qt 合成 → DWM → 屏幕
```

实测开销（1264×2776 原生分辨率，`QS_PERF=1`）：

| 段 | 耗时 |
|---|---|
| 等数据 | 6.0 ms（设备 60Hz 决定） |
| 解码 | 5.6 ms |
| 平面拷贝 + 上传 | 0.4 ms |
| 合计 | 约 12 ms / 帧，60 fps 有余量 |

## 为什么这些设计是现在这样

| 决定 | 原因 |
|---|---|
| 帧只保留"最新一帧" | 投屏要低延迟，队列会累积延迟 |
| `Frame` 用 shared_ptr 带所有权 | 裸指针没人负责释放，上一版每帧漏 1.4 MB |
| 平面拷贝而不是长期持有 AVFrame | 帧活过解码器销毁就是 use-after-free，用 1 ms 换掉一类崩溃 |
| 渲染走 QQuickFramebufferObject | `render()` 是 Qt 保证"渲染线程 + 上下文当前"的唯一入口 |
| 视频线程直连投递 | 排队投递会被 GUI 线程的模态循环拖死（拖窗口卡 5 秒的根因） |
