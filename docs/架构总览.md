# 架构总览

## 一句话

Qt Quick 客户端，通过 adb 隧道跟设备上的 scrcpy-server 通信，拉一条 H.264 流，在 GPU 上转成 RGB 显示，并把鼠标键盘送回设备。

> 只沿用 scrcpy 的协议事实（12 字节包头、控制消息布局），代码和线程模型全部重写，不是 QtScrcpy 的 fork。

## 模块划分

```
QmlScrcpy
├── libs/                    ← 可独立编译、可单测的纯逻辑，不碰界面
│   ├── protocol/            scrcpy 线路格式：包头、控制消息、设备消息
│   ├── adb/                 adb 命令拼装 + 进程执行
│   ├── session/             server 参数、建链、隧道、握手
│   ├── stream/              读包、H.264 解码、帧所有权、耗时埋点
│   └── input/               坐标换算、触摸/滚轮/键盘消息拼装
├── ui/                      视频画布（QQuickFramebufferObject + 三平面着色器）
├── src/                     应用层：设备控制器、窗口配置、main
├── qml/                     控制窗 + 投屏窗
├── tests/                   单测（ctest），真机用例没设备会自动跳过
└── third_party/             vendored FFmpeg 4.4 + scrcpy-server 3.3.3
```

依赖方向是单向的：`src` → `ui` → `libs/*`，`libs` 之间只允许 `session → adb/protocol`、`stream → protocol`。

## 线程模型

```
┌──────────────────────────────────────────────────────────────────────┐
│ GUI 线程（Qt 事件循环）                                                │
│   按钮、QML 绑定、8ms 重绘定时器、每秒帧率结算                          │
│   连接/断开是同步阻塞的（约 1.5 秒），建链阶段界面会卡一下                │
└──────────────────────────────────────────────────────────────────────┘
        │ update()（只是标脏）
        ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 渲染线程（Qt Quick 的 QSGRenderThread）                                │
│   sync 阶段：Renderer::synchronize() → 取最新一帧、拷三平面             │
│   render 阶段：Renderer::render()    → 上传纹理、着色器、画进 FBO       │
│   之后 Qt 把 FBO 当普通纹理合成到窗口，再交给 DWM                       │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ 视频线程（VideoReader，QThread）                                       │
│   waitForReadyRead → 切帧 → 解码 → emit FrameReady（直连，就地执行）     │
└──────────────────────────────────────────────────────────────────────┘
```

三条线程的来源：

- **GUI 线程**：Qt 规定，所有 QObject / QML / 窗口消息都在这里
- **渲染线程**：Qt Quick 自己开的，GL 上下文归它，所有 GL 调用必须在这条线上
- **视频线程**：我们加的，因为 socket 读会阻塞、解码要 5ms，放 GUI 线程界面会冻

## 一帧的旅程

```
设备 MediaCodec
    │ 12 字节头 + H.264 负载
    ▼
adb 隧道（reverse 或 forward）
    │ TCP 27183
    ▼
视频线程  ── 切帧 + 解码 ──▶ Frame（三个平面指针 + shared_ptr 保命）
    │ emit FrameReady（直连）
    ▼
VideoItem::Present（仍在视频线程）── 只存"最新一帧"
    │ update()（GUI 线程定时器发起）
    ▼
渲染线程 synchronize ── 取帧 + 拷三平面（约 5.2 MB / 1 ms）
    ▼
渲染线程 render ── 3 张纹理 + GLSL 转 RGB ──▶ FBO
    ▼
Qt 合成 → DWM → 屏幕
```

实测开销（1264×2776 原生分辨率，`QS_PERF=1`）：

| 段 | 耗时 |
|---|---|
| 等数据 | 6.0 ms（设备 60Hz 决定） |
| 解码 | 5.6 ms |
| 平面拷贝 + 上传 | 0.4 ms |
| 合计 | 约 12 ms / 帧，60 fps 有余量 |

## 为什么这些设计是现在这样

| 决定 | 原因 |
|---|---|
| 帧只保留"最新一帧" | 投屏要低延迟，队列会累积延迟 |
| `Frame` 用 shared_ptr 带所有权 | 裸指针没人负责释放，上一版每帧漏 1.4 MB |
| 平面拷贝而不是长期持有 AVFrame | 帧活过解码器销毁就是 use-after-free，用 1 ms 换掉一类崩溃 |
| 渲染走 QQuickFramebufferObject | `render()` 是 Qt 保证"渲染线程 + 上下文当前"的唯一入口 |
| 视频线程直连投递 | 排队投递会被 GUI 线程的模态循环拖死（拖窗口卡 5 秒的根因） |
