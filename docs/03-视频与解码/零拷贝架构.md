# 零拷贝架构

## 一、背景

现在每帧要搬 21.1 MB，其中 10.5 MB 走 PCIe。链路是这样：

```
┌─ VideoThread（socket 和解码同一条线程）──────────────────────────────┐
│  socket_->readAll()          收到字节流，拼出完整包                   │
│  decoder_->Push(payload)     send_packet / receive_frame             │
│    → GPU 里一张 NV12 纹理（d3d11va）                                  │
│  DownloadFrame               ← 要消掉的就是这一步                     │
│    CopySubresourceRegion     GPU 纹理 → staging 纹理   5.27 MB        │
│    Map(staging) + memcpy     显存 → 内存               5.27 MB        │
│                                         实测 1.65 ~ 3.3 ms           │
│  Frame{ 内存指针 }                                                    │
│  Present()  加锁存进 pending_，投递 update() 到 GUI 线程              │
└──────────────────────────────────────────────────────────────────────┘
                              ↓
┌─ GUI 线程 ─────────────────────────────────────────────────────────┐
│  synchronize()                ← 第二次搬像素                         │
│    逐行 memcpy 5.27 MB → plane_y_ / plane_uv_       实测 1.12 ms     │
└────────────────────────────────────────────────────────────────────┘
                              ↓（框架保证顺序，不加锁）
┌─ 渲染线程 ─────────────────────────────────────────────────────────┐
│  uploadTexture x2            5.27 MB CPU → GPU                       │
│  设置管线 / draw(4)           NV12 着色器采样 → 画进 item 纹理         │
│  endPass                     实测 2.44 ms（含上传）                  │
└────────────────────────────────────────────────────────────────────┘
                              ↓
┌─ 提交 ─────────────────────────────────────────────────────────────┐
│  endFrame / present          实测 1.26 ms，frameSwapped → 统计        │
└────────────────────────────────────────────────────────────────────┘
```

每帧搬运量：

| 方向 | 数据量 | 通道 |
|---|---|---|
| 显存 → 中转纹理 | 5.27 MB | GPU 内部 |
| 中转纹理 → 内存 | 5.27 MB | **PCIe** |
| 内存（帧）→ 内存（平面） | 5.27 MB | 内存 |
| 内存 → 显存 | 5.27 MB | **PCIe** |
| **合计** | **21.1 MB** | **其中 10.5 MB 走 PCIe** |

```
1264×2780 的 NV12：
  Y  平面 1264×2780 = 3.51 MB
  UV 平面 1264×1390 = 1.76 MB
  合计              = 5.27 MB
```

## 二、计划

### 2.1 线程模型

三条全局线程 + 每个窗口一条：

| 线程 | 谁创建 | 干什么 |
|---|---|---|
| GUI 线程 | Qt | QML、输入、控制 socket、`synchronize()` |
| 渲染线程 | Qt（QSG threaded loop） | 所有窗口的 `render()` |
| TaskRunner | 我们（`task_runner.cpp:34`） | 配置落盘、adb push、切无线、更新、上传 |
| VideoThread | 每个窗口一条 | socket 收包 + 解码 + 交帧，**同一条线程** |

```
1 个窗口 = 4 条线程，2 个窗口 = 5 条线程
```

socket 和解码不拆开：解码器不是线程安全的，包必须按顺序喂，拆两条线程只会多出队列和背压。

### 2.2 一个容易搞错的点

`synchronize()` 在 **GUI 线程**跑，不是渲染线程：

```cpp
virtual void synchronize(QQuickRhiItem *item) = 0;   // 拿到 item → 只能 GUI 线程
virtual void render(QRhiCommandBuffer *cb) = 0;      // 只有命令缓冲 → 渲染线程
```

参数是 `QQuickRhiItem*`，而 `QQuickItem` 不是线程安全的，只能在 GUI 线程访问。
连带结论：渲染器构造函数里存的 `item_`，在渲染线程里只能读原子变量
（`ClockUs()` / `MarkRenderEnd()` 是），不能读 `FrameSize()` 这类普通成员。

### 2.3 改完的样子

```
┌─ VideoThread ──────────────────────────────────────────────────────┐
│  socket_->readAll()                    同现在                      │
│  decoder_->Push(payload)   d3d12va，用 Qt 的 D3D12 设备              │
│    拿到 AVD3D12VAFrame：                                            │
│      texture            ID3D12Resource*（就在 Qt 的设备上）          │
│      subresource_index  数组层号                                    │
│      sync_ctx.fence     解码什么时候写完                            │
│      sync_ctx.fence_value                                          │
│  Frame{ 纹理, 层号, fence, fence_value, keep_alive }                │
│    keep_alive 保证这张纹理不被 FFmpeg 复用                          │
│  Present()  32 字节进 pending_                                     │
└────────────────────────────────────────────────────────────────────┘
                              ↓
┌─ GUI 线程 ─────────────────────────────────────────────────────────┐
│  synchronize()   只搬结构体，不碰像素                预计 ≈ 0.01 ms   │
└────────────────────────────────────────────────────────────────────┘
                              ↓（框架保证顺序）
┌─ 渲染线程 ─────────────────────────────────────────────────────────┐
│  录我们的命令列表（还没执行）：                                       │
│    barrier  解码纹理 COMMON → PIXEL_SHADER_RESOURCE                 │
│    barrier  RGBA 纹理 PIXEL_SHADER_RESOURCE → RENDER_TARGET         │
│    设置管线：NV12 双平面 SRV（PlaneSlice 0 / 1）                     │
│    draw(4)  → 直接写进 412×908 的 RGBA 纹理                          │
│    barrier  RGBA 纹理 → PIXEL_SHADER_RESOURCE                       │
│    barrier  解码纹理 → COMMON（还给 FFmpeg）                         │
│  我们的队列：                                                       │
│    Wait(解码 fence, fence_value)   ← GPU 排队，不占 CPU              │
│    ExecuteCommandLists / Signal(我们的 fence, v)                    │
│  CPU 等我们的 fence                ★ 唯一剩下的等待                  │
│    SetEventOnCompletion + WaitForSingleObject   预计 0.1 ~ 0.3 ms    │
│  RHI 采样 RGBA 纹理 → 画进 item 纹理 → 提交                          │
└────────────────────────────────────────────────────────────────────┘
```

| 方向 | 数据量 | 通道 |
|---|---|---|
| 解码纹理 → RGBA 纹理（转色） | 读 5.27 MB / 写 1.5 MB | GPU 内部 |
| RGBA 纹理 → Qt 画面 | 读 1.5 MB / 写 1.5 MB | GPU 内部 |
| **合计** | **约 9.8 MB** | **PCIe 0 MB** |

转色输出按 item 尺寸（412×908）而不是全分辨率：写 1.5 MB 而不是 14 MB，
缩小范围交给 GPU 采样器做。

### 2.4 逐环节对照

| 环节 | 现在 | 改完 | 变化 |
|---|---|---|---|
| 解码 | d3d11va | d3d12va（Qt 的设备） | 换后端 |
| 读回 | **1.65~3.3 ms** | 不存在 | **−1.65~3.3 ms** |
| synchronize | **1.12 ms**（5.27 MB） | ≈0.01 ms（32 字节） | **−1.11 ms** |
| 上传纹理 | 含在 2.44 ms 里（5.27 MB PCIe） | 0（直接读显存） | 归零 |
| CPU 等转色 | 不存在 | **0.1~0.3 ms** | 新增，但净赚 |
| RHI 绘制 | 2.44 ms | 约 0.3 ms | **−2.1 ms** |
| 提交 | 1.26 ms | 1.26 ms | — |

```
现在：1.65~3.3 + 1.12 + 2.44 + 1.26 ≈ 6.5 ~ 8.1 ms
改完：0.05 + 0.3 + 0.3 + 1.26       ≈ 1.9 ms
PCIe：10.5 MB/帧 → 0
```

### 2.5 四个同步点

| # | 谁和谁 | 手段 | 成本 |
|---|---|---|---|
| ① | VideoThread → GUI | `QMutex` + 「只留最新一帧」 | 一次加锁 |
| ② | GUI → 渲染线程 | `synchronize()` / `render()` 框架顺序 | 0（不用加锁） |
| ③ | 解码队列 → 我们的队列 | `queue->Wait(解码fence, value)` | GPU 排队，不占 CPU |
| ④ | 我们的队列 → Qt 队列 | CPU `WaitForSingleObject` | **0.1~0.3 ms（唯一阻塞）** |

同步点 ④ 选了「单缓冲 + CPU 等」，不用双缓冲（双缓冲省掉这次等待，但画面延迟 +1 帧，60fps 下 +16.7ms）。

不能让 Qt 的队列等我们的 fence：QRhi 不暴露「插入外部等待」的接口，
`render()` 里只有 `QRhiCommandBuffer`，没有原生队列操作的入口。

### 2.6 三件必须小心的事

**资源状态 barrier 必须成对**：

```cpp
barrier(解码纹理:   COMMON → PIXEL_SHADER_RESOURCE)           // 写前切进
barrier(RGBA 纹理: PIXEL_SHADER_RESOURCE → RENDER_TARGET)      // 写前切进
    ... draw ...
barrier(RGBA 纹理: RENDER_TARGET → PIXEL_SHADER_RESOURCE)      // 写后切回给 RHI 采样
barrier(解码纹理:  PIXEL_SHADER_RESOURCE → COMMON)             // 写后切回给 FFmpeg
```

切回去这一步不能漏，RHI 采样时状态不对会报 state mismatch 或画面黑。

**纹理生命周期**：D3D12 的解码纹理在 FFmpeg 的 DPB 池里，不持有引用就会被复用去解下一帧。
Frame 必须持有 `AVBufferRef`（或 shared_ptr 包住 AVFrame），渲染完一帧才释放。

**设备引用计数**：

```
Qt 创建设备（引用 1）
getResource 拿到 → AddRef（引用 2）
交给 AVD3D12VADeviceContext.device（引用 3）
FFmpeg 关闭时 Release（回到 2）→ 设备还活着
我们最后释放自己那份（回到 1）→ Qt 正常销毁
```

FFmpeg 文档原话：`Deallocating the AVHWDeviceContext will always release this interface`。
不 AddRef 就会把 Qt 的设备一起释放掉，下一帧直接崩。

### 2.7 四步实施

```
第 1 步  设备交接：Qt 的设备从渲染线程取出来，存进 VideoItem
第 2 步  解码器换 d3d12va + D3D12 读回（能跑、能出画）
第 3 步  去掉读回，改成 2.3 那套
第 4 步  解码器所有权从 DeviceController 挪到窗口
```

第 2 步先于第 3 步：零拷贝失败时能退回「d3d12va + 读回」这个能用的版本，
而不是整个 d3d12va 都白做。

### 2. 解码器换 d3d12va，仍然读回

**动了哪里**

```
libs/stream/h264_decoder.{h,cpp}
  SetExternalDevice(void*)        画布给的设备，Open 之前设
  OpenHardware()                  先试 d3d12va，起不来退回自建 D3D11（旧路径整段保留）
  OpenD3d12()                     把设备挂到 AVD3D12VADeviceContext，交出去之前 AddRef
  DownloadD3d12()                 av_hwframe_transfer_data 转成 NV12 软件帧，再按 linesize 拷进缓冲池
  PickPixelFormat()               D3D12 优先，其次 D3D11
  DrainFrames()                   硬解分支改成 D3D11 和 D3D12 都认

libs/stream/video_reader.{h,cpp}
  构造多一个 std::function<void *()> device_getter
  run() 开头等设备（最多 500ms），然后 SetExternalDevice + Open

src/device_controller.cpp
  不再在这里 Open 解码器，改成把「取设备」的回调交给读线程
```

**为什么要挪 Open**

RHI 的 `initialize()` 要等第一次渲染才跑，设备那时才存在；而原来 `Open()`
在连接完成时就调了。所以在 GUI 线程等设备只能干等，改成在读线程等，等到再开。

**撞到什么**

第一次跑，日志显示 `首帧格式 227`，但 `[perf] 1s 到达 0 帧`，帧一帧都没出来。

原因：`DrainFrames` 里硬解分支写的是

```cpp
if (av_frame->format == AV_PIX_FMT_D3D11)
```

d3d12va 给的是 `AV_PIX_FMT_D3D12`（枚举值 227），条件不成立，
掉进软解分支，把 `data[0]` 当成像素指针用。

```cpp
// 改后
const bool is_hardware_frame =
    av_frame->format == AV_PIX_FMT_D3D11 || av_frame->format == AV_PIX_FMT_D3D12;
```

顺手把两处误导的日志改了：`[decode] 使用 D3D11VA 硬件解码` 是写死的字符串，
现在打实际走的哪条；`首帧格式` 同时打 D3D11 和 D3D12 两个枚举值。

**跑出来什么**

```
[decode] 硬解设备已就绪 d3d12va（画布的 D3D12 设备）
[decode] 首帧格式 227（D3D11 = 171  D3D12 = 227）
[perf] 1s 到达 88 帧，上屏 83 帧，丢 0（0%），实际 17.5 Mbps
```

画面正常，无断言。对照上一轮 d3d11va + 读回（到达 106 / 上屏 76），这一轮上屏 83。
读回这一段还在（`av_hwframe_transfer_data`），第 3 步才删。

### 4. 删掉 CPU 读回的老路径

零拷贝跑通之后，d3d11va 那条「拷进暂存纹理再 Map 读回」的路再也用不上了，留着只会误导。

**删了什么**

```

CreateD3D11Device（枚举适配器、跳过虚拟显卡的那段）
OpenHardwareFallback（自建 D3D11 设备并挂到上下文）
DownloadFrame + ReadStaging（staging 拷贝 + Map + 逐行 memcpy）
SetAsyncReadback / async_readback_（异步读回的开关，d3d12 下没有意义）
src/device_controller.cpp 里的 decoder_->SetAsyncReadback(...)
```

```
libs/stream/h264_decoder.cpp  749 → 453 行
libs/stream/h264_decoder.h    72 → 65 行
净删 316 行
```

**行为变化**：硬解只剩 d3d12va 一条；`OpenD3d12` 失败就直接退软解，
不再有「自建 D3D11 设备」这个中间兜底。软解路径（YUV420P + WrapFrame）原样保留。

**跑出来什么**

```
[decode] 硬解设备已就绪 d3d12va（画布的 D3D12 设备）
[perf] 1s 到达 120 帧，上屏 115 帧，丢 0（0%），实际 15.6 Mbps
[perf]     上屏延迟 <1.5ms 2% / 1.5~2.5ms 0% / 2.5~3.5ms 93% / >3.5ms 3%，最大 3.4 ms

上屏延迟集中在 2.5~3.5 ms（93%），最大 3.4 ms。
这一段里 synchronize 只剩搬结构体，主要开销是转色那一趟的 GPU 等待加 RHI 提交。

### 5. 解码器所有权挪到窗口

到这一步解码器还挂在 `DeviceController` 上：连接时建、断开时销毁。但它的设备来自窗口，
创建时机又要等窗口的 RHI 初始化，挂在"连接"上本身就是错的。

**动了哪里**

```
ui/video_item.{h,cpp}
  Decoder(bool hardware, int soft_threads)   懒创建，参数由调用方传，不负责 Open
  CloseDecoder()                              断开时关掉，画布还在（重连能再开）
  成员 std::unique_ptr<H264Decoder> decoder_

src/device_controller.{h,cpp}
  删掉 decoder_ 成员
  连接时向画布借指针：video_->Surface()->Decoder(...)
  断开时调 video_->Surface()->CloseDecoder()
```

**改完的生命周期**

```
窗口存在   → 解码器存在（第一次取时懒创建）
断开连接   → 只 Close，画布还在，重连能再开
关窗      → 画布析构 → 解码器跟着销毁
```

两个窗口就是两个 `VideoItem`、两个解码器、两条读线程，彼此不共享。

**为什么不把 AppSettings 直接塞进画布**

`ui/` 看不到 `src/`（依赖方向是 `src → ui → libs`），
所以硬件开关和软解线程数由控制器读好当参数传进去，画布不依赖配置模块。

   → git checkout 恢复，改用「锚点 + 索引」重新插

② 删多行时把 TearDown 里的 session 收尾块一起删了 → 括号不匹配
   → 按行号重建那一段

③ VideoItem 里 include app_settings.h 路径不对（ui/ 看不到 src/）
   → 改成参数传递
```

**跑出来什么**

```
[decode] 硬解设备已就绪 d3d12va（画布的 D3D12 设备）
[perf] 1s 到达 97 帧，上屏 94 帧，丢 0（0%），实际 13.5 Mbps
```

连接、解码、上屏、断开都正常，无断言。

### 6. 把等解码围栏挪到解码线程

**怎么发现的**

补了转色耗时拆分（录命令+提交 / CPU 等围栏）之后，日志露出来了：

```
[convert] 241 帧：录命令+提交 145 us，等围栏 1236 us
```

每帧有 **1.25 ms** 卡在等围栏上，和当初估的 0.1~0.3 ms 差了四倍。

**是等谁**

把 `queue->Wait(解码围栏)` 临时去掉再测：

```
[convert] 206 帧：录命令+提交 106 us，等围栏 189 us
```

等围栏从 1236 us 掉到 189 us —— 也就是说那 1.1 ms 全是在等 FFmpeg 的解码围栏，
我们自己的转色只花 0.19 ms。

**怎么改**

解码线程每帧只花约 0.5 ms（拼包 5 us / 送包 225 us / 收帧 238 us），余量比渲染线程大得多。
所以把等待搬到解码线程：`H264Decoder::WaitForDecodeFence()`，在 `DownloadD3d12` 里
交出纹理之前用 CPU 等一次（事件对象自己建，不用 FFmpeg 那个，免得跟它的内部状态打架）。

渲染线程那边不再 `queue->Wait`：数据到它手里时已经是写完的。

**跑出来什么**

| 指标 | 改之前 | 改之后 |
|---|---|---|
| CPU 等围栏 | 1236~1281 us | 114~190 us |
| 绘制（含转色） | 1.57~1.73 ms | 0.27~0.35 ms |
| 上屏延迟 2.5~3.5ms 占比 | 86~96% | 2% |
| 上屏延迟 1.5~2.5ms 占比 | 0~2% | 94% |
| 上屏延迟最大 | 3.0~3.9 ms | 2.3 ms（偶尔 7.9 是卡顿瞬间） |

```
帧 1112 上屏：到达间隔 5.567 ms，上屏间隔 5.419 ms，synchronize 0.002 ms，绘制 0.305 ms，提交 0.612 ms
[perf] 1s 到达 120 帧，上屏 120 帧，丢 0（0%），实际 5.3 Mbps
```

顺带修了一个埋点 bug：零拷贝分支在 `synchronize()` 里提前 return，漏了 `trace_ = trace`，
导致逐帧追踪整个断掉（日志里一条「帧 N 上屏」都没有）。补上之后数字才看得见。
