# 解码链路

> 追踪文档：记录 H.264 解码这一层"为什么这么做、踩过什么、还差什么"。
> 渲染侧的内容不在这里，见 [视频链路]() 与 [渲染延迟]()。

## 一、这一阶段要做什么

把 scrcpy 服务端推来的 H.264 裸流解成一张能画的图，要求：

| 目标 | 约束 |
|---|---|
| 每帧都能解出来 | 不能因为配置包（SPS/PPS）丢一次就整段黑屏 |
| 解码本身要快 | 目标是一帧 3~5 ms 量级，不能成为整条链路的瓶颈 |
| 内存不能涨 | 每秒几十帧，任何一处漏释放都会在几分钟内显形 |
| 出错要说清原因 | 解码失败时给中文原因，而不是 `-1` |

**不做的**：硬件解码（D3D11VA / Media Foundation）。这一阶段只做 FFmpeg 软解。

## 二、怎么做的

### 2.1 为什么选软解而不是硬解

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| FFmpeg 软解 `avcodec` | 兼容所有 H.264 档位，代码量小，出问题好查 | 吃 CPU，多线程要自己调 | **选它** |
| D3D11VA 硬解 | CPU 占用低 | 要接 D3D11 设备、共享纹理、Qt 侧再取纹理，链路长一倍 | 以后再说 |
| Media Foundation | Windows 原生 | 只解决 Windows，跨平台就废 | 不选 |

项目是"先把链路跑通、再把延迟压下来"的顺序，软解在 1264×2776 分辨率下够用，所以硬解一直没做。

### 2.2 输入格式：裸 Annex-B，不手工拼 extradata

`H264Decoder`（[libs/stream/h264_decoder.h:18](H:/YJJ/Project/QmlScrcpy/libs/stream/h264_decoder.h#L18)）收到的数据有两类：

```
配置包（is_config = true）    SPS + PPS
数据包（is_config = false）   一帧或多帧的 slice 数据
```

关键设计：**两类包都原样喂给 FFmpeg，靠 in-band 参数集自己解析**，不手工构造 `extradata`。

这么做的原因：

- scrcpy 服务端在设备旋转、分辨率变化时会重发配置包，手工拼 `extradata` 就得处理"什么时候重建上下文"
- FFmpeg 对 in-band SPS/PPS 的处理是成熟的，直接交给它最省事

### 2.3 配置包可能要等一等

`pending_config_`（[h264_decoder.h:40](H:/YJJ/Project/QmlScrcpy/libs/stream/h264_decoder.h#L40)）解决的是另一个顺序问题：

```
设备可能先发数据包，后发配置包
  ↓
先到的数据包没有 SPS/PPS，单独送进去解不出来
  ↓
把它挂起，等配置包到了拼在一起再送
```

对应代码在 `Push()` 里（[h264_decoder.cpp:136-147](H:/YJJ/Project/QmlScrcpy/libs/stream/h264_decoder.cpp#L136-L147)）。

### 2.4 线程数：4

```cpp
// 实际端到端会多出约 (thread_count - 1) 帧的延迟，用延迟换吞吐
context_->thread_count = 4;
```

FFmpeg 的帧级多线程是"攒够 N 帧一起解"，线程越多吞吐越高、**延迟越大**。4 是在"解 2776p 不卡"和"延迟能接受"之间试出来的值。

### 2.5 只接受 YUV420P

```cpp
if (av_frame->format != AV_PIX_FMT_YUV420P)
{
    *error = QStringLiteral("不是 YUV420P，格式 = %1").arg(av_frame->format);
```

宁可报错也不做格式转换分支：scrcpy 服务端默认就是 YUV420P，真出现别的格式说明配置出了问题，早点暴露比默默转成黑屏好。

### 2.6 帧的所有权：`shared_ptr` 带自定义删除器

`WrapFrame()` 把 `AVFrame*` 塞进 `std::shared_ptr`，删除器里 `av_frame_free`：

```cpp
std::shared_ptr<const void> owner(av_frame, [](const void *ptr) { ... av_frame_free(&frame); });
```

这样 `Frame` 可以在视频线程、GUI 线程、渲染线程之间随便传，谁最后一个放手谁负责释放。像素数据不拷贝，只传指针 + 行宽。

## 三、写完为什么不是理想效果

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动后前几百毫秒黑屏 | 第一个配置包到得比数据包晚 | `pending_config_` 挂起拼包 |
| 旋转屏幕后画面不刷新或花屏 | 分辨率变了但解码上下文还是旧的 | 重新收到配置包时按新尺寸重建 |
| 偶尔报"不是 YUV420P" | 服务端换了编码器配置 | 报错原文打进日志，不静默转格式 |
| 解码耗时看不出来 | 没有埋点 | 加过临时探针，见下 |

## 四、怎么定位的

### 4.1 临时探针（已关）

`h264_decoder.h:36-49` 留着一整段被注释掉的探针：

```cpp
// void ReportDecodeTime(qint64 pack_ns, qint64 send_ns, qint64 drain_ns);   // 临时探针（已关）
// QElapsedTimer timer_;      // 量单次 Push 里三段各花多久
// int stat_frames_ = 0;      // 本秒解了多少帧
```

量的是 `Push()` 里三段：拼包、`avcodec_send_packet`、`avcodec_receive_frame`。**按秒结算**，因为单帧波动大，看一秒平均才有意义。

结论：解码不是瓶颈时就把探针关了——常开的日志会污染统计，也会影响时序。

### 4.2 卡顿到底卡在哪

定位顺序是：

```
帧率上不去
  ↓ 先看 到达帧率（网络/编码）
  ↓ 再看 解码耗时
  ↓ 最后看 上屏耗时
```

`docs/渲染延迟.md` 里记录了完整过程，最终结论是**上屏（渲染）那一侧吃掉了大部分时间**，解码不是主因。这也是后来把力气花在 `QT_QPA_UPDATE_IDLE_TIME` 上的原因。

### 4.3 参考图

`drawio/渲染流程.drawio` 里画了从收包到上屏的分段，本文只讲解码这一段，图里的其它段见渲染文档。

## 五、怎么解决的（当前形态）

| 问题 | 现在的做法 |
|---|---|
| 配置包后到 | `pending_config_` 挂起拼包 |
| 分辨率变化 | 按新配置包重建上下文 |
| 内存泄漏风险 | `shared_ptr` + 自定义删除器，引用计数归零即 `av_frame_free` |
| 解码慢 | `thread_count = 4` 折中 |
| 出错无声 | 所有失败路径带中文 `error` 字符串 |

## 六、最终效果 + 学到什么

### 现状

```
收包（VideoReader，qsc-worker 线程）
  ↓
H264Decoder::Push
  ├─ 拼包（配置包 + 数据包）
  ├─ avcodec_send_packet
  └─ avcodec_receive_frame → Frame（引用计数包装）
  ↓
只保留最新一帧（旧帧直接丢，见 视频链路.md）
  ↓
渲染线程 synchronize 时取走
```

### 学到的

1. **FFmpeg 的 in-band 参数集能省掉一整套 `extradata` 生命周期管理**，代价是要容忍配置包乱序。
2. **帧级多线程是"拿延迟换吞吐"**，线程数不是越大越好。
3. **`AVFrame` 必须用 `shared_ptr` 管**，跨三个线程传裸指针迟早出事。
4. **埋点要能随时关**，常开的日志会把"测量"变成"干扰"。

### 还差的

- 硬解（D3D11VA / MF）没做，4K 或高码率下 CPU 会顶不住
- 只支持 YUV420P，10bit / NV12 直接报错
- 解码耗时探针是注释状态，需要时得手工打开
- 没有解码失败的恢复策略（现在只是把原因打到日志）
## 七、换 GPU 解码（阶段一）

CPU 软解实测 **4.65 ms / 帧**，占整条链路的大头（上屏只有 2.8 ms），所以要换硬解。

### 7.1 目标链路

```
收包 → d3d11va 硬解（GPU 上完成）
     → AVFrame 里装的是 ID3D11Texture2D（NV12）
     → 【阶段一】av_hwframe_transfer_data 下载成 CPU NV12
        【阶段二】WGL_NV_DX_interop2 直接把 D3D11 纹理挂给 OpenGL，零拷贝
     → 着色器里做 NV12 → RGB（两平面，GPU 上转）
```

### 7.2 踩的坑（按遇到顺序，全是实测）

**坑 1：`Cannot allocate memory` —— 这份 FFmpeg 根本没编 d3d11va**

日志：

```
[decode] 硬件解码不可用，改用软解： "建 D3D11 设备失败：Cannot allocate memory"
```

`av_hwdevice_ctx_create()` 返回 `AVERROR(ENOMEM)`。看着像内存不足，实际是它内部调 `av_hwdevice_ctx_alloc()`，**设备类型没注册时返回 NULL**，create 把 NULL 包装成 ENOMEM。

验证方法（决定性）：查 `avutil-56.dll` 的导入表——

```
avutil-56.dll  →  bcrypt.dll, KERNEL32.dll
```

**没有 `d3d11.dll`、没有 `dxgi.dll`**，也没有 `D3D11CreateDevice` / `CreateDXGIFactory`。D3D11VA 的实现必然要调这两个，所以这份 4.4 是 `--disable-d3d11va` 编的。

→ 换成 BtbN 的 **FFmpeg 6.1.3 win64-lgpl-shared**，换完先验证再动代码：

```
avutil-58.dll  →  CreateDXGIFactory True / D3D11CreateDevice True / d3d11.dll True / dxgi.dll True
```

**坑 2：`分配硬解设备上下文失败` —— 同一个根因的第二次表现**

自己调 `av_hwdevice_ctx_alloc(AV_HWDEVICE_TYPE_D3D11VA)` 直接返回 NULL，因为我们换掉了 alloc 的调用位置，但库还是那份没编的。

**坑 3：虚拟显示适配器排在第一个**

换成 6.1.3 之后 `av_hwdevice_ctx_create` 仍然会挑第一个适配器，而这台机器上：

```
IddSampleDriver Device          ← 虚拟（Microsoft IDD 示例）
OrayIddDriver Device            ← 虚拟（向日葵）
NVIDIA GeForce RTX 4080 SUPER   ← 真显卡
```

**修法**：自己用 DXGI 枚举，跳过 `DXGI_ADAPTER_FLAG_SOFTWARE`，指定适配器 `D3D11CreateDevice`，再通过 `AVD3D11VADeviceContext::device` 交给 FFmpeg：

```cpp
const UINT flags = D3D11_CREATE_DEVICE_BGRA_SUPPORT | D3D11_CREATE_DEVICE_VIDEO_SUPPORT;
D3D11CreateDevice(adapter.Get(), D3D_DRIVER_TYPE_UNKNOWN, nullptr, flags, levels, 2,
                  D3D11_SDK_VERSION, device.ReleaseAndGetAddressOf(), &reached,
                  context.ReleaseAndGetAddressOf());
```

注意 `D3D_DRIVER_TYPE_UNKNOWN`——指定适配器时必须写它，否则 `D3D11CreateDevice` 直接失败。

**坑 4：启动弹「找不到 swresample-4.dll」**

6.x 的 `avcodec-60.dll` 自己依赖 `swresample-4.dll`（4.4 那份没有）。原来部署只拷三个 DLL，少一个就起不来。

→ 改成整目录扫：`file(GLOB QS_FFMPEG_DLLS ".../bin/x64/*.dll")`，不再写死文件名（换版本时编号还会变）。

**坑 5：改成 NV12 上传后驱动崩溃（nvoglv64.dll，0xC0000005）**

栈全在 `nvoglv64.dll` 里，看不出我们的代码，但异常地址是越界读。

原因：NV12 的 UV 平面一行是 **w 字节**（每两字节一对 U/V），我把它当成"宽度 = w、高度 = h/2"的 `GL_LUMINANCE_ALPHA` 纹理。LA 每纹素 **2 字节**，驱动按 `w × (h/2) × 2` 去读，我给的缓冲只有一半 → **多读一倍**。

1264×2780 时越界约 1.76 MB，正好是驱动崩的那个地址量级。

→ 纹理尺寸改成 **半宽 × 半高**（一个纹素装一对 U/V），缓冲大小不变：

```cpp
widths_[1] = (size.width() + 1) / 2;
heights_[1] = (size.height() + 1) / 2;
```

**教训：GL 的宽高是"纹素数"，不是"字节数"。交错格式的字节行宽 ÷ 每纹素字节数 = 纹素列数。**

### 7.3 阶段一的实测数据

探针：`QS_TRACE_DECODE=1`，按秒结算，17 秒样本、1678 帧、1264×2780、持续滑动制造画面变化。

```
[decode] 秒结 121 帧（硬解）：拼包 5us / 送包 203us / 收帧 5483us（其中下载 5471us）/ 合计 5692us / 最慢 15132us
```

加权平均：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 拼包 | **5 us** | 一次分配 + 一次 memcpy |
| 送包 | **227 us** | 硬解只是投递，不等 GPU |
| 收帧 | **5325 us** | 其中 **下载 5313 us** |
| 合计 | **5559 us** | 对比软解 4650 us |
| 单秒最慢 | 36691 us | 偶发，滑动密集期 |

### 7.4 阶段一的结论：**比软解还慢**

```
软解（CPU）：           4650 us
硬解 + 下载（阶段一）：  5559 us      ← 慢了 20%
```

原因一眼就能看出来：**下载占了收帧的 99.8%**。GPU 解码本身几乎不要钱（送包 227 us 只是投递），但把 5 MB 的 NV12 从显存拷回系统内存再传给 OpenGL，比原来 CPU 直接解还贵。

所以阶段一**不是一个成功的优化，是一个成功的测量**：它证明了瓶颈不在解码，而在"显存 → 内存"这一趟搬运。

## 八、阶段二要做什么（零拷贝）

### 8.1 目标

```
D3D11 解码纹理 ──WGL_NV_DX_interop2──▶ OpenGL 纹理 ──着色器──▶ RGB
                                       （全程不经过系统内存）
```

### 8.2 关键前提（已确认）

| 前提 | 状态 |
|---|---|
| 显卡支持 `WGL_NV_DX_interop2` | NVIDIA RTX 4080 SUPER，支持 |
| FFmpeg 拿到 `ID3D11Texture2D` | 已经是（`AVFrame::data[0]`） |
| Qt 用 OpenGL 后端 | 已经强制（`setGraphicsApi(OpenGL)`） |
| NV12 着色器 | 阶段一已写好，直接复用 |

### 8.3 要改的地方

| 文件 | 改动 | 预估 |
|---|---|---|
| `libs/stream/frame.h` | 增加"原生纹理"字段（`void*` 纹理指针 + 释放回调），NV12 CPU 缓冲变成可选 | ~40 行 |
| `libs/stream/h264_decoder.cpp` | 不再调 `av_hwframe_transfer_data`，把 `ID3D11Texture2D*` 和数组索引带出去，用 `av_frame_ref` 保活 | ~60 行 |
| `ui/video_item.cpp` | 注册 `wglDXOpenDeviceNV` / `wglDXRegisterObjectNV`，把 D3D11 纹理挂成 GL 纹理；`wglDXLockObjectsNV` 后再画 | ~150 行 |
| 着色器 | 复用阶段一的 NV12 着色器 | 0 |

### 8.4 预期收益与风险

| 项 | 预期 |
|---|---|
| 单帧 CPU 耗时 | 从 5559 us 降到 **300~800 us**（只剩投递和加锁） |
| 主要风险 | 纹理生命周期（解码器池复用，画之前必须 lock/保活） |
| 次要风险 | 驱动兼容（interop 在部分 Intel/AMD 驱动上不稳），需要留软解回退 |
| 观测手段 | 复用 `QS_TRACE_DECODE` 探针，把"下载"字段变成"加锁"耗时 |

### 8.5 阶段二的判断标准

上完零拷贝后：

- `[decode] 秒结` 的合计要 **低于 1000 us**
- 渲染侧 `取帧`（`sync`）耗时不涨（现在 0.89 ms）
- 画面颜色、旋转、断线重连都正常

达不到就退回阶段一（现在这套），**它至少是可用的、行为确定的**。
## 九、阶段一的第二次尝试：复用暂存纹理（B 方案，也失败）

### 9.1 假设

FFmpeg 的 `av_hwframe_transfer_data` 每帧都新建一张 staging 纹理，怀疑 5.3 ms 里很大一块是"分配 + 释放"，于是自己建一张、一直复用：

```cpp
// 尺寸变了才重建，其余时候一直复用
if (!d3d_->staging || d3d_->width != width || d3d_->height != height) { CreateTexture2D(...); }

// NV12 的 Y 和 UV 是两个子资源：下标 = 数组下标 × 2 + 平面号
d3d_->context->CopySubresourceRegion(staging, 0, 0,0,0, texture, slice * 2, nullptr);
d3d_->context->CopySubresourceRegion(staging, 1, 0,0,0, texture, slice * 2 + 1, nullptr);
Map(staging, 0, D3D11_MAP_READ, ...);   // ← 钱在这里
```

### 9.2 数据（1202 帧）

| 方案 | 拼包 | 送包 | 收帧 | 合计 |
|---|---|---|---|---|
| 软解（4.4） | — | — | — | **4650 us** |
| 硬解 + FFmpeg 下载 | 5 | 227 | 5325（下载 5313） | **5559 us** |
| 硬解 + 复用暂存 | 10 | 256 | 4990 | **5257 us** |
| 目标 | | | | ≤ 2000 us |

只省了 5%。

### 9.3 把下载拆成两段，看清钱花在哪

```
拷贝 0 us + 读回 5216 us
```

**拷贝是 0**——`CopySubresourceRegion` 只是往命令队列投递，GPU 拷贝异步执行；真正的时间全在 `Map(D3D11_MAP_READ)`：等 GPU 拷完，再把 5.2 MB 通过 PCIe 读回系统内存。

带宽一算就明白：`5.2 MB / 5.2 ms ≈ 1 GB/s`。

**结论：假设错了，瓶颈不是分配，是回读本身。** 只要还经过系统内存，就不可能进 2 ms。

### 9.4 这次尝试留下的东西

| 保留 | 原因 |
|---|---|
| `D3d11State`（device / context / staging） | A 方案还要用同一个设备做 Video Processor 和 GL interop |
| `DownloadFrame()` | 作为回退路径，A 出问题时能退回来 |
| 探针里的"拷贝 + 读回"拆项 | A 方案要对比"加锁"耗时，字段可以复用 |
| 硬解开关 | A 上线前默认回软解 |

## 十、A 方案（零拷贝）的设计要点

### 10.1 为什么不能直接 interop NV12

`WGL_NV_DX_interop2` 只接受能和 GL 内部格式对应的 DXGI 格式（`R8G8B8A8_UNORM` / `B8G8R8A8_UNORM` 这类）。**NV12 是 YUV 两平面格式，GL 没有对应内部格式**，注册会失败。

所以中间必须多一步 GPU 内转色：

```
D3D11 解码（NV12 纹理）
  ↓ ID3D11VideoProcessor（GPU 内 NV12 → BGRA）
BGRA 纹理（自己建，带 D3D11_RESOURCE_MISC_SHARED）
  ↓ wglDXSetResourceShareHandleNV + wglDXRegisterObjectNV
OpenGL 纹理 → 直接画（连 YUV 着色器都不用了）
```

### 10.2 三个必须处理的点

| 点 | 处理 |
|---|---|
| 设备要共用 | GL interop 必须和 FFmpeg 用同一个 `ID3D11Device`（`D3d11State` 已经有） |
| 纹理要 SHARED | 自己建的 BGRA 纹理必须 `MiscFlags = D3D11_RESOURCE_MISC_SHARED`，并 `GetSharedHandle` 后 `wglDXSetResourceShareHandleNV` |
| 纹理不能边写边读 | 双缓冲：解码线程写 A、渲染线程锁 B；每帧交换，避免撕裂和"锁住正在写的纹理" |

### 10.3 线程与锁的约定

```
解码线程                      渲染线程
  VideoProcessorBlt            wglDXLockObjectsNV
  → 写 bgra_textures_[buf]     → 用 bgra_textures_[buf] 画
  → buf = 1 - buf              wglDXUnlockObjectsNV
```

锁的是"注册给 GL 的那个对象"，不是 D3D 纹理本身；`wglDXLockObjectsNV` 会阻塞到 GPU 写完，这正是我们想去掉的等待——所以**写和读必须用不同缓冲**，否则又变成同步等待。

### 10.4 判断标准

| 指标 | 目标 |
|---|---|
| `[decode] 秒结` 合计 | **< 1000 us** |
| 其中"加锁" | < 300 us |

### 11.1 那个 bug：`d3d_` 里存的是空设备

`OpenHardware` 的"自己建设备"分支里，我先写了一遍 `d3d_ = std::make_unique<D3d11State>()`，后面又写了一遍：

```cpp
...

```

后果：`d3d_->device` 永远为空，`DownloadFrame()` 从来没执行过，第九节测到的 5.2 ms 其实是 `av_hwframe_transfer_data`。**第九节"复用暂存只快 5%"的结论作废**——对照的两边是同一条路径。

## 十二、实测对比与结论修正（重要）

### 12.1 两组数据

同样操作、同样设备，各 20 秒：

| 指标（探针口径） | 硬解 B | 软解 |
|---|---|---|
| 采样帧数 | 2654 | 2683 |
| 拼包 | 7 us | 5 us |
| 送包 | 193 us | 80 us |
| 收帧 | 6030 us（GPU 拷贝 1270 + 读回 4751） | 4 us |
| 合计 | 6231 us | 90 us |
| 丢帧 | 0 | 0 |

### 12.2 这个数字**不能**用来选方案

探针量的是**调用线程的等待时间**，两边的语义完全不同：

```
软解：send_packet 只是投递到 4 个 worker 线程 → 调用方只等 80us
      但帧级多线程会攒够 thread_count 帧才一起解
      → 屏幕上这一帧比最新收到的帧落后约 (thread_count - 1) 帧

硬解 B：send_packet 也是投递 → 调用方等 193us
      但紧接着 Map 要等 GPU 拷完 → 调用方再等 4.7ms
      → 主线程被挡，但画面本身不攒帧
```

**"调用方等得少" ≠ "画面跟手"。** 软解省的是主线程阻塞，代价是引入流水线延迟；硬解 B 反过来。

### 12.3 实际手感（用户实测）

| 场景 | 软解 | 硬解 B |
|---|---|---|
| 打字 | 按一个字母要等一下才出现，打快了更明显 | 跟手 |
| 切换屏幕 | 有帧缓动 | 没有 |
| 帧率 | 够 | 够 |

原因就是 12.2 里的流水线延迟：`thread_count = 4` 时最多攒 3 帧，60fps 下大约 50ms 的额外滞后，打字这种交互一眼能看出来。

### 12.4 结论

**默认走硬解 B**，配置项 `[decode] hardware=1`；想省主线程或对比手感可以改 `0`。

这条结论是**手感优先**，不是探针数字优先。探针只能用来看"哪一步在等"，不能用来判断"哪个方案更快"——这是这一节最该记住的教训。

### 12.5 探针的正确用法

| 想知道什么 | 该看哪一项 |
|---|---|
| 哪一步在等 | 拼包 / 送包 / 收帧 / 读回 的分项 |
| 画面端到端延迟 | **逐帧追踪的"从到达到上屏"**（`QS_TRACE_FRAMES=1`） |
| 打字跟不跟手 | 只能人肉试——流水线延迟不会体现在解码耗时里 |
