# 视频链路

## 一、背景

这篇讲的是**现状**，不是某一次改造：一帧从收包到上屏要横跨三条线程，每段都埋了耗时点。
排查延迟的时候，得能对着下面这张图指出是哪一段慢、是哪一段在等。

换 D3D12 之后渲染那半段全变了（GL 的三平面纹理换成了 RHI 的两平面），
过程见 [D3D12迁移](D3D12迁移.md)。

## 二、正文

### 全链路

```
设备 MediaCodec
    │
    ▼
┌────────────────────── 视频线程 VideoReader ──────────────────────┐
│ ① socket 等数据                                                  │
│ ② readAll → buffer append       收包，多出来的留给下一轮           │
│ ③ 解 12 字节头 → 拼满整帧        帧边界自己数，TCP 没有消息边界      │
│ ④ buffer.mid(12, len)           切出负载                         │
│ ⑤ buffer.remove(0, 12+len)      消费掉这一帧，否则下一轮重复解      │
│ ⑥ H264Decoder::Push             解码（d3d11va，实测 1.65~3.3 ms）   │
│     └ DownloadFrame             GPU 纹理读回内存，5.27 MB          │
│ ⑦ 直接调 VideoItem::Present      直连，就地执行                     │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌────────────────── VideoItem::Present（仍在视频线程）──────────────┐
│ pending_ = frame            只留最新一帧，旧的直接覆盖              │
│ 投递 update() 到 GUI 线程    视频线程直接调 update() 不安全         │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌────────────────── GUI 线程 synchronize（sync 阶段）───────────────┐
│ TakePendingFrame()          取走最新一帧（实测 1.12 ms）            │
│ 逐行拷进 plane_y_ / plane_uv_  5.27 MB，帧引用随后释放              │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌────────────────── 渲染线程 render（RHI 命令缓冲）─────────────────┐
│ uploadTexture ×2              R8 一张 + RG8 一张（实测 2.44 ms）    │
│ NV12 着色器                    BT.601 矩阵在 GPU 上转 RGB           │
│ 画进 item 纹理                 Qt 随后把它当普通纹理合成到窗口        │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                  提交（实测 1.26 ms） → frameSwapped
```

实测口径（1264×2780 原生分辨率，默认就打印 `[perf]`）：

```
[perf] 1s 到达 84~120 帧，上屏 64~76 帧，丢 0~1
```

### Frame 的引用计数

`Frame` = 平面指针 + 每行字节跨度 + 一个 `shared_ptr<const void>`
（持有 AVFrame，最后一个释放时调 `av_frame_free`）。

平面数看解码方式（`libs/stream/frame.h` 的 `PixelFormat`）：

```
软解 Yuv420P   Y / U / V 三个平面，色度宽高各一半
硬解 Nv12      Y 一个平面，UV 交错成第二个平面
```

一帧的完整生命周期：

```
解码      owner 计数 1
frames    vector 存一份      2
Present   pending_ = frame   3 → 函数返回后 frames 清空 → 2 → 局部引用析构 → 1
sync      取走 → 局部变量    2
sync 结束 局部变量析构        1（只剩 pending_ 里的旧帧，下次覆盖时归零）
```

**全程没有像素拷贝**，只有原子引用计数。唯一的像素搬运是 synchronize 里那次 5.27 MB memcpy。

为什么要拷？因为不能跨帧持有 AVFrame：帧活过解码器销毁就是 use-after-free
（踩过一次，崩在 `shared_ptr` 析构里）。用约 1 ms 换掉一类崩溃。

### 为什么只留最新一帧

```
播放器（Player 项目）：必须每帧都播，还要和音频对齐 → 需要队列
投屏（本项目）       ：只要最新画面          → 队列只会增加延迟
```

`pending_` 就是一个变量，新帧直接覆盖。GUI 线程再慢，也不会积压——最多丢帧，不会延迟累积。

### H.264 解码的细节

- 配置包（SPS/PPS）单独一包，不产生画面，`Push` 里存起来拼到下一个普通帧前
- `avcodec_send_packet` 之后要循环 `receive_frame`：一次可能吐 0 帧（还在攒）或好几帧（追赶）
- 硬解走 `AV_PIX_FMT_D3D11`（NV12 纹理），读回后按 NV12 组装；软解走 `AV_PIX_FMT_YUV420P`
- 软解 `thread_count` 由配置决定，默认 4：帧级多线程会多出约 `thread_count - 1` 帧的延迟，用延迟换吞吐

### 耗时埋点

默认每秒打印统计；逐帧明细用 `QS_TRACE_FRAMES=1` 打开：

```
[perf] 1s 到达 106 帧，上屏 76 帧，丢 0（0%），实际 18.9 Mbps
帧 972 上屏：到达间隔 8.178 ms，上屏间隔 7.483 ms，
            synchronize 1.119 ms，绘制 2.439 ms，提交 1.259 ms
```

埋点都在 `ui/frame_probe.{h,cpp}`，四段的定义：

| 段 | 起点 | 终点 |
|---|---|---|
| 到达间隔 | 上一帧到 Present | 这一帧到 Present |
| synchronize | 进 synchronize | 平面拷完 |
| 绘制 | 进 render | endPass |
| 提交 | render 结束 | frameSwapped |
