# GPU 对象模型：设备、上下文、纹理归属

这篇回答三个把人绕晕的问题：

```
① "设备"（device）到底是什么？为什么每个库都自己建一个？
② 纹理不是 GPU 上的一块内存吗？为什么还"属于"某个设备？
③ 上下文（context）又是什么？和线程是什么关系？
```

看懂了这篇，"零拷贝为什么失败"就没那么玄了。

---

## 一、先记住一句话

```
显存是 GPU 的公共土地，设备是"在你名下登记的一块地皮"，
纹理是"登记在你名下的一栋房子"，上下文是"你去办手续的那个窗口"。
```

下面逐条展开。

---

## 二、设备（device）是什么

### 它不是显卡

`ID3D11Device`（D3D11）、`QRhi` 背后的原生设备、Vulkan 的 `VkDevice`、OpenGL 的"上下文"——
这些都不是显卡本身，而是**你和驱动之间的一根会话**。

```
你的程序                    驱动                          GPU
   │                         │                             │
   │ CreateDevice() ───────▶ │  登记一个客户端会话          │
   │ ◀──────── 句柄 ──────── │                             │
   │                         │                             │
   │ CreateTexture2D() ────▶ │  在会话名下分配一块显存       │
   │                         │  并记入账本                  │
```

### 设备管三件事

| 职责 | 具体表现 |
|---|---|
| **资源账本** | 你创建的每个纹理、缓冲、着色器，都记在它的账上 |
| **状态空间** | 你绑定了哪张纹理、哪个视口、哪个着色器，只影响这个设备 |
| **命令提交** | 通过它的 context 把命令送进 GPU 队列 |

### 类比：TCP 连接

```
TCP 连接：登录后这个会话有自己的缓冲区、序号、状态
设备    ：创建后这个会话有自己的显存账本、状态、命令队列
```

差别在于：TCP 断了对端就没了；**设备不释放，资源一直挂着**，所以谁建谁负责销毁。

## 三、为什么纹理"属于"某个设备

因为纹理不是一块裸内存，它有一份**账本条目**：

```
CreateTexture2D 时驱动要记：
  格式（NV12 / RGBA）
  尺寸、mip 层数、数组层数
  在显存里的 GPU 虚拟地址
  引用计数（还有谁在用）
  归属哪个设备
  当前状态（正在被读 / 正在被写 / 可读可写）
```

### 类比：数据库里的表

```
设备 = 数据库的某个连接/用户
纹理 = 某张表里的一行（带主键、归属、权限）
```

你说的那句"没开权限读不到别人的字段"很贴切：

```
另一个设备要访问这张纹理
   → 不是"读不到"，而是"根本没有这个接口"
   → 要么导出共享句柄（≈ 建一个跨库视图）
   → 要么把数据搬过去（≈ 导出成 CSV 再导入）
```

### 关键结论

```
纹理的"归属"不是物理隔离，是账本隔离：
  物理上都在同一块显存里
  但没有句柄 + 没有同步，另一个设备既看不到、也不敢用
```

### 补充：设备到底是谁建的

**是我们自己建的，不是 FFmpeg 建的**（master 路径）。绑定靠 `AVD3D11VADeviceContext` 这个"插座"。

```
① 我们枚举适配器建设备        h264_decoder.cpp:134 / 272
       ↓
② 向 FFmpeg 要一个空壳        av_hwdevice_ctx_alloc(AV_HWDEVICE_TYPE_D3D11VA)
       ↓
③ 自己也留一份（ComPtr 赋值 AddRef）
       d3d_->device = device;  d3d_->context = device_context;
       ↓
④ 把设备塞进 FFmpeg 的插座    d3d11->device = device.Detach();
                            d3d11->device_context = device_context.Detach();
       ↓
⑤ 初始化插座                 av_hwdevice_ctx_init(device_ref)
       ↓
⑥ 挂到解码器上下文            context_->hw_device_ctx = av_buffer_ref(hw_device_)
```

`AVD3D11VADeviceContext` 里就是 `device` / `device_context` 两个字段，FFmpeg 有它就不再自己建。

引用计数的坑（源码注释原话）：

```
// 引用交给 FFmpeg 持有，它释放设备上下文时会 Release，这里不能再自己放
// 先自己留一份引用再 Detach：反过来的话 d3d_->device 拿到的是空指针
```

所以到 `avcodec_open2` 时，进程里只有**一个 D3D11 设备**，FFmpeg 是借用的。

### Qt 自己又建了什么

| 我们的分支 | Qt 的渲染后端 | Qt 建了什么 | 我们能拿到什么 |
|---|---|---|---|
| master（当前） | **OpenGL**（`QQuickFramebufferObject` 强制 GL 后端） | 一个 **GL 上下文**（渲染线程独占） | `render()` 回调里上下文当前化，直接调 `gl*` |
| `exp/zero-copy` | **D3D11**（`QRhi` 的 D3D11 后端） | 一个 **`ID3D11Device` + 即时上下文** | `rhi->nativeHandles()` 里的 `dev` / `context` |

证据（[GPU渲染改造](../03-视频与解码/GPU渲染改造.md) 第 46 行）：

```
Qt 用 D3D11 后端 → rhi->nativeHandles() 拿 device/context
```

### 于是"几个设备"分两种情况

```
master（读回内存）：
  D3D11 设备：1 个（我们建的，FFmpeg 借去解码）
  GL 上下文 ：1 个（Qt 建的）
  → 两边各有各的世界，靠"读回内存"交换，互不干扰 ✅

exp/zero-copy：
  D3D11 设备：2 个（我们建的 + Qt RHI 建的）
  → 跨设备就要共享句柄 + 同步，Qt 不给接口 ❌
```

**兜底路径**：如果第一步建设备失败，代码会退到 `av_hwdevice_ctx_create`（第 306 行），
那时设备才是 FFmpeg 自己建的——但这就是另一条路了。

### 一句话

```
Qt 一定有自己的设备/上下文：
  GL 分支 → 一个 GL 上下文，我们进去画
  D3D11 分支 → 一个 ID3D11Device + 即时上下文，nativeHandles() 能拿到
而解码用的 D3D11 设备是我们自己建的，FFmpeg 只是借用；
麻烦出在"零拷贝时 Qt 也建了一个 D3D11 设备，两个凑不到一起"。
```

## 四、上下文（context）是两种东西

这个词在我们项目里指过两个完全不同的东西，混了就容易互相矛盾。

### ① OpenGL 上下文（GL context）

```
一个状态机实例：
  当前绑定了哪张纹理、哪个帧缓冲、哪个着色器、视口多大
  同一时刻只能被一个线程"current"（当前化）
```

类比：**一个开着的工作台**，上面摊着你正在用的工具。换工作台 = 所有工具要重新摆。

```
特性：隐式状态——你调 glBindTexture 之后，后续所有绘制都用它
风险：谁都能改状态，多线程共用会互相破坏
```

### ② D3D11 设备上下文（device context）

```
命令提交通道：
  immediate context（即时上下文）：一个设备只有一个，所有命令排队进这一条
  deferred context（延迟上下文）：可以录制命令，之后再回放（很少用）
```

类比：**一个柜台**，一个设备只有一个窗口，大家都得排队。

```
特性：显式命令——每次 draw 都带上要用什么资源和状态
风险：多个线程/模块共用同一条队列时，命令顺序会被打乱
```

### 对照表

| | OpenGL 上下文 | D3D11 即时上下文 |
|---|---|---|
| 本质 | 状态机 | 命令队列 |
| 数量 | 每个线程可以 current 一个 | 每个设备只有一个 |
| 冲突形式 | 状态被别的代码改掉 | 命令顺序被打乱 |
| 我们项目里 | master 分支（QQuickFramebufferObject） | exp/zero-copy 分支（RHI + D3D11） |

## 五、命令是怎么走到 GPU 的

```
① 你调 CopySubresourceRegion / DrawIndexed
   ↓
② 命令进"即时上下文"的队列（CPU 侧排队，调用立刻返回）
   ↓
③ 驱动在合适时机把队列打包提交给 GPU（可能攒一批）
   ↓
④ GPU 按顺序执行
   ↓
⑤ 需要等结果时：Map / Fence / Query 让 CPU 阻塞到执行完
```

**这就是为什么"提交很快、Map 很慢"**：

```
CopySubresourceRegion  ≈ 5us（只是入队）
Map                    ≈ 0.6~2ms（等 GPU 真的写完）
```

### 我们量到的数字（硬解读回）

| 阶段 | 耗时 | 本质 |
|---|---|---|
| 提交拷贝 | 0.005ms | 入队 |
| 等 Map | 0.57~2.1ms | 等 GPU 执行完 |
| memcpy | 0.85ms | CPU 读内存 |

## 六、跨设备共享：句柄 + 锁

两个设备要访问同一块纹理，D3D11 的官方办法：

```
设备 A（解码器）
   CreateTexture2D(..., MiscFlags = D3D11_RESOURCE_MISC_SHARED)
        ↓ 取得共享句柄（NT handle）
设备 B（渲染器）
   OpenSharedResource(handle) → 拿到同一个资源的另一个句柄
        ↓
两边同时读写会乱 → 用 keyed mutex 做互斥
```

### keyed mutex 是什么

```
普通互斥锁：锁住整块资源
Keyed mutex：带一个"钥匙编号"
   设备 A 拿到钥匙 1，写完，释放 1
   设备 B 等钥匙 1 释放后才能拿 1 继续用
作用：保证"生产者写完，消费者才能读"
```

类比：

```
共享句柄 = 两个部门共用一个文件柜
keyed mutex = 柜子上只有一把钥匙，谁拿着谁能开
```

## 七、映射到我们项目的三条路

```
① 现在（读回内存）
   解码（设备 #1）→ staging（显存）→ Map → memcpy → 内存
   内存是"公共土地"，不属于任何设备
   Qt 用这块内存自己建纹理（设备 #2）→ 正常画 ✅

② GL 互操作（试过）
   FFmpeg 用 D3D11VA 解（设备 #1）
   我们的渲染器用 OpenGL（上下文 A）
   wglDXRegisterObjectNV 把 D3D11 纹理注册成 GL 纹理
   → 跨"API 世界"，靠 NV 扩展桥接
   → 同步要自己保证：GPU 还在写时 GL 不能读 ⚠️

③ RHI + D3D11 共享（失败）
   FFmpeg 设备 #1，Qt RHI 设备 #2
   需要共享句柄 + keyed mutex
   Qt RHI 不暴露 OpenSharedResource 的接口
   自己在 RHI 里插原生命令 → 抢同一个即时上下文 → TDR ❌
```

## 八、四个常见误解（我一开始也讲错过）

### 误解 1：纹理是"GPU 的公共内存"，谁都能用

```
错：物理上共享，账本上隔离。没有句柄/同步，别人看不到也不敢碰。
```

### 误解 2：纹理必须是 Qt 创建的

```
错（我之前就这么说过）：纹理只要"能被 Qt 当前后端访问"即可。
  - OpenGL 下：我们一直自己 glGenTextures，Qt 也照样能采样 ✅
  - D3D11 下：必须同一个设备，或者共享句柄 + 同步
```

### 误解 3：换个线程就能解决冲突

```
错：冲突来自"共享同一个上下文/队列"，不是线程。
   换线程只是把冲突挪到别处（我们试过，TDR 依旧）。
```

### 误解 4：GPU 慢导致卡

```
错：我们读回慢是因为"等队列排空"，不是搬运速度。
   空闲时 0.6ms、忙碌时 2.1ms —— 同一份代码，差别在队列占用。
```

## 九、自测五问

**Q1** 为什么 `CopySubresourceRegion` 只要 5us，`Map` 却要 2ms？

```
A：前者只是把命令写进队列，后者要等 GPU 真的执行完。
```

**Q2** 一个 D3D11 设备能有几个即时上下文？

```
A：一个。所有命令都排这一条队列，所以多模块共用必然互相影响。
```

**Q3** 我们的视频纹理在显存里，为什么 Qt 不能直接用？

```
A：因为它在 FFmpeg 的设备账本上，Qt 的设备没有它的句柄，
   而且两边没有同步机制（keyed mutex）。
```

**Q4** OpenGL 分支为什么没有这个问题？

```
A：整个进程只有一个 GL 上下文，所有纹理、所有绘制都在同一个"工作台"，
   没有跨设备/跨队列这回事。
```

**Q5** keyed mutex 在防什么？

```
A：防"生产者还没写完，消费者就开始读"。
   它是跨设备共享资源的同步原语，普通互斥锁做不到这个语义。
```

## 十、一句话总结

```
设备 = 显存账本 + 命令柜台
纹理 = 登记在某个账本上的显存块
上下文 = GL 的工作台 / D3D11 的柜台
跨设备 = 共享句柄 + keyed mutex（Qt RHI 不给这个口子，所以零拷贝走不通）
```
