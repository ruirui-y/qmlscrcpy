# 视频链路与图形 API 演进全景图

## 一、背景

这个项目的视频链路改了四代，每一代都是被上一代的具体瓶颈逼出来的。
分散的五篇文档（[Qt渲染插口演进](Qt渲染插口演进.md)、[硬解读回延迟](../03-视频与解码/硬解读回延迟.md)、
[场景图绘制与D3D11状态](场景图绘制与D3D11状态.md)、[零拷贝为什么失败](零拷贝为什么失败.md)、
[D3D12迁移](../03-视频与解码/D3D12迁移.md)）各讲一段，缺一条主线。

这篇就干一件事：**把四代演进串成一条因果链**，说明每一代为什么必须换，
以及为什么换到第四代才真正把画面留在显存里。

## 二、正文

### 1. 四代演进一张表

| 代 | 方案 | 一帧要搬多少 | 上屏帧率 | 最后卡在哪 |
|---|---|---|---|---|
| 一 | CPU 软解（YUV420P） | 0（全在内存里算） | 60 | CPU 算不过来，`thread_count=4` 换来 +3 帧延迟 |
| 二 | D3D11 硬解 + staging 读回 | 21.1 MB（10.5 MB 走 PCIe） | 100~120 | 读回 3.3 ms，其中 2.1 ms 在等 GPU |
| 三 | D3D11 同 Device 零拷贝 | 0 跨 PCIe（理论上） | 崩溃 | 即时上下文被两方共用，状态互相踩，TDR |
| 四 | D3D12 + Qt6 RHI 零拷贝 | 9.8 MB，全在显存内 | 110~120 | 只剩 Qt 的提交节拍 |

一句话概括这条线：**先想办法让 GPU 解码（一代到二代），再想办法别把画面搬回内存（二代到三代），
最后发现搬不搬不是问题、谁改状态才是问题（三代到四代）。**

### 2. 第一代：CPU 软解

```
┌─ 视频线程 ────────────────────────────────────────────────┐
│ 收包 → avcodec_send_packet → receive_frame                │
│   ↓                                                       │
│ FFmpeg 内部 4 条 worker 线程做帧级并行                     │
│   ↓                                                       │
│ AVFrame（YUV420P，三个平面在系统内存）                      │
│   ↓                                                       │
│ Frame{ Y / U / V 指针 + 三个 stride }                     │
└───────────────────────────────────────────────────────────┘
        ↓ Present（只留最新一帧）
┌─ GUI 线程 synchronize ────────────────────────────────────┐
│ 逐行 memcpy 三个平面 → plane_y_ / plane_u_ / plane_v_      │
└───────────────────────────────────────────────────────────┘
        ↓
┌─ 渲染线程 render ─────────────────────────────────────────┐
│ 上传三张纹理 → GLSL 转 RGB → 画进画布                      │
└───────────────────────────────────────────────────────────┘
```

代价有两块：

| 代价 | 数字 | 说明 |
|---|---|---|
| CPU 解码 | 约 5.6 ms/帧 | 1264×2780 这种分辨率，软解吃满一个核还不够 |
| 帧级并行带来的延迟 | `thread_count - 1` = 3 帧 | 4 线程并行，输出要等前 3 帧攒够，延迟 ~50 ms |

**为什么必须换**：不是优化能做掉的，是 CPU 算力上限。转身去用显卡的解码器。

### 3. 第二代：D3D11 硬解 + 读回

显卡解出来的画面在显存里，而我们是 CPU 渲染管线（当时还是 GL），只能搬回来：

```
┌─ 视频线程 ────────────────────────────────────────────────┐
│ d3d11va 解码 → ID3D11Texture2D（NV12，显存）               │
│   ↓                                                       │
│ CopySubresourceRegion → staging 纹理（CPU 可读的显存）      │
│   ↓                                                       │
│ Map(staging) ←── 卡在这里等 GPU 队列排空                    │
│   ↓                                                       │
│ memcpy 逐行 → 紧凑的 NV12 QByteArray                      │
│   ↓                                                       │
│ Frame{ Y / UV 两个平面 }                                   │
└───────────────────────────────────────────────────────────┘
        ↓
   上传两张纹理（又一趟 PCIe）→ 渲染线程转色上屏
```

一帧 4.9 ms 是怎么来的（第一次测量，PCIe 还在省电档 Gen1）：

| 段 | 耗时 | 说明 |
|---|---|---|
| 准备 + 提交拷贝 | 0.01 ms | 只是录了一条复制命令 |
| **等 Map** | **2.1 ms** | 其中约 0.6 ms 是真拷贝，**1.5 ms 是等 GPU 队列排空** |
| 读（memcpy） | 0.9 ms | 5.27 MB 从映射内存搬到紧凑缓冲 |
| 合计 | **4.9 ms** | 有效带宽 1.76 GB/s，只有 PCIe 理论的 9% |

后来查到 `pcie.link.gen.current = 1`（省电档），切到 Gen4 后降到 3.4 ms，但 `5.27MB ÷ 1.3ms ≈ 4 GB/s`
仍远低于 25 GB/s —— **说明瓶颈不是带宽，是"等"**。

异步读回（双 staging）把等待藏起来：CPU 不等，代价是画面晚一帧，3.3 ms → 1.65 ms。

**为什么必须换**：不管怎么优化，"把 5.27 MB 搬回内存再搬回去"这件事本身就是
每帧 10.5 MB 的 PCIe 流量加上一次不可消除的同步等待。

### 4. 第三代：D3D11 同设备零拷贝（失败）

思路很直接：让解码器和渲染器用**同一个 D3D11 设备**，解码出来的纹理直接给渲染器采样，
一个字节都不搬。

```
        同一个 ID3D11Device
   ┌────────────┴────────────┐
   ▼                         ▼
解码线程                  渲染线程
FFmpeg d3d11va            Qt RHI（GL/D3D11 后端）
   │                         │
   └── 同一条 ImmediateContext ──┘
              ↑
      两方共用同一个状态空间
```

失败的表现不是画错，是**整个进程崩溃**：

```
Device loss detected in Present()
崩溃点：nvwgf2umx.dll（NVIDIA 驱动）
```

根因在于 D3D11 的设备模型：

| 层 | 有什么状态 | 谁在改 |
|---|---|---|
| **Pass 级**（一轮一次） | 渲染目标 RTV/DSV、viewport、scissor | Qt 在 beginPass 设一次，**整窗共享** |
| **Draw 级**（每次 draw） | 管线、着色器资源、顶点缓冲 | 每次 draw 前设，缓存能跳过重复设置 |

我们为了让解码纹理能被采样，在渲染线程里跑了一次 `VideoProcessorBlt` 做 NV12→BGRA。
这一步**顺手绑了自己的 RTV 和 viewport**，而且不会还原。Qt 的 state cache 却以为
"这一轮我已经设过了，不用再设"，于是后面那 50~85 次窗口绘制全用错状态。

一个窗口一帧 50~85 次 draw，60 fps 就是 4200 次/秒 —— 状态一旦错，错的是这 4200 次。

**为什么必须换**：D3D11 只有一个 ImmediateContext，它是**全局可变状态**，
两个模块共用一个设备就等于共用一块没加锁的白板。这个问题在 D3D11 里无解，
除非让 Qt 把状态全量重设（它不会），或者我们每次都完整还原（漏一个就崩）。

### 5. 第四代：D3D12 + Qt6 RHI 零拷贝

D3D12 把这两件事拆开了：

| D3D11 的做法 | D3D12 的做法 |
|---|---|
| 一条 ImmediateContext，状态随时改、全局可见 | 每个 CommandList 自己录，录完才提交 |
| 状态是"当前设置" | 状态烘进 PipelineState，绑定时不可变 |
| 同步靠驱动内部排队 | 显式 fence，谁等谁自己写 |
| 一份资源可以隐式跨队列 | 资源状态显式声明，跨用途要 barrier |

改完的链路：

```
┌─ 解码线程 ────────────────────────────────────────────────┐
│ d3d12va 解码（用 Qt 的 ID3D12Device）                       │
│   ↓                                                       │
│ AVD3D12VAFrame：texture / subresource / sync_ctx{fence,value}│
│   ↓                                                       │
│ WaitForDecodeFence()：CPU 等这里，约 1.1 ms（它有 0.5 ms 余量）│
│   ↓                                                       │
│ Frame{ ID3D12Resource* + 层号 + fence + keep_alive }       │
└───────────────────────────────────────────────────────────┘
        ↓ Present（32 字节结构体，不过像素）
┌─ GUI 线程 synchronize ────────────────────────────────────┐
│ 只搬结构体，实测 0.002 ms                                  │
└───────────────────────────────────────────────────────────┘
        ↓ 框架保证顺序
┌─ 渲染线程 render ─────────────────────────────────────────┐
│ 自己的 CommandQueue / CommandList：                        │
│   barrier  NV12: COMMON → PIXEL_SHADER_RESOURCE            │
│   barrier  RGBA: PIXEL_SHADER_RESOURCE → RENDER_TARGET     │
│   DrawInstanced(3)  全屏三角形，NV12 两平面采样 → RGBA8     │
│   barrier  两个资源切回去                                   │
│   ExecuteCommandLists → Signal(自己的 fence)               │
│   CPU 等自己的 fence（约 0.17 ms）                          │
│   ↓                                                       │
│ RHI 采样 RGBA8 纹理 → 画进 Qt 的画布纹理 → 提交              │
└───────────────────────────────────────────────────────────┘
```

关键点不是"D3D12 更快"，而是**隔离**：

| 冲突点 | 三代（D3D11） | 四代（D3D12） |
|---|---|---|
| 状态空间 | 共用一条上下文，谁都能改 | 各录各的 CommandList，互不可见 |
| 同步 | 隐式，靠 Map 阻塞 | 显式 fence，谁等谁写清楚 |
| 资源状态 | 隐式（driver 兜底） | 显式 barrier，漏了立刻报错而不是静默画错 |

代价是代码多了：多一条命令队列、一个描述符堆、一条根签名、一个运行时编译的着色器 ——
换来的是 PCIe 流量归零，以及**一个模块再也不可能把另一个模块画错**。

### 6. Qt 的渲染插口怎么跟着变

四代演进里，Qt 那边也换了一代插口：

| 项 | Qt5 `QQuickFramebufferObject` | Qt6 `QQuickRhiItem` |
|---|---|---|
| 后端 | 只能 OpenGL | 由 RHI 决定（这里选 D3D12） |
| `synchronize(item)` | GUI 线程，**没有** GL 上下文 | GUI 线程，**没有** GPU 上下文 |
| `render()` | 渲染线程，GL 上下文当前 | 渲染线程，拿到 `QRhiCommandBuffer` |
| 谁开 render pass | Qt（画进 FBO） | **我们自己**（不调 `beginPass` 什么都不画） |
| 纹理格式限制 | GL 内部格式 | **必须 RGBA**，BGRA 会黑屏或错色 |
| `initialize()` 调用次数 | 一次 | **会重复调**，资源创建必须幂等 |

最后这条踩过：16 秒里 `initialize()` 被调了 567 次，每次新建采样器和顶点缓冲，全泄漏。

### 7. 同步机制演进（这条线索最值钱）

| 代 | 解码完没完，怎么知道 | 代价 |
|---|---|---|
| 一 | 不需要，解码在当前线程同步返回 | 0 |
| 二 | `Map(staging)` 隐式阻塞 | 每次 2.1 ms，且无法取消 |
| 三 | 无有效手段（想靠同一设备"自然同步"） | 直接崩 |
| 四 | 帧自带 `sync_ctx.fence` + 值；GPU 侧 `queue->Wait`，或 CPU 侧等事件 | 可控，能挪到有余量的线程 |

四代的关键进步是**同步变成了显式对象**：FFmpeg 在帧里给了 fence，我们可以决定
"在哪条线程、用什么方式等它"。最终把 1.1 ms 的等待从渲染线程挪到解码线程，
渲染线程每帧的绘制时间从 1.7 ms 降到 0.3 ms。

### 8. 现在的真实数字

同一台机器、1264×2780、硬解：

| 指标 | 数值 |
|---|---|
| 解码（含等 GPU 写完） | 约 0.5 ms 计算 + 1.1 ms 等待（在解码线程上） |
| synchronize（GUI 线程） | 0.002 ms（只搬 32 字节结构体） |
| 转色 + 绘制（渲染线程） | 0.27~0.35 ms |
| 提交 | 0.52~0.79 ms |
| 上屏延迟（到达→上屏） | 中位 1.5~2.5 ms，最大 2.3 ms |
| 帧率 | 到达 120 / 上屏 120，丢 0 |
| 每帧搬运算 | 21.1 MB → 9.8 MB，PCIe 部分 10.5 MB → 0 |

### 9. 一句话记住

```
一代：CPU 算不动
二代：算了但要把画面搬回来（PCIe 上每帧 10.5 MB）
三代：想不搬，结果发现搬不是问题、共用状态才是
四代：把状态和同步都变成显式的，画面从此留在显存里
```
