# 图形 API 对比与选型：D3D11 / D3D12 / OpenGL / Vulkan

## 一、背景

> 这篇写于换 D3D12 之前。文中「我们目前 6.x」「渲染：OpenGL」是当时的状态；
> 现在已升到 FFmpeg 8.1（`avcodec-62`）、渲染走 D3D12，见 [D3D12迁移](../03-视频与解码/D3D12迁移.md)。

零拷贝在 D3D11 上撞死之后，问题就变成了：是不是 API 选错了？要不要干脆换 D3D12 或 Vulkan？

换之前得先把三件事摆清：哪个 API 能真的在 GPU 里把 NV12 变成能采样的 BGRA、各家的状态模型差多少、换过去要动多少代码。

这篇顺带把"谁在解码、谁在渲染"这个最容易搞混的分工讲清——后面很多"换个更强的 API 就快了"的判断，都错在这一步。

---

## 二、正文

这篇回答三个问题：

```
① 想把"解码 + 转色 + 渲染"合成一个线程，哪些 API 支持？
② D3D11 / D3D12 / OpenGL（顺便带 Vulkan）差在哪？
③ 有没有别的工具能直接干这活？
```

---

## 三、目标方案长什么样

```
渲染线程（= 解码线程）
   ↓ avcodec_receive_frame
NV12 纹理（显存）
   ↓ GPU 转色（不经过 CPU）
BGRA 纹理
   ↓ 交给 Qt 画
屏幕
```

**唯一的硬性要求：这个 API 必须能让 GPU 把 NV12 变成可采样的 RGBA/BGRA。**

---

## 四、各 API 能不能完成 NV12 → BGRA

| API | 能在 GPU 里转 | 手段 | 限制 |
|---|---|---|---|
| **D3D11** | ✅ | `ID3D11VideoContext::VideoProcessorBlt` | 会改 Pass 级状态，没有 save/restore |
| **D3D12** | ✅ 且更干净 | 多平面格式（PlaneSlice）直接给着色器采样 | 代码量 ×2~3 |
| **Vulkan** | ✅ 同上 | `VkImageView` 平面视图 | 跨平台，但 FFmpeg 硬解配置复杂 |
| **OpenGL** | ⚠️ 实际不可行 | `WGL_NV_DX_interop` 注册 D3D 纹理 | GL 没有 NV12 格式，仍需拆两平面，扩展不支持 |
| **Metal** | ✅ | `CVPixelBuffer` 双平面纹理 | 只有 macOS（我们不用） |

**结论：想"完全在 GPU 里把 NV12 转成 BGRA"，只有 D3D11（VideoProcessor）、D3D12、Vulkan 三条路。**

---

## 五、三个 API 的核心差别

| 维度 | D3D11 | D3D12 | OpenGL |
|---|---|---|---|
| 年代 | 2009 | 2015 | 1992 |
| 状态模型 | 全局一份，**没有作用域** | 状态烘进 pipeline 对象 | 全局状态机，有 push/pop |
| 命令提交 | 一个即时上下文 | 多个命令队列 + 命令列表 | 隐式，调用即执行 |
| 多线程录命令 | ❌ | ✅ 每线程一个 command list | ❌ |
| NV12 着色器采样 | ❌ | ✅ 平面视图 | ❌ |
| 驱动开销 | 中 | 低 | 高 |
| 代码复杂度 | 低 | 高（资源屏障、描述符堆、fence） | 中 |
| Qt RHI 支持 | ✅ | ✅ | ✅ |
| FFmpeg 硬解 | `d3d11va`（成熟） | `d3d12va`（FFmpeg 7.1+） | 无原生硬解 |

### 一句话对比

```
D3D11  = 自动挡，一个收银台，NV12 只能走专用柜台（VideoProcessor）
D3D12  = 手动挡，多个收银台，NV12 直接能采样，但什么都自己排
OpenGL = 老爷车，规则简单，跟不上新格式
```

---

## 六、"不用 D3D11"的真实代价

| 换法 | 需要改什么 | 门槛 |
|---|---|---|
| **换 D3D12** | Qt RHI 后端 → D3D12；FFmpeg → `d3d12va`；着色器重编 QSB；原生互操作全部重写 | FFmpeg 7.1+（我们目前 6.x，`avcodec-60`） |
| **换 Vulkan** | 同上 + Vulkan 硬解（FFmpeg 需 `--enable-vulkan`）+ 驱动支持 | 更复杂，调试工具链不同 |
| **换 OpenGL** | 解决不了 NV12 采样问题（等于没换） | ❌ 无意义 |

---

## 七、还有别的工具吗

| 工具 | 能干什么 | 代价 |
|---|---|---|
| **libplacebo**（mpv 的渲染层） | Vulkan/D3D11 上做完整色彩转换与缩放 | 大依赖，要自己接进 Qt 渲染循环 |
| **CUDA + NVDEC** | 解码 + `cudaGraphicsGLRegisterImage` 直接产出 GL 纹理 | 只 NVIDIA，要装 CUDA Toolkit |
| **oneVPL / Media SDK**（Intel） | 解码 + VPP 转色 | 只 Intel |
| **AMF**（AMD） | 同上 | 只 AMD |
| **FFmpeg `libplacebo` 滤镜** | 滤镜链里完成转色 | 要 Vulkan 版 FFmpeg |

**没有"装个库就完事"的选项**，全都要求换解码后端或绑厂商。

---

## 八、三条现实选择

| 选择 | 做法 | 改动量 | 风险 | 延迟代价 |
|---|---|---|---|---|
| **A 留在 D3D11** | 单线程解码 + `VideoProcessorBlt` + 保存/恢复 RTV/viewport | 10~15 行 | 中（可能漏状态） | 无 |
| **B 换 D3D12** | RHI 换后端 + FFmpeg 升级 + 着色器直接采样 NV12 | 1~2 周 | 高 | 无 |
| **C 保持读回内存** | 现有架构 | 0 | 无 | 2~3ms/帧 |

### 推荐顺序

```
1. 先做 A（今天就能验）
   成立 → 省下 2~3ms，不必动 API
   不成立（还有别的状态被改）→ 再评估 B

2. B 的前置条件要提前确认
   FFmpeg 是否能升到 7.1（dll 体积、API 兼容）
   Qt 6.8 的 D3D12 后端在本机是否可用
```

## 九、补充：Vulkan 到底是什么

### 它不是一个"库"

```
Vulkan = 规范（Khronos 发布）
   ├─ 文档：定义了所有函数、结构体、语义
   ├─ 头文件：vulkan.h（Khronos 提供）
   ├─ 加载器：vulkan-1.dll（Khronos 提供，运行时找驱动）
   └─ 驱动实现：ICD（NVIDIA / AMD / Intel 各自写）
```

应用链接的是**加载器**，真正的实现在显卡驱动里。

### 跨平台范围

| 平台 | 支持方式 |
|---|---|
| Windows | ✅ 原生 |
| Linux | ✅ 原生 |
| Android | ✅ 原生（主要目标之一） |
| macOS / iOS | ⚠️ 通过 MoltenVK 转成 Metal |
| 游戏主机 | ✅ 部分 |

**它是跨平台的**，设计初衷就是替代 OpenGL。

### 设计哲学：像 D3D12，不像 OpenGL

| API | 状态模型 | 命令提交 |
|---|---|---|
| OpenGL | 隐式状态机 | 调用即执行 |
| D3D11 | 隐式 + 一个即时上下文 | 单队列 |
| D3D12 | 状态烘进 pipeline | 多队列 + 命令列表 |
| **Vulkan** | 状态烘进 pipeline / descriptor set | 多队列 + command buffer |

```
Vulkan ≈ 跨平台的 D3D12（两者都源自 AMD 的 Mantle）
```

### 对我们的价值

| 能力 | Vulkan |
|---|---|
| NV12 着色器采样 | ✅ `VK_FORMAT_G8_B8R8_2PLANE_420_UNORM`，Y/UV 分别取 |
| 状态隔离 | ✅ 没有"全局状态被改坏" |
| 多线程录命令 | ✅ 每线程一个 command buffer |
| FFmpeg 硬解 | ⚠️ 需要 `--enable-vulkan` 构建，且解码器支持 |

### 代价

| 项 | 说明 |
|---|---|
| FFmpeg 重编 | 现有 FFmpeg 不带 Vulkan 硬解 |
| Qt 后端 | `QSGRendererInterface::Vulkan`，QSB 着色器重编 |
| 原生代码 | 现有 D3D11 互操作全部作废 |
| 调试 | 要装 validation layers；驱动差异大 |

### 选型建议

```
Windows 上只要"快 + 干净"   → D3D12 更贴近原生，驱动路径最短
要跨平台                   → Vulkan
只想最小改动验证想法       → D3D11 + VideoProcessor + 状态还原
```

## 十、最容易搞混的一件事：谁在解码，谁在渲染

### 分层图

```
┌─────────────────────────────────────────────────────────┐
│ 你的代码 / Qt / FFmpeg                                   │
├─────────────────────────────────────────────────────────┤
│ 图形 API 家族（同一类东西，只是新旧/平台不同）             │
│   OpenGL │ D3D11 │ D3D12 │ Vulkan │ Metal                │
├─────────────────────────────────────────────────────────┤
│ 驱动                                                   │
├─────────────────────────────────────────────────────────┤
│ GPU 芯片内部的两个独立单元                                │
│   ┌──────────────┐        ┌──────────────┐               │
│   │ 视频解码引擎   │        │ 3D 渲染引擎   │               │
│   │ (NVDEC/VCN/QS)│        │ (着色器/ROP)  │               │
│   └──────────────┘        └──────────────┘               │
└─────────────────────────────────────────────────────────┘
```

**解码和渲染是两个硬件单元**，不是"某个 API 负责解码、某个 API 负责画"。

### 正确的任务 → API 映射

| 任务 | 走哪个 API | FFmpeg 里的名字 |
|---|---|---|
| 硬件解码 | D3D11 Video API | `d3d11va` |
| 硬件解码 | D3D12 Video API | `d3d12va`（FFmpeg 7.1+） |
| 硬件解码 | Vulkan Video | `vulkan`（需 `--enable-vulkan`） |
| 硬件解码 | VA-API（Linux） | `vaapi` |
| 渲染 | 任意（OpenGL/D3D11/D3D12/Vulkan） | Qt RHI 决定 |

### 我们 master 的真实分工

```
解码：D3D11（d3d11va）
渲染：OpenGL（Qt 的 QQuickFramebufferObject）
   ↓
两个 API 世界、两个设备账本
   ↓
只能读回内存交换 → 每帧 2~3ms
```

这就是读回开销的根源，不是"D3D11 慢"。

### 为什么"用最强的"不是答案

| 误区 | 实情 |
|---|---|
| D3D12 更快，所以该换 | 我们只画一个矩形，渲染开销 <0.1ms，换 API 不会更快 |
| 换 API 能提升帧率 | 换 API 只解决"NV12 能不能采样"，不解决性能 |
| Vulkan 最牛 | 最麻烦：FFmpeg 要重编、驱动差异大 |

### 决策依据：改多少，而不是多强

| 方案 | 改动 | 收益 | 门槛 |
|---|---|---|---|
| A D3D11 + 状态还原 | 10~15 行 | 省 2~3ms | 无 |
| B 换 D3D12 | 1~2 周 | 同 A，但更干净 | FFmpeg 7.1+ |
| C 换 Vulkan | 2 周+ | 同 A，且跨平台 | FFmpeg 带 vulkan |
| D 读回内存（现状） | 0 | 稳 | 2~3ms/帧 |

---

```
想把 NV12→BGRA 完全放在 GPU 里做，D3D11 的唯一手段是 VideoProcessor（会改状态），
D3D12/Vulkan 让着色器直接采样平面（不用改状态，但代码量翻倍）；
OpenGL 根本采不了 NV12，换它等于没换。
所以路线只有两条：D3D11 加状态还原（小改），或换 D3D12（大改）。
```
