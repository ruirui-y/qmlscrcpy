# 零拷贝为什么失败

目标：让 D3D11 解码出来的 NV12 纹理**不进内存**，直接给渲染用，省掉每帧约 2ms 的读回。

结果：三次尝试，三次失败。这篇把每次**怎么写的、报什么错、根因是什么**全部写清楚，不再一笔带过。

---

## 一、为什么想做零拷贝

```
现在（读回内存）：
  GPU 解码 → 纹理在显存
     ↓ 拷到 staging（DMA，0.6ms）
     ↓ Map（等 0.57~2.1ms）
     ↓ memcpy 到内存（0.9ms）
     ↓ glTexImage2D 上传（GPU 再吃一遍）
     ↓ 着色器转色

零拷贝想做：
  GPU 解码 → 纹理在显存
     ↓ 直接采样 / GPU 内转色
     ↓ 画到屏幕
```

省掉的是：**一次 DMA + 一次 Map 等待 + 一次 CPU memcpy + 一次上传**。

---

## 二、当时的前提：三条路

| 路径 | 做法 | 前置条件 |
|---|---|---|
| A 共用同一个 D3D11 设备 | FFmpeg 用 Qt RHI 的设备解码 | Qt 能给出 device/context |
| B 跨设备共享 | 解码器独立设备 + 共享句柄 + keyed mutex | 渲染端能打开共享资源 |
| C GL 互操作 | D3D11 纹理注册成 GL 纹理 | 用 `wglDX*` 扩展 |

我们分别试了 A 和 C，B 理论上可行但 Qt RHI 不提供接口。

---

## 三、第一次尝试：视频线程里做转色

### 写法

```
解码线程（视频线程）：
  avcodec_receive_frame → 拿到 D3D11 纹理
  VideoProcessorBlt(NV12 → RGBA)      ← 在视频线程调 D3D11
  RGBA 纹理交给渲染线程

渲染线程：
  Qt RHI 用这张 RGBA 纹理采样
```

### 现象

```
画面出不来，进程直接崩
栈：nvwgf2umx.dll!00007ff8eda7ca80()   未知
    ...
    kernel32.dll!00007ff9049f1fd7()    未知
    ntdll.dll!RtlUserThreadStart()     未知
```

`nvwgf2umx.dll` 是 NVIDIA 的 D3D11 用户态驱动。**崩在驱动内部，不是空指针。**

### 根因

```
Qt RHI（渲染线程）正在用设备 D 的即时上下文录命令
视频线程（另一条线程）也用同一个 D 的上下文提交 VideoProcessorBlt
    ↓
同一个上下文被两条线程同时写
    ↓
命令流损坏 → 驱动内部崩
```

**D3D11 的即时上下文不是线程安全的**，除非显式开启 `ID3D11Multithread` 保护（我们没开，开了也只保证不崩，不保证顺序）。

---

## 四、第二次尝试：把转色搬到渲染线程

### 思路

既然跨线程冲突，那就"谁录命令谁做转色"——把 `VideoProcessorBlt` 放到渲染线程的 `render()` 里。

### 现象

```
[decode] 首帧格式 172（D3D11 = 172）
Device loss detected in Present()
Graphics device lost, cleaning up scenegraph and releasing RHI
```

画面停在第一帧，`[rhi] 视频处理器就绪` 一次都没打。

### 根因

文档原话（[GPU渲染改造](../03-视频与解码/GPU渲染改造.md) 第 513 行）：

```
Qt RHI           正在即时上下文上录制本帧的绘制命令
我们的转换代码   也往同一个即时上下文里塞 VideoProcessorBlt
                 ↓
            命令顺序被打乱 → GPU 挂起 → 驱动移除设备（TDR）
                 ↓
            Present() 发现设备没了 → 清理场景图 → 停在第一帧
```

**TDR**（Timeout Detection and Recovery）：Windows 规定 GPU 一条命令超过 2 秒没完成就判定驱动挂了，强制重置设备。

即使同线程，"RHI 以为自己在独占上下文"这个假设被我们打破了。

---

## 五、第三次尝试：设备握手（`SetExternalDevice`）

### 思路

让 FFmpeg 直接用 Qt RHI 的设备解码（提交 `44c96aa`）：

```
① Qt RHI 初始化 → 建了设备 D
② rhi->nativeHandles() 拿到 D 的 device / context
③ decoder->SetExternalDevice(device, context)
④ FFmpeg 用 D 解码 → 纹理就在 D 上，不需要共享
```

文档当时的判断（第 173 行）：

```
目的只有一个：让解码器和 Qt 渲染后端用同一个 ID3D11Device。
不同设备上的纹理，createFrom 一定失败。
```

### 结果

解码成功、NV12 帧正常出（`[decode] 首帧格式 172`），但一到渲染就 TDR，和第二次一样。

### 根因（关键）

```
"同一个设备" 解决了纹理归属问题，
但同时意味着：解码线程和渲染线程共用**同一个即时上下文**
    ↓
FFmpeg 解码时提交的命令，和 RHI 录制绘制命令，仍然会交错
    ↓
TDR
```

**共用设备 ≠ 共用安全**。D3D11 的一设备一上下文模型，注定两个线程不能同时提交。

## 六、GL 互操作（路径 C）：原理与半途

### 代码里还留着的部分

```cpp
void YuvRenderer::EnsureInterop();      // 加载 wglDX* 扩展并打开设备
bool YuvRenderer::RegisterNative();     // 把 D3D11 纹理注册成 GL 纹理
```

### 原理

```
D3D11 纹理（FFmpeg 解出来的）
    ↓ wglDXRegisterObjectNV
得到一个 GL 纹理名（在同一块显存上"借看"）
    ↓
wglDXLockObjectsNV / UnlockObjectsNV 包裹采样
    ↓
GL 着色器正常采样，NV12 双平面转色
```

这是 NV 专有扩展（`WGL_NV_DX_interop`），Windows + NVIDIA 上可用。

### 为什么没走完

| 问题 | 说明 |
|---|---|
| **同步靠人肉** | GPU 还在写这张纹理时 GL 不能读，`Lock` 只能覆盖一部分窗口 |
| **锁粒度大** | 锁住整张纹理期间 GL 不能画别的东西，容易卡 |
| **厂商绑定** | 只有 NVIDIA 有；AMD/Intel 要另写 `WGL_AMD_interop` |
| **Qt 的 FBO 生命周期** | 纹理注册/注销时机要和 Qt 的 render 对齐，容易泄漏 GL 对象 |

理论收益 2ms，实际风险是花屏和偶发卡顿，所以停下来。

## 七、跨设备共享（路径 B）：理论可行，Qt 不给口子

### 标准做法

```
解码设备 D1：
  CreateTexture2D(..., D3D11_RESOURCE_MISC_SHARED) → 共享句柄
        ↓
渲染设备 D2：
  OpenSharedResource(handle) → 同一个资源的另一个句柄
        ↓
同步：keyed mutex（一把带编号的钥匙）
```

### 为什么在 Qt RHI 上做不了

```
Qt RHI 的接口只有 newTexture() / importTexture? 
    → Qt 6.6 的 QRhi 不暴露"用 NT 句柄打开外部资源"
    → 想做得自己调原生 D3D11 API
    ↓
又回到"往 RHI 的上下文里插命令" → TDR
```

## 八、结论

| 方案 | 可行性 | 卡在哪 |
|---|---|---|
| 共用同一个设备 | ❌ 试过 | 同一即时上下文，两线程抢队列 → TDR |
| 视频线程转色 | ❌ 试过 | 跨线程用同一上下文 → 驱动崩 |
| 渲染线程转色 | ❌ 试过 | 打乱 RHI 命令顺序 → TDR |
| GL 互操作 | ⚠️ 部分可用 | 同步难、厂商绑定、Qt 生命周期难对齐 |
| 跨设备共享 + keyed mutex | ❌ 无接口 | Qt RHI 不暴露导入共享资源 |
| 换 D3D12 / Vulkan 后端自写 `QSGRenderNode` | 理论可行 | 渲染器全部重写 |

**最终选择：保留 CPU 读回**（硬解 3.3ms/帧，60fps 余量 5 倍）。

---

## 九、学到什么

1. **D3D11 一个设备只有一个即时上下文**，这是硬约束，不是"加把锁"能绕过的。
2. **"同一个设备"解决纹理归属，不解决并发提交**。这两件事经常被混为一谈。
3. **TDR 不是崩溃，是驱动主动重置**——现象是"画面停在第一帧 + Device loss 日志"。
4. **先量收益再动手**：省 2ms 听起来诱人，但 60fps 预算 16.7ms，本来就有 5 倍余量。
5. **框架给你的插口是有所有权边界的**：Qt RHI 拥有设备，就轮不到我们往里插命令。

---

## 十、一句话总结

```
零拷贝失败不是因为 GPU 慢，也不是驱动烂，
而是 D3D11 的"一设备一队列"模型撞上 Qt RHI 的"设备归我管"，
两个所有权无法共存 —— 谁先想到绕过它，就得先重写渲染器。
```
