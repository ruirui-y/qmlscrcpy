# 一帧到底画了什么：Qt 场景图与 D3D11 状态

## 一、背景

> 这篇分析的是 D3D11 的模型。项目最终没在 D3D11 上解决，而是换了 D3D12，
> 见 [D3D12迁移](../03-视频与解码/D3D12迁移.md) 与 [零拷贝为什么失败](零拷贝为什么失败.md)。

零拷贝在 D3D11 上撞出 TDR 之后，问题就从"API 怎么调"变成了"Qt 画一帧的时候到底在干什么"。

一开始以为是跨线程抢上下文，可把 blit 挪到渲染线程照样崩；换线程救不了，说明坏掉的是状态本身，不是线程。

那就得弄清两件事：一帧里 Qt 改几次状态、它凭什么敢跳过重复的 Set。这篇从"一秒画多少帧"这种最笨的问题一路问到"我们 blit 一下为什么整个窗口花屏"。

## 二、正文

这篇回答五个具体问题：

```
① 一秒到底画多少帧？三个窗口是同时画还是各画各的？
② 一个窗口一帧有多少次 draw？
③ 这些 draw 是不是按顺序、每帧都改状态？
④ 状态缓存到底省了什么？跨帧有用吗？
⑤ 为什么我们自己调的 VideoProcessorBlt 会"改坏 Qt 的状态"？
```

## 三、一秒画多少帧

### 每个窗口独立计帧

```
屏幕 60Hz  → 一个窗口最多 60 帧/秒
屏幕 120Hz → 一个窗口最多 120 帧/秒

三个窗口都显示：
   视频窗口  60 帧/秒
   主窗口    60 帧/秒（内容不变也重画）
   设置窗口  60 帧/秒（同上）
   ────────────────────
   合计 180 帧/秒，但分属三个窗口
```

### "内容没变也要重画"

Qt Quick 不保存画面像素（除非显式开 `layer.enabled` 把静态内容烘成纹理），
每一帧都从头遍历场景图重画。

### 三个窗口不是"同时画"

```
同一 vsync 周期内：三个窗口各自录命令，依次提交
GPU 只有一条执行队列 → 实际是一个窗口一个窗口地执行
```

## 四、一个窗口一帧有多少次 draw

以投屏窗为例（估算，可用 `QSG_RENDERER_DEBUG=render` 或 RenderDoc 实测）：

| 部分 | 元素数 | 每元素 draw | 小计 |
|---|---|---|---|
| 视频矩形（我们的 item） | 1 | 1 | 1 |
| 右侧工具栏 12 个按钮 | 12 | 背景 + 文字/图标 ≈ 2~3 | 24~36 |
| 顶部标题栏文字 | 4 段 | 每段若干字形 | 10~20 |
| 边框 / 圆角 / 分隔线 | 6~8 | 1~2 | 8~16 |
| 滚动条 / 阴影 / 状态提示 | 3~5 | 1~2 | 5~10 |
| **合计** | | | **50~85** |

```
60 帧/秒 × 70 次 ≈ 4200 次 draw/秒
```

**视频只是其中 1 次**，剩下 50~80 次是工具栏、文字、边框。

## 五、绘制顺序

Qt 会排序，但**不完全是 QML 里写的顺序**：

```
① 不透明元素先画（按材质分组，尽量合批）
② 半透明/混合元素后画（按 z 序）
③ 同材质的连续元素合批（字体图集、图标图集）
```

大方向：先远后近、先不透明后透明，为了合批会微调顺序。

## 六、D3D11 的状态分两层（关键）

| 层级 | 有哪些 | 多久设一次 | 和元素有关吗 |
|---|---|---|---|
| **Pass 级** | 渲染目标 RTV/DSV、viewport、scissor | 一轮一次 | ❌ 整窗共享 |
| **Draw 级** | 管线（着色器 + 混合 + 光栅）、纹理绑定 SRB、顶点缓冲、常量缓冲 | 每次 draw | ✅ 各不相同 |

- "viewport"是**渲染目标尺寸**，整窗一个值，不是每个元素的大小；
- 元素大小写在**顶点坐标**里，不需要改状态。

## 七、state cache 到底省了什么

### 概念：账本 ≠ 真相

```
真相：D3D11 上下文里那份唯一的状态（谁都能改）
账本：Qt RHI 记着"当前是什么"（只用来判断能不能跳过 Set）
```

Qt 每次 draw 前对比：

```
要用 的值 == 账本里的值 → 跳过 Set（省调用）
要用 的值 != 账本里的值 → Set，并更新账本
```

### 一帧内的收益（主要在这）

```
85 次 draw，不缓存大约 85 × 12 ≈ 1000 条命令
有缓存：只在材质/纹理变化时 Set ≈ 250 条命令
```

典型命中场景：

```
20 个字形共用一张字体图集 → 第 1 个 Set，后 19 个全部命中
12 个按钮共用同一圆角材质 → 同理
```

### 跨帧的收益（有限）

```
一帧结束后上下文状态还在
下一帧：
   RTV / viewport → Qt 在 beginPass 时必定重设（跨帧不用缓存）
   pipeline 对象  → 复用，不重建（省的是对象创建，不是 Set）
```

**结论：state cache 的价值 90% 在帧内，跨帧主要是对象复用。**

## 八、为什么我们的 `VideoProcessorBlt` 会改坏 Qt 的状态

### 状态不属于 Qt，属于 D3D11 上下文

```
ID3D11DeviceContext（整个进程唯一）
   ┌──────────────────────────────┐
   │ 当前 RTV      = ？            │ ← 真实值，谁都能改
   │ 当前 viewport = ？            │
   │ 当前 pipeline = ？            │
   └──────────────────────────────┘
        ↑                 ↑
     Qt RHI 读写      我们的代码写
```

类比：

```
白板写着"当前用红笔"（= 上下文状态）
Qt 账本记着"红笔"    （= RHI 的缓存）
我们把白板改成"蓝笔" （= VideoProcessorBlt）
Qt 继续按账本用红笔  → 后面画的全都错
```

### VideoProcessorBlt 不是纯计算，它是一次内部绘制

```
① 把输出视图（我们的 BGRA 纹理）绑成 render target   ← 改 RTV（Pass 级）
② 把 viewport 设成输出尺寸                          ← 改 viewport（Pass 级）
③ 用驱动内置着色器画一个全屏面（NV12 → BGRA）
④ 返回，不还原
```

这是 D3D11 视频处理器的常规行为，文档没有承诺还原。

### 一帧里的时间线（伤害可视化）

```
beginPass（Qt 设 RTV = 窗口目标，viewport = 窗口尺寸）
   │
   ├─ draw 1~4    标题栏
   ├─ draw 5      ← 我们的 VideoItem，render() 被调用
   │                 VideoProcessorBlt 执行 → RTV 被换成我们的纹理
   │
   ├─ draw 6~85   工具栏、按钮、文字
   │                 全部画到我们的纹理上 / 视口错位
   │
endPass
   ↓
现象：视频正常（画进了自己的纹理），工具栏消失或花屏
严重时：GPU 收到非法状态 → 驱动重置设备（TDR）
```

日志原文（`exp/zero-copy` 分支实测）：

```
[decode] 首帧格式 172（D3D11 = 172）
Device loss detected in Present()
Graphics device lost, cleaning up scenegraph and releasing RHI
```

### 为什么换线程没用

```
问题不是"两个线程同时改"
而是"Qt 的账本和 GPU 的真相不一致"
同线程只保证没有数据竞争，不保证账本正确
```

## 九、三个解法

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A 保存/恢复** | blit 前后 Get/Set RTV + viewport + scissor | 10~15 行 | 中：可能还有别的状态被动过 |
| **B 挪出 pass** | 在 `endFrame` 之后做 blit，下一帧再画 | 延迟 +1 帧 | 低：完全不碰 Qt 的 pass |
| **C 换 D3D12/Vulkan** | 状态烘进 pipeline，无全局可变状态 | FFmpeg 7.0+、渲染器重写 | 高成本，根治 |
| **D 读回内存（现状）** | 不碰 GPU 状态 | 每帧 2~3ms | 无 |

恢复清单（方案 A）：

```
必须恢复（Pass 级）：
   OMGetRenderTargets → OMSetRenderTargets
   RSGetViewports     → RSSetViewports
   RSGetScissorRects  → RSSetScissorRects

不用管（Draw 级）：
   纹理、管线、顶点缓冲 —— Qt 每次 draw 都会重设
```

## 十、自测五问

**Q1** 一帧 85 次 draw，是不是要改 85 次状态？

```
A：不是。只有"要的值和账本不一致"时才 Set；连续同材质会命中跳过。
```

**Q2** 100 个图标是不是 100 张纹理轮换？

```
A：不一定。通常拼成一张图集，100 个图标只改 UV，不改绑定。
```

**Q3** 跨帧缓存有什么价值？

```
A：主要是复用 pipeline/纹理对象，省对象创建；状态本身 beginPass 会重设。
```

**Q4** 我们的 blit 改的是 Draw 级还是 Pass 级状态？

```
A：Pass 级（RTV、viewport），这是最不能动的一层。
```

**Q5** 窗口里只有视频、没有工具栏，还会崩吗？

```
A：伤害小很多（后面没有 draw 用错状态），但 endPass 时状态不匹配仍可能报错。
```

## 十一、追问：能不能让它不改状态？Qt 那时在干什么？

### 为什么一定会改

```
VideoProcessorBlt(processor, output_view, ...)
   内部：
   ① 把 output_view 的纹理绑成 render target   ← Pass 级状态
   ② viewport / scissor 设成输出尺寸            ← Pass 级状态
   ③ 用驱动内置着色器 + 视频固定功能单元画全屏面
   ④ 返回，不还原
```

根因是 D3D11 的状态模型：

| API | 状态模型 | 能否隔离 |
|---|---|---|
| OpenGL | 状态机 | 可以 `glPushAttrib`（慢） |
| **D3D11** | 全局一份 | **没有 save/restore API** |
| D3D12 | 状态烘进 pipeline | 没有全局可变状态 |

### 四条规避路线

| 路 | 做法 | 改谁的上下文 | 代价 |
|---|---|---|---|
| ① 保存/恢复 | `OMGetRenderTargets` / `RSGetViewports` → blit → Set 回 | Qt 的（临时） | 10~15 行，可能漏状态 |
| ② 挪到帧外 | `endFrame` 之后再做 blit | Qt 的（但本帧已结束） | 延迟 +1 帧 |
| ③ 独立设备 | 自己的设备转色，共享纹理给 Qt | 自己的 | Qt `createFrom` 只支持同设备 |
| ④ Deferred Context | 录进命令列表再执行 | 执行时仍是 Qt 的 | 顺序可控，仍要恢复 |

**结论：没有"完全不碰状态"的路，只有"改完还回去"或"趁 Qt 不用时改"。**

### 我们的 blit 在一帧的哪个位置

```
beginFrame()
   ↓
beginPass(主 render target)        ← 设 RTV / viewport
   ↓
遍历场景图
   ├─ 画标题栏
   ├─ 画背景
   ├─ ★ VideoItem → 我们的 render(cb)
   │        ConvertNativeFrame() 在这里执行  ← pass 还开着
   ├─ 画工具栏（50+ 次 draw，全用被改过的状态）
   ├─ 画文字
   ↓
endPass()
   ↓
endFrame()
```

**答案：Qt 已经开始画这一帧了，我们是在一帧的正中间动手。**

### 方案②为什么安全

```
endFrame() 之后（Qt 不再录命令）
   ↓
我们做 blit
   ↓
下一帧 beginFrame() → beginPass() 重设 RTV / viewport
   ↓
Qt 从干净状态开始 ✅
```

代价：转换结果下一帧才用 → 画面 +1 帧延迟。

### 推荐顺序

| 顺序 | 方案 | 风险 | 延迟 |
|---|---|---|---|
| 1 | 保存/恢复 | 中 | 无 |
| 2 | 挪到帧后 | 低 | +1 帧 |
| 3 | 独立设备 | 高 | 无 |
| 4 | 换 D3D12/Vulkan | 高 | 无 |

---

```
一帧不是一个 draw，是几十上百个 draw 共用一条 GPU 状态；
Qt 靠账本跳过重复的 Set，靠合批省命令；
我们的 VideoProcessorBlt 在 pass 中间把 Pass 级状态改掉，账本立刻失效，
后面所有 draw 全画错 —— 这才是零拷贝在 D3D11 上走不通的真正原因。
```
