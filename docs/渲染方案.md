# 渲染方案

结论先给：**用 `QQuickFramebufferObject`，在 `Renderer::render()` 里画**。这是 Qt5 里唯一"GL 上下文保证当前"的自定义渲染入口。

## 三条路

| 方案 | 做法 | 代价 | 谁在用 |
|---|---|---|---|
| A 自己开窗口 | 拿 HWND 建交换链，直接 Present | 窗口/事件/DPI/输入全自己写 | scrcpy（SDL）、Player 项目（D3D11） |
| B Qt Quick + FBO | `render()` 里画进 FBO，Qt 合成 | 多一次 GPU blit + 一次平面拷贝 | 本项目 |
| C Qt Quick + 自定义材质 | 往场景图里塞纹理和材质 | 省掉 FBO blit，但 GL 时机不受控 | 试过，崩了五次 |

## 为什么不是 A

A 是最直接的：一个窗口句柄 + 一个交换链 + 两个着色器就够了。Player 项目就是这么干的（`D3D11Pipeline::Execute` → `Draw(3,0)` → `Present`），全程在一个线程里，没有 FBO，没有合成器。

但我们用的是 Qt Quick：窗口、GL 上下文、事件循环都归它。要在它管理的窗口上再挂一个自己的交换链，等于两套合成打架。走 A 就得把投屏窗从 QML 降级成原生窗口，窗口管理、拖拽、DPI、输入全部自己重写。

**现在多花的成本约 1 ms/帧，换来的是窗口管理白拿。** 60fps 预算 16.7ms，解码已占 5.6ms，这 1ms 不值得省。

## 为什么不是 C（踩坑记录）

自定义 `QSGNode` + 材质理论上最快，但 Qt 对"在场景图里自己播 GL"的容忍度极低：

| 尝试 | 结果 |
|---|---|
| `QSGSimpleTextureNode` 每帧换纹理 | 崩：材质被渲染器缓存，纹理被自己删了，`bind()` 野指针 |
| 材质持有 AVFrame 跨帧 | 崩：断开连接时帧活过解码器，`shared_ptr` 析构 use-after-free |
| 在 `updatePaintNode` 里 `glTexSubImage2D` | 崩：那里的上下文状态不保证 |
| 自管 GLuint + `updateTexture` 上传 | 绿屏 + 崩 |

共同点：**GL 调用的时机不对**。`updatePaintNode` 是"同步阶段"，不是渲染阶段。

## B 的正确姿势

```cpp
class VideoItem : public QQuickFramebufferObject
{
    Renderer *createRenderer() const override;   // 返回自己的 Renderer
};

class YuvRenderer : public QQuickFramebufferObject::Renderer
{
    void synchronize(QQuickFramebufferObject *item) override;   // 渲染线程，无 GL
    void render() override;                                     // 渲染线程，GL 当前
};
```

两个回调的分工：

- `synchronize()`：把 GUI/视频线程那边的数据搬过来（拷三平面），**不能调 GL**
- `render()`：建纹理、上传、画——**所有 GL 都在这儿**

另外两条硬性要求：

```cpp
// ① 用完要把 GL 状态还回去，否则 Qt 接着画自己的东西时会出错
glActiveTexture(GL_TEXTURE0);
glPixelStorei(GL_UNPACK_ALIGNMENT, 4);

// ② v 轴要反向：FBO 的 y 朝上
//    顶点用 v=1 放顶部，否则整幅画面上下颠倒
```

这两条都踩过：状态没还原导致标题栏文字糊成一团，v 轴没反向导致画面上下颠倒。

## 每秒一行链路统计

默认每秒打一行（`QS_PERF=0` 关掉）。只留四个数，都是实测的墙钟时间：

```
[perf] 79 轮：GUI 排队 0.09 ms | 取帧 0.42 ms | 画一帧 0.63 ms | 两轮间隔 12.7 ms
```

| 字段 | 量的代码 | 怎么读 |
|---|---|---|
| `轮数` | `synchronize` 调用次数 | 这一秒渲染了几轮，也是四个数的分母 |
| `GUI 排队` | 视频线程投递 → GUI 线程开始执行 | 大 = GUI 线程被别的事堵住了；正常在 0.1ms 量级 |
| `取帧` | `synchronize()` 全程 | 只跟分辨率有关，稳定；突然变大说明在等锁 |
| `画一帧` | `render()` 全程 | 含上传三平面 + 画 quad；首次建纹理那一次会明显偏大 |
| `两轮间隔` | 本轮 `synchronize` 开始 − 上一轮开始 | 渲染线程的节奏；超过 1 秒的空闲不计入 |

定位顺序：

```
两轮间隔 12.7ms - 取帧 0.42 - 画一帧 0.63 = 11.6ms   → 这段是 Qt 的交换缓冲 + 等唤醒，不在我们代码里
GUI 排队 0.1ms                                      → GUI 线程没被堵
两轮间隔明显大于 16.7ms                              → 渲染线程被限流，掉帧是正常的，不是处理不过来
```

### 重绘什么时候发生（P13 改过）

```cpp
// 改前：8ms 定时器轮询，120fps 时帧成批落在两个 tick 之间被覆盖
OnRefreshTimer() { if (arrived != painted) update(); }

// 改后：Present 里逐帧投递，GUI 线程执行
QMetaObject::invokeMethod(this, [this]() { update(); }, Qt::QueuedConnection);
```

定时器只留"尺寸变化通知 + 兜底统计"。

视频线程不能直接调 `update()`（`QQuickItem` 归 GUI 线程），所以用 `invokeMethod(..., Qt::QueuedConnection)` 投递——这是唯一线程安全的做法。

**实测数据（1264×2776，120Hz 屏）**

| 指标 | 有线 | 无线 |
|---|---|---|
| 入队到上屏 平均 | 3.3~4.6ms | 3.6~4.5ms |
| 入队到上屏 最大 | 6~7ms | 6~8ms |
| 解码 | 3.7~6.6ms | 3.7~7.0ms |
| 上屏（纹理上传） | 0.4ms | 0.4~0.5ms |

两条链路基本一样 → **渲染和"我们这侧"都不是瓶颈**。

### 曾经想用 PTS 算传输积压，失败了

思路：设备包头里的 PTS 是它出帧的时刻，`现在 - PTS` 就是"这一帧在路上排了多久"。试了两版：

1. 直接相减 —— 设备的单调钟和本机不同源，差一个固定偏移，绝对值无意义
2. 第一帧记基准 `offset = now - pts`，之后算 `now - pts - offset` —— 理论上只剩"相对增长"

实测这个值恒为 0，而且打出来的 `offset` 每秒都在变（-79841481894 → -79841469020 → -79841419842），说明基准没固定住，数字不可信。**与其留一个看不懂的假指标，不如删掉。**

替代方案是 `入队到上屏`：从帧进入我们进程到真正上屏，全在本进程的同一个单调钟里，跨机器比较也成立。

## 换分辨率必须重建纹理

`render()` 里建纹理时，第一版只判断"纹理是不是 0"：

```cpp
if (textures_[i] == 0) { /* 建纹理 */ }
```

横竖屏切换时帧尺寸从 1264×2776 变成 2776×1264，纹理还是旧尺寸，`glTexSubImage2D` 拿新尺寸往旧纹理里写 → 越界，画面直接卡住（只有返回竖屏才恢复，因为那时尺寸又匹配了）。

现在每张纹理记住自己当前的尺寸，变了就删掉重建：

```cpp
const bool size_changed = texture_sizes_[i] != QSize(widths_[i], heights_[i]);
if (textures_[i] == 0 || size_changed) { /* 删旧建新 */ texture_sizes_[i] = ...; }
```

同时投屏窗在检测到帧宽高比翻转（`|aspect - lastAspect| > 0.05`）时，按新比例调整窗口大小，全屏视频不会缩在一条缝里。

## 三平面着色器

```
纹理 0：Y 平面（GL_LUMINANCE，全尺寸）      采样 .r
纹理 1：U 平面（半尺寸）                     采样 .r
纹理 2：V 平面（半尺寸）                     采样 .r
        │
        ▼
BT.601 有限范围矩阵（Android 屏幕采集默认）：
    y -= 0.0625     u -= 0.5     v -= 0.5
    R = 1.164y + 1.596v
    G = 1.164y - 0.391u - 0.813v
    B = 1.164y + 2.018u
```

如果颜色偏（发灰/发绿），先换 BT.709 再排查。

## 缩放与清晰度

窗口尺寸决定清晰度：

```
窗口比帧小 → 缩小，清晰（只是有点软）
窗口比帧大 → 放大，糊
```

所以首次连上时按帧的物理像素定窗口大小（`frameSize / devicePixelRatio`），再用屏幕可用区域封顶。用户手动调过之后记进 `userdata.ini`，下次照原样恢复。

采集分辨率用原生（`max_size=0`，1264×2776）。之前用 720（328×720）拉到全屏窗口，插值放大，字全是糊的。

```
[perf] fps 61 等数据 6.5 ms 解码 5.6 ms 转换 0 ms 上屏 0.4 ms
```

`转换 0 ms` 是因为 RGB 转换搬到 GPU 了；之前 CPU 版这里是 6.4 ms。
## 渲染循环用 windows 模式（P24）

Qt 在 Windows 上有三种渲染循环，用 `QSG_RENDER_LOOP` 选。实测同样条件下客户端总延迟：

| 模式 | `update` → 处理重绘 | 一帧到上屏（中位 / 90 分位） |
|---|---|---|
| `threaded`（默认） | 5.11ms | 7.08 / 7.83 ms |
| `basic` | 5.02ms | 7ms 量级 |
| **`windows`** | 不产生该事件 | **3.78 / 4.62 ms** |

`windows` 循环不用 `QEvent::UpdateRequest` 那条路，改用 Windows 消息/定时器直接驱动渲染，省掉约 5ms 的调度等待。代码在 `main.cpp` 的 `PrepareSurfaceFormat()` 里，必须在 `QGuiApplication` 构造之前生效。

排查全过程见 [渲染延迟](渲染延迟.md)。
