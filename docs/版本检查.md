# 版本检查（零服务器方案）

客户端启动时取一个静态 `latest.json`，比一下版本，有新版就在主窗右上角亮红标。

**不需要服务器、不需要数据库、不需要常驻进程**——那个 JSON 就是全部"后端"。

## 1. 三条链路

```
仓库里的 latest.json
   │
   ├─ Gitee raw        https://gitee.com/bai-maxifeng/qmlscrcpy/raw/master/latest.json
   ├─ jsDelivr CDN     https://cdn.jsdelivr.net/gh/ruirui-y/qmlscrcpy@master/latest.json
   └─ GitHub raw       https://raw.githubusercontent.com/ruirui-y/qmlscrcpy/master/latest.json
            │
            ▼
      客户端启动时依次尝试（谁先成功用谁）
            │
            ▼
      比版本 → 主窗红标：新版 0.1.5 / 必须更新 0.1.5
```

**为什么 Gitee 排第一**：实测这台机器直连 GitHub 和 jsDelivr 都是 000（超时/被拦），Gitee 正常——国内环境必须有国内源。

**Gitee 仓库必须是公开的**：私有仓库的 `raw` 对匿名访问返回 404，客户端会一路退到 GitHub/CDN，国内用户就永远收不到更新提示。

顺序不是随便定的：

1. **Gitee**：国内直连最稳
2. **jsDelivr**：读 GitHub 仓库但走 CDN，国外快
3. **GitHub raw**：兜底

三个都失败就静默跳过，**不影响正常使用**。

## 2. latest.json 长什么样

放在仓库根目录：

```json
{
  "latest": "0.1.5",
  "minimum": "0.1.0",
  "url": "https://github.com/ruirui-y/qmlscrcpy/releases/latest",
  "notes": "修复拖动卡顿",
  "published_at": "2026-11-13"
}
```

| 字段 | 作用 |
|---|---|
| `latest` | 最新版本号，和本地版本比 |
| `minimum` | 最低可用版本；本地低于它就"必须更新" |
| `url` | 点红标打开的下载页（可以换成网盘链接） |
| `notes` | 悬停提示里显示的一句话 |

## 3. 客户端怎么知道自己是哪个版本

编译期就定死了，**不联网也知道**：

```cmake
project(QmlScrcpy VERSION 0.1.5 ...)          # 改这里
```

```cpp
// CMakeLists.txt
QS_APP_VERSION="${PROJECT_VERSION}"
```

```cpp
// src/main.cpp
qsc::UpdateChecker update_checker(QStringLiteral(QS_APP_VERSION));   // 0.1.5 就此进入二进制
```

## 4. 比较规则

`libs/update/version_compare.*`，纯逻辑、可单测：

- 只认 `x.y.z` 三段，`-beta` / `+build` 后缀丢掉
- **按数字比，不按字符串比**（`0.10 > 0.9`）
- 解析失败一律当 `0.0.0`：远端给错格式时，本地会被判为更新，**不会把用户拦在旧版本上**

三态：

```
本地 < minimum  →  updateRequired = true   红色「必须更新 0.1.5」
本地 < latest   →  updateAvailable = true  橙色「新版 0.1.5」
本地 >= latest  →  什么都不显示
```

## 5. 为什么失败了也不报错

版本检查是**锦上添花**，不能因为拿不到 JSON 就打不开软件：

- 5~6 秒超时，超时换下一个源
- 全部失败只写一行 info 日志
- 不重试、不弹窗、不阻塞启动

## 6. TLS 的坑：Qt 5.15 不带 OpenSSL

Qt 5.15 在 Windows 上走 OpenSSL，而这套 Qt 安装里**没有 `libssl-1_1-x64.dll`**，直接报：

```
[update] 检查更新失败（不影响使用）: "TLS initialization failed"
```

解法是两级：

```cpp
if (!QSslSocket::supportsSsl())
{
    // 退到系统自带的 curl.exe（Win10 1803+，用 SChannel）
    AttemptWithCurl(url);
    return;
}
```

`curl.exe` 走系统 TLS，不依赖 OpenSSL，效果一样。代价是多一个进程，但只在启动时跑一次。

## 7. 换源 / 自建

`config.ini` 里可以覆盖：

```ini
[update]
url=https://你的域名/latest.json
```

配了它就不再走内置的源列表。想换成自己服务器、对象存储、甚至网盘直链都行——**客户端只认这个 JSON 的格式**。

## 8. Gitee 不会自动同步 GitHub

Gitee 的「导入 GitHub 仓库」是**一次性导入**，之后 GitHub 的新提交不会自动过去（自动镜像要钱）。

两个办法：

| 办法 | 操作 |
|---|---|
| 手动刷新仓库 | Gitee 仓库页 → 管理 → 仓库镜像管理 → 手动更新 |
| 只维护 latest.json | 每次发版直接在 Gitee 网页上编辑这个文件，一分钟 |

**推荐第二个**：版本检查只读 `latest.json`，代码以 GitHub 为准，不必追求两个仓库代码完全一致。

## 9. 发版流程（多一步）

```
① 改 CMakeLists 的 project(... VERSION 0.1.5)
② collect.ps1 → build_installer.bat
③ 改 latest.json 的 latest / notes / url → git push
④ git tag + gh release create
```

**最容易忘的是第 ③ 步**：忘了改 `latest.json`，用户就永远收不到更新提示。

## 10. 为什么不做"踢下线"

一开始想的是"服务端发现版本太旧就把连接踢掉"。问题：

- 客户只在**启动时**连一次版本接口，之后就没有连接可踢
- 真要踢就得保持长连接或者定时轮询，那就不是一个静态文件的事了

所以做成客户端自己判断：`minimum` 决定硬拦，`latest` 决定软提示。**控制权在客户端，服务端只提供数据**——这也正是静态文件方案能成立的原因。


链路验证（把 `latest.json` 临时放到本地、用 `update/url` 指过去）：

```

```

主窗右上角出现橙色「新版 0.1.5」，悬停显示备注，点击开浏览器。
