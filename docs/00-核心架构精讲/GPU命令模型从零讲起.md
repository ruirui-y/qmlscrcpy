## 一、颠覆直觉的事实：CPU 从来不画图

写 `DrawInstanced(3, 1, 0, 0)` 这行代码的时候，**GPU 什么都不知道**。这行代码没有触发
任何绘制，它只是往一块内存里写了几条指令字节——像在纸上抄了一条作业。

CPU 和 GPU 是两台各自狂奔的机器，中间隔着驱动和硬件调度器。CPU 唯一能让 GPU 干活的方式：

> **把写好的"作业清单"扔进一个队列，GPU 自己按顺序取着做。**

整个 D3D12 编程模型就围绕这个"异步工厂"展开：录单（CPU）→ 派活（交队列）→
干完拉铃（围栏）。理解了这一点，后面所有概念都是水到渠成。

## 二、三个对象 = 一张工单的一生

`d3d12_nv12_convert.cpp::PrepareQueue()` 建厂时一次性建好的四个对象：

```cpp
d.queue      // ID3D12CommandQueue        「传送带」：GPU 的作业通道，按先进先出执行
d.allocator  // ID3D12CommandAllocator    「工单纸仓库」：给工单分配内存
d.list       // ID3D12GraphicsCommandList 「工单本身」：往里录指令的地方
d.fence      // ID3D12Fence               「出餐铃」：GPU 干完了把计数器拨一格
```

| 对象 | 类比 | 真实身份 |
|---|---|---|
| CommandList | 订单单据 | 一块内存，顺序写入指令（Barrier、Draw、状态切换…） |
| CommandAllocator | 单据纸仓库 | 工单占的内存从它这批发 |
| CommandQueue | 后厨传送带 | GPU 前面的 FIFO 队列，放上去的单子按序执行 |
| Fence | 出餐铃 | 共享内存里的计数器，GPU 完成后亲手拨 |

**关键点：往 CommandList 里"录命令"的全程，GPU 完全无感。** 录 100 条 Draw 也毫无发生。
GPU 开始干活只发生在一个动作上：

```cpp
ID3D12CommandList *lists[] = {d.list.Get()};
d.queue->ExecuteCommandLists(1, lists);   // ← 全 D3D12 唯一真正"派活"的调用
```

`Convert()` 每帧干的事翻译成人话——**异步工厂的完整生产周期**：

```cpp
d.allocator->Reset();                    // 撕一张新单
d.list->Reset(allocator, pipeline_);     // 单据清空

// 第一段：往单子上抄指令（此刻 GPU 仍然什么都不知道）
d.list->ResourceBarrier(2, barriers);    // "画之前把两块显存的用途开关拨一下"
d.list->OMSetRenderTargets(...);         // "画到 rgba_texture_ 这张画纸上"
d.list->DrawInstanced(3, 1, 0, 0);       // "画一个三角形做颜色转换"
d.list->ResourceBarrier(2, barriers);    // "画完把开关拨回去"
d.list->Close();                         // ← 封单！这之后不能再往里写

// 第二段：派活 + 确认干完了
d.queue->Wait(decode_fence, ...);        // （可选）"这张单子排在解码完成之后再执行"
d.queue->ExecuteCommandLists(1, lists);  // ★ 此刻 GPU 才真正开始画
WaitFence();                             // CPU 睡觉，等出餐铃响（~0.17ms）
```

为什么最后要 CPU 等一下？**不是 GPU 需要等，是下一个人要等**——下一步（Qt 采样这张纹理）必须等 RGBA 真的画完才能开始。等待的本质是"给下一个人挡门"。

## 三、多队列不是排队，是并行

直觉误区："GPU 从两条队列拿活，先拿谁先执行谁，不就自然同步了？"

**恰恰相反——多队列存在的意义就是并行。** GPU 芯片里有多个独立的执行引擎，
每条队列（通常）喂给一个引擎，多条队列的活真正同时跑：

```
CPU                                    GPU 芯片内部
Qt 队列 ────── 工单 ──────┐
                         ├──→  ┌─────────────────┐
转色队列 ────── 工单  ─────┘     │ 3D 引擎（画图）   │ ← 两条队列的单子
                               │ 计算/复制引擎     │    可以同时在不同
FFmpeg 解码队列 ── 工单 ──→      │ 视频解码引擎      │    引擎上执行
                               └─────────────────┘
```

顺序保证的分界线，一句话记牢：

> **队列内有序是免费的（FIFO）；队列之间无序是设计使然（并行才是目的）；
> 想要跨队列顺序，必须显式申请。**

几个推论，全部在本项目里得到印证：

1. **队列是软件对象，引擎是硬件资源**——谁调 `CreateCommandQueue` 谁就有一条
   （本项目一个进程就有 3 条：Qt 隐藏的一条、转色器一条、FFmpeg 内部一条）。
   少数几个引擎会被 N 条队列共享，GPU 硬件调度器负责分时/并行/抢占。
2. **队列里只有指令**。纹理不在任何队列里——它是显存里的一块内存，工单里的指令
   只是引用它的地址。
3. **`queue->Wait` 的存在本身就是"跨队列无序"的官方承认**——如果天然有序，
   这个 API 就不需要存在（见 `Convert()` 里的解码围栏兜底）。

## 四、围栏：一块单写多读的记牌器

**fence（`ID3D12Fence*`）** 是 CPU/GPU 共享内存里的一块 64 位计数器，餐厅叫号屏：

| 概念 | 是什么 | 会变吗 |
|---|---|---|
| `fence_value`（预期值） | 提货单上印死的号码，随帧派发 | **永远不变**，第 105 帧就是 105 |
| `fence->GetCompletedValue()`（当前值） | 计分牌本身 | GPU 每完成一帧 Signal 一次：0 → 1 → 2 → … |

设计成"单写多读"是有讲究的——CPU 和 GPU 是两台机器，普通内存两边写会乱，围栏的约定是：

- **只有 GPU 能写**（Signal 指令是唯一合法的拨牌动作，单调递增不回退）
- **CPU 和 GPU 都能读**（同一块共享内存的映射视图，读无竞争）

单写多读 = 天然无锁的进度广播，这就是它能当跨机器"叫号屏"的全部原理。

**每个生产者一个围栏，号码互不相干**（这不是协议强制，是惯例）：

```
记牌器 A（FFmpeg 的）                记牌器 B（转色器自己的 d.fence）
生产者：FFmpeg 解码队列               生产者：转色队列
计数含义：解完了几帧                  计数含义：提交了几次转色（++d.fence_value）
读者：解码线程 CPU + 转色队列闸门      读者：渲染线程 CPU（WaitFence）
```

两个记牌器的号码**永远不互相比较**——各自单调递增，各自闭环。

## 五、三种等待的精确区别

本项目一帧里出现过三种等待，只有两种阻塞 CPU：

| # | 代码位置 | 谁在等 | 等什么 | 阻塞谁 |
|---|---|---|---|---|
| 1 | `WaitForDecodeFence`（解码线程） | **CPU** | FFmpeg 解码围栏 → 目标值 | CPU 睡觉（最多 50ms） |
| 2 | `d.queue->Wait(decode_fence, value)`（Convert 里） | **GPU**（转色队列前端） | 同一个解码围栏 → 同一个目标值 | **CPU 立即返回，零阻塞**；卡住的是队列本身 |
| 3 | `WaitFence`（渲染线程） | **CPU** | 自己的转色围栏 → `++fence_value` | CPU 睡觉（~0.17ms） |

### 等待 2 的机制：不是"等"，是"在流水线上扎一道闸门"

```cpp
if (fence->GetCompletedValue() < decode_fence_value) {   // 读【当前值】只为判断要不要插闸门
    d.queue->Wait(fence, decode_fence_value);            // 传入【预期目标值】
}
```

```
转色队列的 FIFO：
┌────────────┐   ┌─────────────┐   ┌──────────────────────┐
│ 闸门标记    │ → │ 转色工单      │ → │ Signal(++fence_value)│
│ Wait(围栏,  │   │ barrier→draw│   │ 干完拨自己的计分牌      │
│ 目标值)     │   │ →barrier    │   │                      │
└────────────┘   └─────────────┘   └──────────────────────┘
     ↑
  GPU 执行到这里【自己停下】，定期看解码围栏计分牌，≥ 目标值才放行后面的工单 —— CPU 早就返回干别的了
```

两种等待方式对照：

| 方式 | 用在谁身上 | 机制 |
|---|---|---|
| `SetEventOnCompletion` + `WaitForSingleObject`（等待 1、3） | **CPU** 等 | CPU 看不见 GPU 内部进度，靠内核事件被叫醒（0% CPU） |
| `queue->Wait`（等待 2） | **GPU 队列**等 | 闸门直接扎进流水线，GPU 前端执行到这条时自己盯计分牌 |

### 为什么 1 敢设 50ms 超时、3 却敢写 `INFINITE`

- 等待 3 等的是**自己刚提交的工单**：队列里只有自己的命令，必然完成——写 `INFINITE`
  省掉超时分支（真等不到说明设备已经出大事，那不是代码能救的）。
- 等待 1 等的是**别人（FFmpeg）的围栏**：万一驱动异常解不出来，死等会把解码线程钉死。
  50ms 兜底提前放行，这一帧就算有瑕疵也会被 Present 的单槽覆盖自然丢掉——
  **等不到就丢弃，比死等好。**

## 六、账本：资源状态的所有权

GPU 显存是公共仓库，但每个框架（QRhi、FFmpeg）手里各有一本**私有登记簿**，登记的不是内存本身，而是"这个资源的用途约定和当前状态"。

### 账本怎么工作

```cpp
// rgba_texture_ —— QRhi 亲手创建（EnsureRgbaPipeline 里）
rgba_texture_.reset(rhi()->newTexture(QRhiTexture::RGBA8, size, ...));
rgba_texture_->create();
// → 出生即在账本：格式、尺寸、用途（可采样 + 可当渲染目标）全部登记
// → Qt 每帧提交时按账本自动插状态切换

// NV12 纹理 —— FFmpeg 亲手创建（解码池分配）
native->texture    // 裸的 ID3D12Resource*，QRhi 完全不知道它存在
// → 账本上没有它：什么状态、多大、活着没有，QRhi 一概不知
// → 它的状态归 FFmpeg 的约定管（进出都是 COMMON），切换由我们手工 Barrier
```

两块显存在硬件层面**没有任何区别**，区别只有一个：**谁记账，谁负责替你插 Barrier。**

### 借账本上的资源，必须原样归还

`Convert()` 手工 Barrier 拨 `rgba_texture_` 的状态（PSR→RT→PSR），等于在两次 Qt 帧之间
**临时借了账本上的资源**：借走前什么样，还回去必须还是什么样——归还时和账本记录一致，
Qt 下次提交时它的自动 Barrier 依然成立。这就是《精讲》4.2 节"成对切回"的另一半原因：

- NV12 成对切回 = 还给 **FFmpeg 的约定**（COMMON）
- rgba 成对切回 = 还给 **QRhi 的账本**（PSR）

**两块显存，两个账本，各还各的。**

### 为什么 QRhi 创建不了 NV12（即使能也不行）

1. **格式层就不行**：`QRhiTexture::Format` 全是单平面格式（RGBA8/R8/RG8/压缩格式…），
   没有 NV12 这种多平面格式（一个资源、两个 PlaneSlice、两种布局）——QRhi 的抽象里
   没有"平面切片"概念。连 QtMultimedia 放视频都是自己内部专门处理的。
2. **即使绕过也不行**：假设用 R8 + RG8 两张单平面纹理拼，解码器也不认——d3d12va
   必须写进**自己的 DPB 纹理数组**（参考帧管理要求切片稳定存在、由解码器自己复用）。
   走 `AVHWFramesContext` 外部帧池理论可行，但立刻制造"双账本"：
   解码器每帧覆写这块内存、QRhi 同时登记这块内存的状态——**这就是 D3D11 三次实验
   死掉的那个坑，换 QRhi 版本再死一次**。

所以《精讲》第四节那套"海关区"是**结构性必需**：

```
FFmpeg 账本：NV12 数组（COMMON 进出，解码器专用池）      ← 解码器独占
QRhi   账本：rgba_texture_（PSR/RT，自动 Barrier）      ← Qt 独占
                     │
        D3d12Nv12Convert = 海关：
        手工给 NV12 插 Barrier + 手工借还 rgba + 两道围栏同步
```

外来资源必须自带三件套：**Barrier、同步、保活引用**（keep 副单）——Convert 模块干的就是这三件事。

## 七、为什么不能并成一条队列

最自然的疑问：既然跨队列同步这么麻烦，为什么不让转色直接录进 Qt 的 `cb`，
变成同一队列里的相邻段落（FIFO 天然锁死顺序，0.17ms 的 CPU 挡板直接省掉）？

这是"教科书理想方案"，本项目不采纳有三条理由：

| # | 理由 | 说明 |
|---|---|---|
| ① | 纹理所有权卡死 Barrier | Qt 的 cb 只接受 QRhi 托管的资源；NV12 不在账本上，QRhi 不会帮它插 Barrier，也没有 API 对非托管资源手工插原始 Barrier |
| ② | 解码闸门没地方插 | `queue->Wait` 是**队列级**操作，工单（CommandList）内部没有跨队列等待指令——CPU 挡板删掉的同时，最后防线也没了 |
| ③ | 架构隔离 | FFmpeg 的资源永不碰 Qt 队列、Qt 的资源永不碰 FFmpeg 队列，升级/出错时故障面锁死在一个模块里 |

| 方案 | 每帧同步开销 | 控制权 | 评 |
|---|---|---|---|
| 并进 Qt 队列（理想） | ~0 | 依赖 QRhi 抽象 | 双账本冲突 + 闸门丢失 |
| 自建队列（现状） | CPU 挡板 ~0.17ms | 全部自己掌控 | 用过路费买隔离与正确性 |

> 顺带回答"一帧入队几个工单"：**2 个**。所有 QML 元素（包括我们）往 Qt 的同一个 cb
> 里抄，帧末 `endFrame()` 一次 ExecuteCommandLists——一个大工单；转色器自己一单。
> 各在各自的队列上。

## 八、自检题（面试向）

1. **Q：CPU 调用 `DrawInstanced` 后 GPU 何时开始画？**
   A：和调用时刻无关。开始画只发生在 `ExecuteCommandLists` 把整张工单提交进队列之后，
   而且 GPU 真正执行还要看队列排到没排到、引擎忙不忙。

2. **Q：两条队列各提交一个工单，GPU 保证先提交的先执行吗？**
   A：不保证。单队列内 FIFO 免费；跨队列并行是设计使然，顺序必须显式申请——
   CPU 等围栏或 `queue->Wait` 扎闸门。

3. **Q：`queue->Wait(fence, v)` 会阻塞调用它的 CPU 线程吗？**
   A：不会。它只是往队列里插一道闸门标记，CPU 立即返回；卡住的是 GPU 队列前端——
   执行到闸门时自己盯计分牌，≥ v 才放行后续工单。

4. **Q：`fence_value` 和 `GetCompletedValue()` 是同一个东西吗？**
   A：不是。前者是随帧派发、冻结不变的预期号码；后者是计分牌的当前值，只有 GPU 能拨。
   所有等待的本质都是"当前值 ≥ 预期值"。

5. **Q：如果 Qt 开放了"往它的工单中间插队列等待"的接口，本项目哪行代码可以删？**
   A：`WaitFence()` 那行可删，省 ~0.17ms——它存在的唯一原因就是两条队列的接缝处
   只有 CPU 一个公共空间。

6. **Q：为什么解码的 CPU 等待设 50ms 超时、转色的却写 `INFINITE`？**
   A：等自己提交的工单必然完成（INFINITE 省超时分支）；等别人的围栏可能有意外，
   超时放行 + 丢弃比死等好。

## 附：一图流总纲

```
CPU 侧（录单，GPU 无感）              GPU 侧（执行）
                                       
  allocator.Reset() ← 撕新单            
  list.Reset()       ← 单据清空          
  list.Record(...)   ← 抄指令            
  list.Close()       ← 封单              
  queue.ExecuteCommandLists ★ ──────→  队列 FIFO 逐条执行
  queue.Wait(别人围栏)  ← 扎闸门          ↑ 执行到闸门自己停，看别人计分牌
  CPU WaitFence()    ← 睡觉等自己的铃      ← 干完 Signal 拨自己的计分牌
                                       
同步的本质：队列内 FIFO 免费，跨队列必须显式申请；
资源状态是各框架的私有账本，外来资源自带 Barrier/同步/保活。
```
