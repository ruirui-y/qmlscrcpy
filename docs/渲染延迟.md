# 渲染延迟：那 5ms 到底在等什么

> 这篇是一次完整排查的记录。问题本身很简单——**一帧从进进程到上屏平均 7ms，能不能更低**——但定位过程走了不少弯路，中间被平均值误导过两次。把过程写下来，是因为"差点被自己编的指标骗了"这件事比结论更值钱。

## 一、要解决什么问题

投屏的观感延迟 = 设备编码 + 传输 + 我们这侧的解码 + 渲染。前三段只能调参数，最后一段完全在我们手里。

所以想要一个能回答"我们这侧一帧到底花了多久、花在哪"的观测手段。

要求：
- 每一帧一条记录，不能是平均值（平均会把双峰抹平，前面吃过亏）
- 每个数字必须来自同一帧，不能把不同阶段的时间混在一行
- 发布版不能有这些日志

## 二、观测手段怎么搭的

### 第一版：全局计数器 + 每秒打印

用 `PerfStats` 存九个累计值，每秒打印一次"这一秒的平均"。

**问题**：立刻发现读数会骗人。比如某秒打印"等唤醒 5.1ms"，但同一秒里有的帧是 0.3ms、有的是 6ms，平均值把两种情况糊成一个数，看起来像"固定延迟"。

### 第二版：只打印最近一帧

把累计改成"每个字段只存最近一帧的值"。读数真实了，但**又出新问题**：一行里的九个数字不属于同一帧——`Present` 时才拿到前两个，后面几个还是上一帧留下的。

### 第三版（最终）：每帧一个 FrameTrace

给每一帧分配一个 `FrameTrace`，跟着帧在三个线程间传递，谁的事件谁来填：

```
视频线程 Present
  ├─ 建 trace{id, 到达时刻, 到达间隔}
  ├─ 顶掉旧帧 → 打印「丢掉」行（存活多久）
  └─ 投递 lambda（带着这个 trace）

GUI 线程
  ├─ trace.queue_us = 现在 − 到达时刻
  └─ update()

渲染线程
  ├─ trace.wake_us  = synchronize 开始 − 上一段结束
  ├─ trace.sync_us  = synchronize 全程
  └─ trace.draw_us  = render 全程

GUI 线程（frameSwapped）
  ├─ trace.swap_us = 提交完成 − render 结束
  └─ 打印「上屏」行（同一帧九个数字），然后标记已打印
```

关键实现点：

- `TakePendingFrame(FrameTracePtr *trace_out)` 让帧和它的 trace 一起被取走，不会错配
- `printed` 原子标记：Qt 有时会因为窗口重绘多跑一轮 `render()`，同一帧会打印两次，必须挡掉
- 打印在 `frameSwapped` 里做（这一帧真正提交给系统之后），此时九个数字全部就位

日志长这样：

```
帧 128 上屏：到达间隔 16.6，GUI 排队 0.05，update到事件 5.01，事件到渲染 0.02，取帧 0.45，画一帧 0.73，交换阻塞 0.14，从到达到上屏 6.9 ms
帧 129 丢掉：到达间隔 4.2 ms，存活 3.8 ms
```

## 三、第一次结论错在哪

看到"等唤醒稳定在 5ms"，我第一反应是 **Qt 唤醒渲染线程慢**。为了让这个说法可证伪，加了两个探针：

1. `QEvent::UpdateRequest` 被 GUI 线程处理的时刻
2. 每帧有多少次 `update()` 调用（判断 Qt 是否合并了重绘请求）

结果：

| 探针 | 读数 | 说明 |
|---|---|---|
| 合并次数 | 恒为 1 | 没合并，一次 update 一个事件，测量没歪 |
| `update() → 事件被处理` | **4.3 ~ 6.5ms** | 全在这里 |
| `事件被处理 → 渲染线程开跑` | **0.02ms** | 渲染线程根本不慢 |

也就是说，渲染线程被叫醒之后立刻就开始干活，**5ms 花在 Qt 处理重绘请求之前**，跟我最初的说法正好相反。

## 四、排除掉的三个嫌疑

| 嫌疑 | 怎么排的 | 结果 |
|---|---|---|
| 我们自己的 8ms 轮询定时器占了 GUI 事件队列 | 删掉 `refresh_timer_` 重跑 | ❌ 还是 5ms |
| 打印日志在 GUI 线程写文件太慢 | 量 `qInfo` 本身耗时 | ❌ 0.25~0.35ms，只占 5% |
| `update()` 被合并导致测量错位 | 每帧统计合并次数 | ❌ 恒为 1 |

## 五、真正的原因：Qt 给下一帧留的 5ms 余量

Qt 在 Windows 上有三种渲染循环，用 `QSG_RENDER_LOOP` 切：

| 模式 | `update() → 事件处理` | `事件 → 渲染开跑` | 总延迟（中位 / 90 分位） |
|---|---|---|---|
| `threaded`（默认） | **5.11ms** | 0.1ms | **7.08 / 7.83 ms** |
| `basic` | 5.02ms | — | 7ms 量级 |
| **`windows`** | **不产生这个事件** | 2.07ms | **3.78 / 4.62 ms** |

`windows` 循环不用 `QEvent::UpdateRequest` 这条路径（探针读数恒为 `-1`，表示没抓到过事件），改由 Windows 消息/定时器直接驱动渲染，所以那 5ms 的调度等待整个消失，只剩 2ms 的交接。

**客户端总延迟从 7.1ms 降到 3.8ms，接近砍半。** 但这不是终点——后来发现那 5ms 其实是 Qt 一个可配置的余量，见第十节。

实测三组各跑 16~20 秒，同一台真机、同一个直播页面，样本 250~643 帧。

## 六、中途的改动：换 windows 渲染循环

`src/main.cpp`，在 `QGuiApplication` 构造之前：

```cpp
qputenv("QSG_RENDER_LOOP", "windows");
```

这一步把总延迟从 7.1ms 压到 3.8ms。但它只是**绕过**了那 5ms，并没有解决它——第十节说明真正的原因和更彻底的改法。

## 七、留下的约束和坑

1. **别用平均值判断延迟**。这次连续两次被平均值误导：一次把 0.3ms 和 6ms 糊成"稳定 5ms"，一次把不同帧的数据混成一行。逐帧、同帧，是唯一可信的观测方式。
2. **`windows` 循环不是 Qt 默认路径**。双窗口、无边框、置顶、拖拽缩放这些组合要回归一遍。
3. **丢帧和渲染轮次不是一回事**。一帧被顶掉（丢掉）和一次多余的 `render()`（窗口重绘）会打出两条一样的帧号，`printed` 标记就是为此加的。
4. **`frameSwapped` 只在真正提交时发**。窗口被遮挡或最小化时日志会停，不是 bug。

## 八、剩下的 2ms 是什么（第二轮排查）

换到 `windows` 循环后总延迟 3.7ms，里面还有一段 `update()` 完到渲染线程开跑。继续拆，需要两个新探针：

- `QQuickWindow::beforeSynchronizing`（渲染线程发出的第一个信号）的到达时刻
- 它到 `synchronize` 开始之间的差，就是 Qt 同步前的准备工作

改成三段：

```
update() 执行完 ──①唤醒──▶ beforeSynchronizing ──②预处理──▶ synchronize 开始
```

实测（连续画面 660 帧）：

| 段 | 中位 | 90 分位 |
|---|---|---|
| ① GUI→渲染线程（唤醒） | **1.95 ms** | 2.78 ms |
| ② Qt 同步前准备 | **0.01 ms** | 0.02 ms |
| 取帧 | 0.61 ms | — |
| 画一帧 | 0.72 ms | — |
| 交换阻塞 | 0.16 ms | — |
| **总延迟** | **3.72 ms** | 4.63 ms |

### 为什么说它是"节拍"而不是"排队"

唤醒时间的分布：

```
<0.5ms    59 帧
0.5~1.5  126 帧
1.5~2.5  347 帧   ← 87% 堆在这
2.5~4    128 帧
>=4        0 帧
```

排队会铺满 0~4ms，实际是"**永远约 2ms，带点抖动**"。这是定时器节拍的特征，不是负载。

### Qt 自己的日志也印证

打开 `QSG_RENDER_TIMING=1`：

```
Frame rendered with 'windows' renderloop in: 2ms, polish=0, sync=1, render=1, swap=0
Frame rendered with 'windows' renderloop in: 0ms, polish=0, sync=0, render=0, swap=0
```

Qt 统计的 sync + render 只有 0~3ms、swap 恒 0——**因为它没把"等下一次被唤醒"算进去**，而我们量到的 2ms 正是这一段。

### 结论

这 2ms 在 Qt 的 `SGWindowsRenderLoop` 里，靠应用层代码改不掉。想再压只能绕开 Qt 的渲染循环（自绘原生窗口 + 自己的 swapchain），收益上限 2ms，代价是输入路由、窗口管理、DPI、z-order 全部自己重做。

## 九、三种渲染循环到底是什么（源码证据）

Qt 5.15.2 私有头文件里的枚举（`qsgrenderloop_p.h`）：

```cpp
enum RenderLoopType {
    BasicRenderLoop,        // GUI 线程自己画
    ThreadedRenderLoop,     // 专用渲染线程画
    WindowsRenderLoop       // 专用渲染线程画，但由定时器驱动
};
```

`QSGWindowsRenderLoop` 的私有头（`qsgwindowsrenderloop_p.h`）里全是定时器字段：

```cpp
private:
    struct WindowData {
        QQuickWindow *window;
        bool pendingUpdate;          // update() 只置这个标志
    };

    void maybePostUpdateTimer();     // 然后投一个定时器
    int m_updateTimer;               // 驱动的就是它
    int m_animationTimer;
    int m_vsyncDelta;                // 还自己估算 vsync 间隔
```

所以它的时序是：

```
update()  →  pendingUpdate = true  →  maybePostUpdateTimer()
                                          ↓ 等 m_updateTimer 到点
                                      render()
```

这正好对上实测的两个现象：

| 现象 | 解释 |
|---|---|
| `UpdateRequest` 探针恒为 `-1` | windows 循环不走这条事件 |
| 唤醒中位 1.95ms、集中在 1.5~2.5ms | 定时器 tick 的相位，不是负载排队 |

而 `basic` / `threaded` 都走 `UpdateRequest` 事件链：`update()` 投事件 → GUI 事件循环处理 → 渲染开跑。我们量到「update → 事件被处理」5ms、「事件 → 渲染线程开跑」0.02ms，说明**堵在事件被处理之前**。换到 windows 循环后这条链没了，5ms 收缩成 2ms 的定时器等待。

三种循环的用途分工：

| 循环 | 适用场景 |
|---|---|
| `basic` | 单线程、软件渲染、调试；没有渲染线程，好排查 |
| `threaded` | 默认；渲染与 GUI 解耦，动画流畅，靠 vsync 同步 |
| `windows` | Windows 专用；绕开平台上 `SwapBuffers` 与 vsync 的时序坑，`m_vsyncDelta` 就是为此存在 |

`m_updateTimer` 没有对外 setter，所以只能整段换循环，不能单独调它的 tick——这也是"再压 2ms 只能自绘"的技术原因。

## 十、120fps 撑得住吗

先分清两件事：**延迟**是"一帧从到达到上屏 3.7ms"，**吞吐**是"每秒能画多少帧"。120fps 要求的是后者：每 8.33ms 画完一帧。

按实测拆开看各条线程每帧要花多久：

| 线程 | 每帧工作 | 120fps 预算 8.33ms | 余量 |
|---|---|---|---|
| 视频线程 | 等数据 + 解码 3~5ms | 8.33ms | 够，但最紧 |
| 渲染线程 | 取帧 0.6 + 画 0.7 = 1.3ms | 8.33ms | 很宽松 |
| GUI 线程 | 排队 0.08 + update 0.01 | 8.33ms | 几乎不占 |

**结论：渲染这侧撑 120fps 没问题，瓶颈不在我们。** 实测直播页面（约 90~150fps 源）时渲染轮次能跟上，掉帧主要来自"只留最新帧"的策略——源比渲染快时旧帧被覆盖，这是设计如此，不是性能不够。

真正的限制在两处，都不在客户端：

1. **设备编码**：1264×2776 分辨率下每秒 120 帧 H.264，编码器是中端 SoC，实际很难稳定跑满
2. **传输**：120fps 需要的码率通常是 60fps 的两倍以上，无线（adb tcpip）下更容易成为瓶颈

所以调参的正确顺序是：先看 `[perf]` 里的"帧间隔"是否真的到 8.3ms，再看丢帧比例，最后才怀疑客户端。
## 十一、最终答案：QT_QPA_UPDATE_IDLE_TIME

换 windows 循环之后我一直在想：那 5ms 太规整了，不像调度，像定时器。翻 [Qt 官方文档关于场景图与渲染循环的说明](https://doc.qt.io/qt-6.8/qtquick-visualcanvas-scenegraph.html)时看到一句关键的话：

> 两个渲染循环都通过 `QWindow::requestUpdate()` 来安排窗口的下一次更新。**在多数平台上，这由一个 5ms 的 GUI 线程定时器支撑**，以便给事件处理留出时间。……对于做低层基准测试的应用，把 `QT_QPA_UPDATE_IDLE_TIME` 设为 `0` 可能有助于减少 GUI 线程的空闲时间。

原来那 5ms 就是 Qt 主动给"处理事件"留的余量，`QT_QPA_UPDATE_IDLE_TIME` 可以把它调掉。

### 五种组合的实测（同一真机、同样画面）

| 配置 | 总延迟中位 | 唤醒中位 |
|---|---|---|
| windows 默认 | 3.74 ms | 2.06 ms |
| windows + `IDLE=0` | 3.65 ms | 1.92 ms |
| threaded 默认 | 6.26 ms | 4.41 ms |
| **threaded + `IDLE=0`** | **1.89 ms** | **0.11 ms** |
| basic + `IDLE=0` | 1.69 ms | 0.06 ms |

- `windows` 循环用的是自己的定时器，`IDLE` 对它几乎无效
- `threaded` / `basic` 走 `QWindow::requestUpdate`，`IDLE=0` 直接把 5ms 余量抹掉，唤醒从 4.4ms 掉到 0.1ms
- `basic` 最快但渲染在 GUI 线程，CPU 18.4%（threaded 是 10.4%），双窗口下风险更高，不选

长时间对照（各 22 秒、800+ 帧）：`threaded + IDLE=0` 中位 2.43ms / 90 分位 5.16ms；`windows` 中位 3.84 / 90 分位 4.86。**中位明显更好，长尾略差**，取中位优先。

### 最终改动

```cpp
// Qt 用一个定时器给"下一帧什么时候准备"留余量，默认 5ms；关掉这个余量后
// update() 到渲染线程被唤醒从 5ms 降到 0.1ms，客户端总延迟 6.3ms → 2.4ms。
// 换 windows 渲染循环只是绕过同一段等待（3.8ms），不如直接把余量关掉。
if (qEnvironmentVariableIsEmpty("QT_QPA_UPDATE_IDLE_TIME"))
{
    qputenv("QT_QPA_UPDATE_IDLE_TIME", "0");
}
```

保留"外部设过就不覆盖"的行为，方便做对照实验。

### CPU 代价

| 场景 | CPU |
|---|---|
| 画面静止（每秒 2~5 帧） | 0.8 ~ 2.2%（各配置差别不大） |
| 连续滑动（每秒 100+ 帧） | 明显升高，但主要来自解码与渲染本身，不是空闲自旋 |

静止时 `IDLE=0` 并没有多渲染帧（10 秒 23 帧 vs 默认 43 帧），说明它不是空转，只是不再人为等 5ms。

### 顺带回答两个问题

**能不能跨线程直接调 `render()`？** 不能。GL 上下文和 Renderer 归渲染线程所有，`synchronize()` / `render()` 只能由 Qt 的渲染循环调用。想要"帧到了立刻画"只有两条路：

1. `QQuickRenderControl`：Qt 官方让你自己驱动 polish / sync / render，但你要自己负责把结果呈现到窗口（它本身不绑窗口）
2. 原生子窗口 + 自己的 swapchain：完全绕开 Qt 的渲染循环

**升级 Qt 6 有用吗？** 没用，而且会更麻烦。Qt 6.8 文档明确只剩 `basic` 和 `threaded` 两种循环——我们用的 `windows` 循环是 Qt 5 独有的，升级后就没有了。而真正的解法（`QT_QPA_UPDATE_IDLE_TIME`）在 Qt 5 上已经可用，不需要升级。
## 十二、最后的观测方案（分层，默认轻量）

排查结束后把观测手段收成两层，避免长期开着重开销的埋点：

| 层级 | 内容 | 开销 | 开关 |
|---|---|---|---|
| 每秒统计 | 到达 / 上屏 / 丢帧率 + 延迟三档分布 + 这一秒最大 | 四个原子计数 + 两个时间戳，可忽略 | **默认开** |
| 逐帧追踪 | 每帧九段耗时 + 丢帧明细 | 每帧一个 Trace 分配 + 一行日志 I/O | `QS_TRACE_FRAMES=1` |

默认每秒三行：帧数与丢帧率、上屏延迟分布、到达间隔分布。

```
[perf] 1s 到达 113 帧，上屏 113 帧，丢 0（0.0%）
[perf]     上屏延迟 <1.5ms 49% / 1.5~2.5ms 40% / 2.5~3.5ms 10% / >3.5ms 1%，最大 4.0 ms
[perf]     到达间隔 <8.5ms 57% / 8.5~17ms 43% / 17~34ms 1% / >34ms 0%
```

上屏延迟是一帧从到达画布到真正上屏的时间；到达间隔是源帧率，按 120/60/30fps 档位切桶。两者分开统计，才能区分"源慢"和"我们慢"。

为什么延迟用分档而不是平均，这次已经交了两次学费：平均值会把 0.3ms 和 6ms 的帧糊成一个"看起来还行"的数。三档分布只要几个计数器，却能把双峰和长尾直接暴露出来。

`frameSwapped` 会为窗口重绘多触发几次，所以统计里加了"这一轮必须真的取到了新帧、且交换发生在 100ms 内"的过滤，否则窗口被遮挡后补上的那次交换会算出一个几百毫秒的假延迟。
## 十三、无线实测：码率、帧率上限，以及"12M 是不是一帧 12M"

### 怎么测的

早期测法有坑：用 `adb shell input swipe` 连续快刷，几十秒内把抖音刷过好几个视频，最后停在"加载中"的画面上——画面不动，帧数自然掉到 20 多，得出一堆自相矛盾的数据（1M 比 12M 帧数还高）。

改成**慢速滑动 + 连接后再计时**：

```powershell
# 设备端循环，12 次，每次 400ms 的小幅滑动，间隔 2.5 秒
input swipe 600 1250 600 950 400
Start-Sleep -Milliseconds 2500
```

- 等日志出现 `连接完成`，再等 4 秒让画面稳定
- 只统计之后的 14 秒
- 会话参数在 `config/window.ini` 的 `[video_wireless]` 里改（`bitrate` / `max_fps`），改完重启程序生效

### 帧率参数到底有没有用：取决于应用自己的刷新率

| 配置 | 到达帧数 |
|---|---|
| 6M + `max_fps=0`（不限） | 94 帧/秒 |
| 6M + `max_fps=60` | **57 帧/秒** |
| 6M + `max_fps=120` | **97 帧/秒** |

设备 `SurfaceFlinger` 里确实有 120Hz 档：

```
HwcConfigIndex:0  name:60.00 Hz
HwcConfigIndex:1  name:120.00 Hz
```

但**应用自己锁 60Hz 时，`max_fps=120` 只能拿到 58 帧**——参数没生效不是客户端的锅，源头就没那么多帧。把抖音设成 120Hz 后立刻变成 97 帧。结论：

> `max_fps` 是"上限"，不是"目标"。上限能不能用上，取决于屏幕刷新率和当前应用自身的帧率。

### 码率和帧数：2M 只能撑 72 帧，12M 能到 114 帧

| 码率（`fps=0`） | 到达帧数 |
|---|---|
| 2 Mbps | 72 帧/秒 |
| 6 Mbps | 94 帧/秒 |
| 12 Mbps | 114 帧/秒 |

### "12M 是不是一帧 12M"——不是，单位是每秒

码率的单位是 **bit per second**：

```
12 Mbps = 12 兆比特/秒 = 1.5 MB/秒
```

换算到单帧：

```
12 Mbps ÷ 114 fps ≈ 13 KB/帧
 2 Mbps ÷  72 fps ≈ 3.5 KB/帧
```

屏幕内容的 H.264 压缩率极高（大片纯色、文字、缓慢移动），单帧只有几 KB 到几十 KB，完全正常。**不是"一帧 12M"。**

### 为什么码率低了帧数也掉

编码器每秒能花的字节数是固定的（就是码率）。画面复杂时单帧需要更多字节：

```
要发 114 帧 → 每帧预算 = 12 Mbps / 114 ≈ 13 KB
            2 Mbps / 114 ≈ 1.8 KB  ← 编码器做不到这么小还不糊
```

预算不够时，编码器只有两条路：降质量，或者降帧率。实测就是后者——2M 下只输出 72 帧。所以：

> **码率不只是"清晰度旋钮"，它同时是帧率的上限约束。**

"M 数越大效果越好"在"不超网络带宽"的前提下是对的：清晰度和可承载帧数都随码率上升。但它不是无限的——12M 之后再往上加，收益主要落在画质上，帧数会被设备和网络卡住。
