# 硬解读回延迟

记录「硬解一帧为什么要 5ms、这几毫秒花在哪」的完整过程：先搞清楚概念，再一步步测量、排除错误假设，最后定位到真正的原因。

**结论先说**：一帧 3.3ms = 准备 0.01ms + 等 Map 2.1ms（其中 0.6ms 是拷贝、1.5ms 是等 GPU 队列）+ 读 0.9ms。

---

## 一、这一阶段要做什么

### 起点

硬解（B 方案）每帧要走一遍「显存 → 内存」：

```
D3D11 解码纹理 → 拷到 staging → Map 读回 → memcpy 到 QByteArray
```

实测每帧约 5ms，但没人说得清这 5ms 具体花在哪一步。

### 目标

1. 把 5ms 拆到每一段，精确到微秒
2. 找出真正的瓶颈
3. 判断哪些能优化、哪些是硬件限制

### 不做什么

- 不改解码协议、不动渲染
- 不做零拷贝（已在 [GPU渲染改造](GPU渲染改造.md) 里试过三次，全部失败）

---

## 二、概念澄清

这一节是后面所有讨论的基础。搞不清这几个词，就看不懂时间花在哪。

### 1. AVFrame 只是"运货单"

```
AVFrame = 尺寸 + 像素格式 + 若干指针 + 行跨度（linesize）
```

它**不装像素**，只描述像素在哪：

| 解码方式 | `data[0]` | `data[1]` |
|---|---|---|
| 软解（`AV_PIX_FMT_YUV420P`） | Y 平面指针（内存） | U 平面指针 |
| 硬解（`AV_PIX_FMT_D3D11`） | `ID3D11Texture2D*`（显存） | **切片号（整数）** |

**硬解时 `data[1]` 是编号，不是指针**——这是最容易误解的一点。

### 2. 为什么叫"纹理"而不是"切片数组"

D3D11 的资源类型叫 `ID3D11Texture2D`，几个关键字段：

```
ID3D11Texture2D
  ├─ Format     = DXGI_FORMAT_NV12
  ├─ Width      = 1264
  ├─ Height     = 2780
  └─ ArraySize  = 16        ← 这个字段让它变成"切片数组"
```

微软的命名是"二维纹理 + 数组层"，`ArraySize > 1` 时功能上就是切片数组，但**类型名不变**。这是历史命名，确实反直觉。

### 3. DPB：解码器的帧池

```
Decoded Picture Buffer = 一块 ArraySize=N 的 NV12 纹理
                        每个切片 = 一帧
                        要 N 张是因为 P/B 帧要参考前面解出来的帧
```

FFmpeg 在 `avcodec_open2` 时按 SPS 算 N（通常 16~20），**它自己 `CreateTexture2D`**，我们看不到那行代码，也改不了池子的 Usage 和 BindFlags。

### 4. 三种纹理用法互斥

| Usage | CPU 能 Map | 能解码 | 用途 |
|---|---|---|---|
| `DEFAULT` | ❌ | ✅（`BIND_DECODER`） | GPU 读写 |
| `STAGING` | ✅ | ❌（BindFlags 必须 0） | CPU 读回 |
| `DYNAMIC` | 只能写 | ❌ | 频繁上传 |

**"解码器可写"和"CPU 可读"在 D3D11 里互斥**，所以必须有 staging 中转。

### 5. YUV 只需要知道三个数

做传输/缓冲时不用理解颜色语义，只要：

| 事实 | 值 |
|---|---|
| 每帧字节数 | `宽 × 高 × 1.5` |
| 行跨度 RowPitch | ≥ 宽，可能有对齐填充（1264 → 1280） |
| 平面数 | 软解 3 个 / 硬解 2 个（NV12） |

## 三、第一版测量：4.9ms 花在哪

### 3.1 埋点方法

在 `DownloadFrame` 里打四个时间戳：

```cpp
t0   CopySubresourceRegion 之前
t1   CopySubresourceRegion 之后
t1b  QByteArray 分配之后
t2   Map 之后
t3   memcpy 之后
```

对应三段：

```
准备 = (t1 - t0) + (t1b - t1)     分配缓冲 + 提交拷贝
等Map = t2 - t1b                  等拷贝执行完
读    = t3 - t2                   uncached 内存逐行拷
```

通过 `DecodeProbe` 按秒汇总：

```
[decode] 秒结 120 帧（硬解）：拼包 7us / 送包 227us / 收帧 3912us（准备 1278 + 等Map 1555 + 读 1046us）
```

### 3.2 第一版数据（3 次 × 20 秒）

| 段 | 数值 |
|---|---|
| 准备（分配 + 提交） | 0.86~0.95 ms |
| **等 Map** | 1.3 → **3.0 ms** 后不再涨 |
| 读（memcpy） | 0.87~1.16 ms |
| 合计 | **~4.9 ms** |

反推有效带宽：`5.27 MB ÷ 3.0 ms ≈ 1.76 GB/s`（PCIe 理论 20GB/s 的 9%）。

### 3.3 第一个小优化：不清零

```cpp
// 改前：QByteArray(size, '\0')  → 准备 1.29ms
// 改后：QByteArray(size, Qt::Uninitialized) → 准备 0.87ms
```

省 0.4ms（不是预估的 1.2ms，因为分配本身也要时间）。

## 四、逐个排除错误假设

### 假设 1：socket 包堆积，来不及投递

**验证**：在 `VideoReader::run` 每次循环末尾打印「缓冲区里还剩多少个完整包」+ `socket->bytesAvailable()`。

**结果（20 秒，1100 次循环）**：

| 残留完整包 | 次数 | 占比 |
|---|---|---|
| 0 | 989 | **89.9%** |
| 1 | 54 | 4.9% |
| 2 | 29 | 2.6% |
| 3~10 | 28 | 2.6%（都在启动瞬间） |

```
socket 未读字节：全程 0
```

**结论：没有积压，假设不成立。**

### 假设 2：拷贝排在自己刚提交的解码命令后面

**验证**：把 `DrainFrames` 从 `send_packet` 之后移到之前。

**结果**：等 Map 仍 1.4→3.8ms，无改善，还多 1 帧延迟。

**结论：不成立**（解码器的提交节奏和我们无关）。

### 假设 3：驱动把拷贝命令攒在队列里

**验证**：`Map` 前加 `ID3D11DeviceContext::Flush()`。

**结果**：三次 × 20 秒，等 Map 仍是 1.35 → 3.0ms。

**结论：不成立**，命令本来就已经提交。

## 五、定位一：PCIe 省电降档

### 现象

nvidia-smi 在解码运行时采样：

```
pcie.link.gen.max     = 4
pcie.link.gen.current = 1      ← 只有 Gen1
图形时钟              = 255MHz  ← 空闲档
GPU 利用率            = 16%
```

**负载太轻，驱动把 PCIe 链路和核心时钟都压在最低档。**

### 处理

NVIDIA app → 程序设置 → `QmlScrcpy.exe` → 电源管理模式 = **最高性能优先**。

### 对比

| 段 | Gen1（省电） | **Gen4（最高性能）** |
|---|---|---|
| 准备 | 0.87~0.95ms | 0.82~0.85ms |
| **等 Map** | 1.3 → **3.0ms**（还递增） | **1.30ms（稳定）** |
| 读 | 0.87~1.16ms | 0.92~1.08ms |
| 合计 | 4.9ms | **3.4ms** |

**等 Map 不再递增**——之前的“递增”就是链路从空闲档往上升的过程。

---

## 六、定位二：Map 等的是 GPU 队列排空

Gen4 下 1.3ms 已经比 3.0ms 好很多，但 `5.27MB ÷ 1.3ms ≈ 4 GB/s` 仍远低于 Gen4 的 25GB/s。继续查。

### 实验 A：普通 NV12 纹理的纯拷贝基准

建一张普通（非解码器）NV12 纹理，拷到 staging 再 Map，循环 30 次：

```
提交 1us / 等 Map 497us / 吞吐 ≈ 10 GB/s
```

**普通纹理只要 0.5ms。**

### 实验 B：两步拷贝（先转普通布局）

```
解码器纹理（tiled） → 中间普通纹理 → staging
```

结果：等 Map **2143us，和单步一模一样**。

**说明瓶颈不是 tiled 布局。**

### 实验 C：让 GPU 空闲后再 Map

在 `Push` 的 send 与 drain 之间插 `msleep(60)`，使投递变慢、GPU 队列排空：

| 场景 | 准备 | 等 Map | 读 |
|---|---|---|---|
| 正常投递（GPU 一直忙） | 8us | **2147us** | 911us |
| 延迟 60ms（GPU 空闲） | 18us | **595~657us** | 817~921us |

### 结论

```
2.1ms = 0.6ms 真实拷贝 + 1.5ms 等 GPU 队列排空
```

- 拷贝本身 0.6ms，和普通纹理基准（0.5ms）吻合
- **Map 的同步粒度是"GPU 队列排空"，不是"这次拷贝完成"**
- 所以改拷贝方式、加 Flush、调整投递顺序全都无效

## 七、最后一块：帧缓冲池

### 做了什么

`h264_decoder.cpp` 加 `FrameBufferPool`：

```cpp
struct FrameBufferPool
{
    QByteArray *Take(int size);      // 池里有就复用，没有才 new
    void Give(QByteArray *buffer);   // 引用计数归零时归还，最多留 3 个
    QMutex mutex;
    QVector<QByteArray *> free_list;
};
```

`Frame` 带着的 `shared_ptr<QByteArray>` 用自定义 deleter 归还：

```cpp
auto pool = pool_;                    // 捕获 shared_ptr，解码器先析构也不会悬空
std::shared_ptr<QByteArray> buffer(pool->Take(total_size), [pool](QByteArray *raw)
{
    pool->Give(raw);                  // 渲染器画完 → 归还池子
});
```

### 结果

| 段 | 缓冲池前 | 缓冲池后 |
|---|---|---|
| 准备 | 0.83ms | **0.009ms** |
| 等 Map | 1.30ms | **2.11ms** |
| 读 | 0.99ms | 0.90ms |
| **合计** | **3.4ms** | **3.3ms** |

### 为什么总时间没变

**之前的 malloc 和 GPU 拷贝是重叠的**：

```
提交 CopySubresourceRegion
   ↓
malloc 5MB（0.8ms）   ← 这段时间 GPU 正在执行拷贝
   ↓
Map（等拷贝完成）
```

省掉 malloc 后，那 0.8ms 没有别的事填，直接还给了等待。

### 要不要留着

| 理由 | 说明 |
|---|---|
| 延迟 | 不变（3.4 → 3.3ms） |
| 内存 | 更好：不再每帧分配/释放 5MB，减少堆碎片和缺页 |
| 复杂度 | 增加（池子 + 锁 + 引用计数） |

**留着**：它是"异步读回"的前提，异步读回需要多块缓冲轮转。

## 八、最终时间账

```
一帧 3.3ms：
  准备   0.01ms   （缓冲池复用，可忽略）
  等Map  2.10ms   （0.6ms 拷贝 + 1.5ms 等 GPU 队列排空）
  读     0.90ms   （5.27MB uncached memcpy，≈5.5 GB/s）
异步模式（`async_readback=1`）：

```
一帧 1.65ms：
  准备   0.01ms
  等Map  0.05ms   （读的是上一帧，队列已空）
  读     0.90ms
（代价：画面延迟 +1 帧）
```

### 能改与不能改

| 方案 | 效果 | 结论 |
|---|---|---|
| PCIe 最高性能 | 等 Map 3.0 → 1.3ms | ✅ 已做（NVIDIA 控制面板设一次） |
| 缓冲池 | 准备 0.83 → 0.01ms（总时间不变） | ✅ 已做 |
| `Qt::Uninitialized` | 准备 1.29 → 0.87ms | ✅ 已做 |
| 异步读回（双 staging + Query） | 等 Map 2.1 → 0.05ms，代价延迟 +1 帧 | ✅ 已做，设置界面可切（默认关） |
| 降分辨率 | 三段按比例下降 | 唯一大杠杆，看画质取舍 |
| 零拷贝 | 归零 | ❌ 已证伪（见 GPU渲染改造） |
| 多解码器 | 无 | ❌ 瓶颈在读回，不在解码 |

### 余量

```
60fps  预算 16.7ms，用 3.3ms → 余量 5 倍
120fps 预算 8.3ms， 用 3.3ms → 余量 2.5 倍
```

## 九、异步读回（已实现，随 0.3.1 发布）

针对第六节定位到的「1.5ms 等 GPU 队列」，做了异步读回，并在设置界面给了开关。

### 思路

```
帧 N   ：Copy 到 staging[slot]，End(query[slot])，立刻返回（不等）
帧 N+1 ：先读上一帧的槽（query 早就完成）→ Map + memcpy（几乎不阻塞）
         再把当前帧 Copy 到另一个槽，End(query)
```

关键点：**读的永远是上一帧**，所以 Map 时队列已经空了。

### 实现

`D3d11State` 从单 staging 扩成双缓冲：

```cpp
ComPtr<ID3D11Texture2D> staging[2];   // 一帧在拷，另一帧在读
ComPtr<ID3D11Query> query[2];         // 每张 staging 配一个 D3D11_QUERY_EVENT
int write_slot = 0;
int pending_slot = -1;                // 已拷好、等着读的槽
```

`DownloadFrame` 拆成两步：

```cpp
// 第一步：只提交，不等待
CopySubresourceRegion(staging[slot], ..., texture, slice);
End(query[slot]);

// 第二步：读上一帧
const int read_slot = pending_slot;
pending_slot = slot;
write_slot = 1 - slot;
if (read_slot < 0)
{
    return ReadStaging(slot, ...);   // 第一帧没上一帧，同步读一次
}
GetData(query[read_slot], ...);      // 查完成状态（已完成就不阻塞）
return ReadStaging(read_slot, ...);
```

读回逻辑抽成 `ReadStaging(slot, width, height, frame, error)`：Map → 逐行 memcpy → Unmap → 组装 `Frame`。

### 开关

- 配置项：`[decode] async_readback=0/1`（0 = 同步，默认）
- 设置界面：画质下面「读回方式」下拉，切换后自动重连
- 解码器接口：`H264Decoder::SetAsyncReadback(bool)`

同步路径保留在同一个函数里，`async_readback_ == false` 时走「拷完立刻读同一张」。

### 实测

| 段 | 同步 | **异步** |
|---|---|---|
| 准备 | 0.009ms | 0.010ms |
| **等 Map** | **2.11ms** | **0.052~0.062ms** |
| 读 | 0.90ms | 0.82~1.12ms |
| **收帧合计** | **3.3ms** | **1.4~1.8ms** |

等 Map 降了约 40 倍，总时间减半。

### 代价与取舍

| 项 | 说明 |
|---|---|
| 画面延迟 | **+1 帧**（60fps 下 16.7ms） |
| 内存 | 多一张 staging（5.27MB 显存） |
| 尾帧 | 连接结束时最后一帧会丢（不影响使用） |

**默认保持同步**：手感优先。异步只在 120fps 高负载、或 CPU 明显被读回拖住时才建议开。

**纯吞吐不变**——异步只是把等待藏进上一帧的时间里，不会让搬运变快。

---

## 十、一句话总结

```
一帧 3.3ms = 0.01ms 准备 + 2.1ms 等 Map（含 1.5ms 等 GPU 队列）+ 0.9ms 读
socket 没有积压、解码不是瓶颈；
瓶颈是 staging 读回的同步方式和 GPU 队列占用，
能靠"降分辨率"或"异步读回（+1 帧延迟）"解决。
```
