# 硬解读回延迟：概念、实测与结论

这一轮把「硬解一帧为什么要 5ms、这 5ms 花在哪」彻底量清楚了。前半截是概念（搞清楚 AVFrame / 纹理 / DPB / staging 各是什么），后半截是实测（三段打点 + 3 次 × 20 秒复测）。

---

## 一、概念：这些东西到底叫什么

### 1. AVFrame 只是"运货单"

```
AVFrame = 尺寸 + 像素格式 + 若干指针 + 行跨度（linesize）
```

它**不装像素**，只描述像素在哪：

| 解码方式 | `data[0]` | `data[1]` |
|---|---|---|
| 软解（`AV_PIX_FMT_YUV420P`） | Y 平面指针（内存） | U 平面指针 |
| 硬解（`AV_PIX_FMT_D3D11`） | `ID3D11Texture2D*`（显存） | **切片号（整数）** |

**`data[1]` 在硬解时是编号，不是指针**——这点最容易误解。

### 2. "纹理"到底是什么

D3D11 的资源类型叫 `ID3D11Texture2D`，它有几个关键字段：

```
ID3D11Texture2D
  ├─ Format     = DXGI_FORMAT_NV12
  ├─ Width      = 1264
  ├─ Height     = 2780
  └─ ArraySize  = 16        ← 这个字段让它变成"切片数组"
```

**为什么叫纹理而不是切片数组**：微软的命名习惯是"二维纹理 + 数组层"，`ArraySize > 1` 时才在功能上变成切片数组，但类型名不变。所以文档里说 "texture array"（纹理数组），不说 slice array。

### 3. DPB：解码器的帧池

```
Decoded Picture Buffer = 一块 ArraySize=N 的 NV12 纹理
                        每个切片 = 一帧
                        为什么要 N 张：P/B 帧要参考前面解出来的帧
```

FFmpeg 在 `avcodec_open2` 时按 SPS 算 N（通常 16~20），**它自己 `CreateTexture2D`，我们看不到那行代码**，也改不了池子的 Usage 和 BindFlags。

### 4. 三种纹理用法是互斥的

| Usage | CPU 能 Map | 能解码 | 用途 |
|---|---|---|---|
| `DEFAULT` | ❌ | ✅（`BIND_DECODER`） | GPU 读写 |
| `STAGING` | ✅ | ❌（BindFlags 必须 0） | CPU 读回 |
| `DYNAMIC` | 只能写 | ❌ | 频繁上传 |

**"解码器可写"和"CPU 可读"在 D3D11 里是互斥属性**，所以必须走 staging 中转。

### 5. YUV 只需要知道三个数

做传输/缓冲时不用理解颜色语义，只要：

| 事实 | 值 |
|---|---|
| 每帧字节数 | `宽 × 高 × 1.5` |
| 行跨度 RowPitch | ≥ 宽，可能有对齐填充 |
| 平面数 | 软解 3 个 / 硬解 2 个（NV12） |

颜色系数（BT.601 等）是渲染层的事。

## 二、一帧从 socket 到屏幕的完整链路

```
socket 字节流
   ↓ 拼 12 字节包头 → 按长度切包
avcodec_send_packet()
   ↓ 解码器内部队列（异步，GPU 解码）
avcodec_receive_frame()
   ↓ 返回 AVFrame：纹理指针 + 切片号（像素还在显存）
CopySubresourceRegion()
   ↓ 显存 → staging（这次拷贝就是 PCIe 传输）
Map(staging)              ← 阻塞：等拷贝执行完
   ↓ 拿到 CPU 指针 + RowPitch
逐行 memcpy
   ↓ 压紧成 QByteArray（5.27 MB）
Frame(NV12) → 渲染器上传两张纹理 → 着色器 YUV→RGB
```

---

## 三、实测方法

### 三段打点

在 `DownloadFrame` 里加四个时间戳：

```cpp
t0  CopySubresourceRegion 之前
t1  CopySubresourceRegion 之后
t1b QByteArray 分配之后
t2  Map 之后
t3  memcpy 之后
```

对应三段：

```
准备 = (t1 - t0) + (t1b - t1)     分配缓冲 + 提交拷贝
等Map = t2 - t1b                  拷贝真正执行完
读    = t3 - t2                   uncached 内存逐行拷
```

通过 `DecodeProbe` 按秒汇总，日志长这样：

```
[decode] 秒结 120 帧（硬解）：拼包 7us / 送包 227us / 收帧 3912us（准备 1278 + 等Map 1555 + 读 1046us）/ 最慢 7866us
```

### socket 残留打点

在 `VideoReader::run` 的每次循环末尾统计：

- 缓冲区里还有多少个**完整包**
- `socket_->bytesAvailable()`（内核里还没读的字节）

## 四、实测数据

### 1. 三段耗时（3 次 × 20 秒，硬解 1264×2780）

| 段 | 数值 | 稳定性 |
|---|---|---|
| 准备（分配 + 提交） | 0.86~0.95 ms | 稳定 |
| **等 Map** | 1.3 → **3.0~3.1 ms** 后不再涨 | 三次一致 |
| 读（memcpy） | 0.87~1.16 ms | 稳定 |
| 收帧合计 | ~4.9 ms | —— |

反推有效读回带宽：

```
5.27 MB ÷ 3.0 ms ≈ 1.76 GB/s
```

远低于 PCIe 4.0 理论值 20GB/s，原因是 **staging 读回是 uncached、非流水、带驱动开销**。

### 2. 提交时间几乎为零

```
CopySubresourceRegion 调用本身：5 us
Flush() 之后：没有变化
```

说明命令本来就已经提交，等待发生在 GPU 执行侧，不是驱动攒命令。

### 3. socket 残留（第 3 次 20 秒，1100 次循环）

| 残留完整包 | 次数 | 占比 |
|---|---|---|
| 0 | 989 | **89.9%** |
| 1 | 54 | 4.9% |
| 2 | 29 | 2.6% |
| 3 | 14 | 1.3% |
| 4~10 | 14 | 1.3%（全部在启动瞬间） |

```
socket 未读字节：全程 0
```

**结论：没有持续积压。** 90% 的循环缓冲区是空的，大残留只出现在首帧 IDR 集中投递时。

### 4. 优化效果验证

| 改动 | 效果 |
|---|---|
| `QByteArray(size, '\0')` → `Qt::Uninitialized` | 准备 1.29ms → 0.87ms（**省 0.4ms**） |
| `Flush()` 放在 Map 前 | **无变化**（已删） |
| 把 drain 移到 send 之前 | 等 Map 无变化，还多 1 帧延迟（已回退） |

## 五、被证伪的假设

| 假设 | 验证方式 | 结果 |
|---|---|---|
| "socket 包没来得及投递，堆积导致 Map 变慢" | 每次循环打印残留包数 | ❌ 90% 循环残留为 0，socket 全程无积压 |
| "拷贝排在我们刚提交的解码后面" | 把 drain 移到 send 之前 | ❌ 等待无变化 |
| "驱动把拷贝命令攒在队列里" | Map 前加 `Flush()` | ❌ 等待无变化 |
| "等的是解码完成" | `receive_frame` 返回即已解码 | ❌ 解码早已完成 |

## 六、仍然没完全解释的

**为什么等 Map 从 1.3ms 涨到 3.0ms 后不再涨**，目前只能说：

- 1.3ms 是"拷贝刚提交、GPU 还没排满"时的初值
- 3.0ms 是稳态：拷贝 5.27MB 的真实耗时（1.76GB/s）
- 中间过程是 GPU 队列从空到充满

要更精确只能上 GPUView / ETW，成本高于收益，到这里为止。

## 七、能改的与不能改的

| 方案 | 效果 | 结论 |
|---|---|---|
| 降分辨率（1264×2780 → 1280×720） | 5.27MB → 1.38MB，三段按比例降到 ~1.3ms | ✅ 唯一大杠杆 |
| `Qt::Uninitialized` | -0.4ms | ✅ 已做 |
| 双 staging 交替 | 把等待藏到上一帧，总吞吐不变 | ⚠️ 多 1 帧延迟，未做 |
| 帧缓冲池（复用 5MB 缓冲，引用计数归还） | 准备 -0.82ms，但总时间不变 | ✅ 已做（见第十一节） |
| 零拷贝 | 归零 | ❌ 已证伪（D3D11 上下文冲突致 TDR） |
| 多解码器 | 无 | ❌ 瓶颈在读回，不在解码 |

## 八、一句话总结

```
一帧 4.9ms ≈ 5.27MB ÷ 1.76GB/s（读回带宽）+ 1ms 的 memcpy + 0.9ms 分配
socket 没有积压，解码也不是瓶颈；
瓶颈是 D3D11 staging 读回这条路的有效带宽，只能靠减少数据量解决。
```

## 九、补充：省电降档是 3ms 的主因（2026-11-19）

前面测到的「等 Map 3.0ms」是在**驱动省电模式**下测的。设了 NVIDIA 的“最高性能优先”后重测，结论变了。

### 触发条件

nvidia-smi 在解码运行时采样：

```
pcie.link.gen.max     = 4
pcie.link.gen.current = 1      ← 只有 Gen1
图形时钟              = 255MHz  ← 空闲档
GPU 利用率            = 16%
```

**负载太轻，驱动把 PCIe 链路和核心时钟都压在最低档。**

### 设置后

NVIDIA app → 程序设置 → QmlScrcpy.exe → 电源管理模式 = **最高性能优先**：

```
pcie.link.gen.current = 4      （Gen1 → Gen4）
图形时钟              = 2580MHz
```

### 对比数据

| 段 | Gen1（省电） | Gen4（最高性能） |
|---|---|---|
| 准备 | 0.87~0.95ms | 0.82~0.85ms |
| **等 Map** | 1.3 → **3.0ms**（还递增） | **1.30~1.34ms（稳定）** |
| 读 | 0.87~1.16ms | 0.92~1.08ms |
| **合计** | **~4.9ms** | **~3.4ms** |

**等 Map 不再随运行时间上涨**——之前那个“递增”就是链路从空闲档往上升的过程。

### 剩下的开销

```
等 Map 1.3ms：5.27MB ÷ 1.3ms ≈ 4 GB/s（Gen4 理论 25GB/s）
              → 瓶颈变成 staging 读回路径本身（uncached、逐行、驱动开销）
准备 0.83ms ：每帧 make_shared<QByteArray>(5.27MB) 的分配 + 首次写入缺页
读   0.99ms ：5.27MB ÷ 0.99ms ≈ 5.5 GB/s，uncached 内存读取的实际速度
```

### 还能省的

| 项 | 收益 | 状态 |
|---|---|---|
| 帧缓冲池（复用 5MB 缓冲，引用计数归还） | 准备 0.83ms → 0.009ms，但**总时间不变** | ✅ 已做（见第十一节） |
| 非临时存储指令（`_mm_stream`） | -0.1~0.2ms | ❌ 需内联汇编，不值当 |

**结论：3.4ms 已经够用**（60fps 余量 5 倍、120fps 余量 2.4 倍）。

## 十、补充：Map 到底在等什么（2026-11-19 下午）

第九节说读回 1.3ms（Gen4 下），但那是在“GPU 空闲”的假设下推的。这一节把它坐实：**Map 大部分时间在等 GPU 队列排空，不是在等拷贝**。

### 三个实验

**① 普通 NV12 纹理的纯拷贝基准**

在解码器里临时加一个基准：建一张普通（非解码器）NV12 纹理，拷到 staging 再 Map，循环 30 次。

```
提交 1us / 等 Map 497us / 吞吐 ≈ 10 GB/s
```

**普通纹理拷 5.27MB 只要 0.5ms。**

**② 两步拷贝（先转普通布局再读回）**

```
解码器纹理（tiled） → 中间普通纹理 → staging
```

结果：等 Map **2143us，和单步一模一样**。说明瓶颈不是 tiled 布局。

**③ 送包后人为延迟 60ms 再取帧（让 GPU 队列排空）**

在 `Push` 的 send 与 drain 之间插 `msleep(60)`：

| 场景 | 准备 | 等 Map | 读 |
|---|---|---|---|
| 正常投递（GPU 一直忙） | 8us | **2147us** | 911us |
| 延迟 60ms（GPU 空闲） | 18us | **595~657us** | 817~921us |

（收帧显示 62ms 是因为延迟被算进去了，不影响结论）

### 结论

```
2.1ms = 0.6ms 真实拷贝 + 1.5ms 等 GPU 队列排空
```

- 拷贝本身 0.6ms，和普通纹理基准（0.5ms）吻合
- Map 的同步粒度是“GPU 队列排空”，不是“这一次拷贝完成”
- 所以：改拷贝方式（单步/两步）、加 Flush、调整投递顺序，全都无效

### 正确的优化方向：异步读回

```
帧 N   ：Copy 到 staging[A]，End(query[A])，立刻返回
帧 N+1 ：CheckQuery(staging[B])
           已完成 → Map B（几乎不阻塞）→ 读出来
           未完成 → 本帧跳过
         Copy 到 staging[B]，End(query[B])
```

- 等 Map：2.1ms → 接近 0
- 代价：画面延迟 +1 帧（60fps 下 16.7ms）
- 前提：双 staging + `ID3D11Query`（`D3D11_QUERY_EVENT`）

**这是唯一能压掉那 1.5ms 的办法**，纯吞吐不会变。

## 十一、帧缓冲池：省了 0.8ms，但总时间没变

### 做了什么

`h264_decoder.cpp` 里加 `FrameBufferPool`：

```cpp
struct FrameBufferPool
{
    QByteArray *Take(int size);      // 池里有就复用，没有才 new
    void Give(QByteArray *buffer);   // 引用计数归零时归还，最多留 3 个
    QMutex mutex;
    QVector<QByteArray *> free_list;
};
```

`Frame` 带着的 `shared_ptr<QByteArray>` 用了自定义 deleter：

```cpp
auto pool = pool_;                    // 捕获 shared_ptr，解码器先析构也不会悬空
std::shared_ptr<QByteArray> buffer(pool->Take(total_size), [pool](QByteArray *raw)
{
    pool->Give(raw);                  // 渲染器画完 → 归还池子
});
```

### 结果

| 段 | 缓冲池前 | 缓冲池后 |
|---|---|---|
| 准备 | 0.83ms | **0.009ms** |
| 等 Map | 1.30ms | **2.11ms** |
| 读 | 0.99ms | 0.90ms |
| **合计** | **3.4ms** | **3.3ms** |

### 为什么总时间没变

**之前的 malloc 是和 GPU 拷贝重叠的**：

```
提交 CopySubresourceRegion
   ↓
malloc 5MB（0.8ms）   ← 这段时间 GPU 正在执行拷贝
   ↓
Map（等拷贝完成）
```

省掉 malloc 之后，那 0.8ms 没有别的事填，直接还给了等待。

### 要不要留着

| 理由 | 说明 |
|---|---|
| 延迟 | 不变（3.4 → 3.3ms） |
| 内存 | 更好：不再每帧分配/释放 5MB，减少堆碎片和缺页 |
| 复杂度 | 增加（池子 + 锁 + 引用计数） |

**结论：留着**。它是“异步读回”（第十二节方向）的前提——异步读回需要多块缓冲轮转。
